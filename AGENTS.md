# AGENTS.md

Guidance for coding agents (and humans) working in this repository. This is the
canonical instructions file — `CLAUDE.md` just imports it, so edit this file,
not that one.

## What this is

A personal HPDE/track-day logbook on Cloudflare Workers + D1 (SQLite): tracks → events → sessions → laps, with progress charts and Google (plus optional Apple) OAuth sign-in. Multi-user — every domain row is scoped to a `user_id`. The hosted instance users are pointed to is https://trackevolution.app.

## Commands

```sh
npm install
npm run seed:generate       # writes seed/seed.sql from seed data (see below)
npm run db:migrate:local    # applies migrations/ to the local D1 SQLite
npm run db:seed:local       # loads seed/seed.sql locally
npm run dev                 # wrangler dev → http://localhost:8787
npm test                    # vitest: unit tests + API tests against a real D1 (miniflare)
npm run typecheck           # tsc over src/ and test/ (no linter is configured)
```

Local dev needs a gitignored `.dev.vars`:

```
DEV_MODE=1
DEV_USER_EMAIL=you@example.com   # must match the seed data's USER_EMAIL
DEV_USER_NAME=Your Name
GOOGLE_CLIENT_ID=dev
GOOGLE_CLIENT_SECRET=dev
```

`DEV_MODE=1` makes `GET /auth/login` sign in as a fixed local user (no Google OAuth) — navigate there once to get a session cookie. The bypass only answers on local dev hosts (`localhost`, `127.0.0.1`, `[::1]`, and the Android emulator's `10.0.2.2`); on any other hostname login falls through to real OAuth, so a leaked `DEV_MODE=1` fails closed. Still, never set it in production.

Deployment: `npm run deploy` (plus `db:migrate:remote` / `db:seed:remote`). Secrets are set via `npx wrangler secret put`.

Native clients (`apps/`, own build systems, not part of the npm project):

```sh
cd apps/ios/Packages/TrackEvolutionKit && swift test   # iOS pure logic, no simulator
# the iOS screens end to end; needs `npm run dev`, skips without it
xcodebuild test -project apps/ios/TrackEvolution.xcodeproj -scheme TrackEvolution \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:TrackEvolutionUITests/CoreScreensUITests
apps/ios/generate.sh                                   # regenerate the Xcode project from project.yml
node apps/ios/Tools/generate-tokens.mjs                # regenerate iOS color tokens from public/style.css
cd apps/android && ./gradlew :core:test                # Android pure logic, no emulator
cd apps/android && ./gradlew :core:check               # …plus the "no Android dependency" guard
cd apps/android && ./gradlew :app:assembleDebug        # the Android Compose shell (needs ANDROID_HOME or local.properties)
cd apps/android && ./gradlew :app:bundleRelease         # the Play Store .aab (unsigned without TE_UPLOAD_KEYSTORE*)
node apps/android/tools/generate-tokens.mjs            # regenerate Android color tokens from public/style.css
npm run contracts:generate                             # refresh contracts/golden/ (the pinned API contract)
npm run contracts:logic                                # refresh contracts/logic/ (cross-language fixtures for ported logic)
npm run contracts:check                                # regenerate both and fail if the tree is dirty
```

## Issues close with the PR that finishes the work

Tracked work has a GitHub issue — the native rewrite has one per `NS-*` spec
under epic #63 (`gh issue list --search "NS-13" --state all`). **Closing it is
part of the change, not a follow-up:** put `Closes #<n>` in the PR body, one line
per issue, so merging does it.

A PR that only *partly* implements a ticket uses `Refs #<n>`, leaves the issue
open, and comments on it with what's outstanding. Never close an issue whose
acceptance criteria aren't all met — a ticket closed early is worse than no
ticket, because the remaining gap stops being visible.

## Architecture

One Worker serves both the API and the static frontend (`wrangler.jsonc`: `public/` is served as SPA assets; `/api/*` and `/auth/*` hit the Worker first).

**Backend** (`src/`, Hono):
- `index.ts` — composes the routers. Route order matters: `/api/share` (public, no auth) is registered before `/api` so `GET /api/share/:slug` stays unauthenticated while everything else under `/api` passes through `requireSession` (`middleware.ts`).
- `routes/` — one router per resource: `auth.ts` (Google OAuth or the DEV_MODE bypass → `auth_sessions` row → `session` cookie; a first sign-in claims a user row by matching email where that provider's sub column is NULL — which covers pre-seeded rows *and* cross-provider linking, so Google and Apple sign-ins with the same email share one account, and *because* accounts are claimed by email, both callbacks reject id_tokens whose email isn't verified (`isEmailVerified` in `lib/oidc.ts`); plus the native-app flow — `?client=app&code_challenge=…` runs OAuth in the system browser and redirects to `trackevolution://auth` with a single-use code that `POST /auth/exchange` trades for a bearer token, PKCE-verified. Sign in with Apple is feature-flagged by the four `APPLE_*` secrets — `GET /auth/providers` tells the login screen whether to draw the Apple button — and mirrors the Google flow under `/auth/apple/*` with two quirks: the client secret is a self-signed ES256 JWT from `lib/apple.ts`, and Apple's email-scope callback is a *cross-site POST* (`response_mode=form_post`), so its state/PKCE cookies are `SameSite=None` and the callback route is a POST), `me.ts` (the signed-in user and their totals, plus `PUT /me/checklist-template` — the per-user prep list new event checklists start from, `users.checklist_template`, null meaning "use the client's built-in default"), `tracks.ts` (tracks + `GET /tracks/:id/setups`, the "setup vs. lap times" rows for a track), `events.ts` (events; per-event-day setup sheets — `PUT`/`DELETE /events/:id/setups/:day` upserting JSON validated by `sanitizeSetup`, plus `GET /events/:id/setups/prefill` for the copy-forward form prefill; `events.car` stays free text but is auto-matched to a garage vehicle by name into `events.vehicle_id` on create/update, and `events.track_hours` optionally overrides the on-track-hours estimate), `sessions.ts` (sessions + laps), `vehicles.ts` (the per-user garage backing Settings → Vehicles — at most one `is_default` row per user pre-fills new events — plus the garage logbook: `GET /garage` returns every vehicle with accrued hours and its parts, each carrying measurements and a computed `wear` estimate; parts CRUD under `/vehicles/:id/parts` + `/parts/:id`, one-tap replacement via `POST /parts/:id/refresh` — retires the part as of the swap date and inserts a same-spec successor — wear measurements under `/parts/:id/measurements`; a new part with no expected life defaults it from retired lifecycles of the same kind), `share.ts` (authed slug management plus the public share endpoint, which returns stats/times but strips notes, email, per-lap data, and all garage/setup linkage), and `wellKnown.ts` (`/.well-known/apple-app-site-association` for iOS Universal Links; the Android `assetlinks.json` is a static file in `public/.well-known/`).
- `middleware.ts` `requireSession` accepts the session as the `session` cookie (web) **or** an `Authorization: Bearer` header (native apps) — same `auth_sessions` rows. There is deliberately **no CORS**: the web app is same-origin and the native clients are HTTP clients that send no `Origin`, so nothing needs it (`lib/cors.ts` existed only for the retired web-view shells' local origins and was deleted with them — `test/api/native-auth.test.ts` now asserts that no origin gets a CORS header).
- `db.ts` — data-access helpers. All take `(db, userId, ...)` explicitly so ownership scoping is visible at call sites: `ownedEvent`/`ownedSession` guard nested writes, `resolveTrack` find-or-creates tracks by name (`COLLATE NOCASE`; the name carries the layout — "Virginia International Raceway (Full)" vs "(Patriot)" — so bests/goals never mix across layouts), and `eventSelect`/`listEvents`/`tracksSummary` produce event rows with lap aggregates (a single-pass LEFT JOIN + GROUP BY, not per-row subqueries). D1 pays a network round trip per statement, so helpers backing a single endpoint also expose prepared *statements* (`…Stmt`) that routes combine with `db.batch()` into one round trip, and ownership checks on simple writes are folded into the write itself (`WHERE … user_id = ?`, or `INSERT … SELECT` from an ownership-scoped query, with zero changed rows meaning 404) rather than issued as a separate `SELECT` first. Tracks stay per-user, but each row carries a nullable `catalog_id` into the seeded `track_catalog` table — a canonical identity matched by name (NOCASE) via `catalogIdForName` on create and rename, so the same physical track is recognizable across users without sharing user-entered data. The catalog also backs the track-name suggestions in the event form (`GET /api/catalog`); adding a track to it means a new migration.
- `lib/` — pure logic, unit-tested: `stats.ts` (`withComputed` derives `best_ms = MIN(manual best_time_ms, best logged lap)`, `consistency` — coefficient of variation, only with 3+ laps — and `hours` via `eventHours`), `wear.ts` (the garage's math: `eventHours` — override, else `max(days × 2h, logged lap time)`; `wearEstimate` — accrued hours/heat cycles per part plus remaining-life projection, least-squares from 2+ measurements else expected-hours prior), `validate.ts` (slug/goal/lap validation, `sanitizeSetup` for setup sheets, `sanitizeChecklist`/`sanitizeChecklistTemplate` — the second takes plain strings, since a template carries no done flags, and treats an empty list as "cleared" so deleting every item leaves the built-in default rather than nothing, part kind/date validation), `session.ts` (session token + cookie plumbing; session tokens and one-time auth codes are stored SHA-256-hashed — `sha256Hex` — so the DB never holds usable credentials), `oidc.ts` (id_token decode + `isEmailVerified`), `apple.ts` (Sign in with Apple: the ES256 client-secret JWT and the first-auth `user` name field).

**Frontend** (`public/`, dependency-free vanilla JS as native ES modules — no build step):
- `app.js` — the module entry (`<script type="module">`): app state, `shell()`, the views and the hash router (`#/`, `#/new`, `#/event/:id`, `#/event/:id/edit`, `#/track/:id`, `#/vehicle/:id` — the garage page: consumables with wear bars/projections, measurement logging, the add-part form and the track-hours ledger — `#/settings` — vehicle garage management plus the privacy/terms links, reached from the account dropdown — plus public `/share/<slug>` pages with their own hash routes). The event page carries the per-day setup notebook (copy-forward prefill, changed-value highlighting), the track page a "Setup vs. lap times" diff table, and the dashboard a maintenance-due strip + garage cards fed by `GET /api/garage`. Each route re-renders the whole view via `shell()`, so element handles go stale after any navigation; module-level listeners are used where per-render listeners would accumulate. HTML is built with template strings — always pipe user data through `esc()`.
- `js/` — extracted modules, importable by unit tests: `checklist.js` (`DEFAULT_CHECKLIST`, the prep list a new event's checklist starts from — its own module so `contracts/logic/checklist.json` can import it and pin the iOS port `EventDates.DEFAULT_CHECKLIST` to it; a user who edits the list in Settings gets their own, served by `GET /api/me`), `format.js` (`fmtMs`/`parseTime`/`esc`…), `garage.js` (the garage/setup helpers: the setup-sheet field spec — mirrors `sanitizeSetup` in `src/lib/validate.ts`, keep in sync — `flattenSetup`/`diffSetups` for the correlation views, and part-kind/wear-status/remaining-life formatting), `chart.js` (hand-rolled SVG `lineChart` + `multiLineChart` lap overlay; lower lap time plotted lower = improvement trends downward), `channel-graphs.js` (an imported session's lap list as chips plus per-lap speed/RPM/lateral-G overlay charts in a collapsible `<details>`, on a shared driven-distance axis; up to 3 laps highlighted via the chips in the `--chart-line`/`-b`/`-c` slot colors, the rest a dim envelope; with 2+ laps highlighted a lap **delta chart** renders above the channels — `lapTimeSeries`/`deltaSeries` integrate elapsed time from the stored speed samples, scaled to the timed lap, pinned for ports by `contracts/logic/lap-delta.json`), `lap-stats.js` (per-session analysis: best-N avg, pace slope, warmup), `year-review.js` (year-in-review aggregation), `api.js` (fetch wrapper throwing `ApiError` with status — same-origin requests with cookie auth; routes everything through the offline layer below), `theme.js`, `pull-refresh.js` (touch pull-to-refresh: dampened pull past a threshold re-runs the current route's fetches, with the brand chevron sweeping left→right in a pill while refreshing; `initPullRefresh` is wired at the bottom of `app.js`).
- `js/offline.js` + `js/prefetch.js` — the offline-first layer (also the reference the native apps' offline stores are ported from — NS-21/NS-22). `offline.js` keeps an IndexedDB cache of GET `/api` responses (in-memory backend in Node, so it's unit-testable) plus a persistent queue of writes made offline: `api.js` GETs are network-first with cache fallback, and queueable mutations (events/sessions/laps/setup-sheet/track edits — the whitelist is `QUEUEABLE`; vehicle and garage-part writes need a live server and fail offline normally) are stored, patched into the affected cached responses so the UI shows them immediately, and replayed in order on reconnect, with temp ids (`tmp-N`) mapped to real ids; `app.js` then remaps any `#/event/tmp-N` hash. Deleting a not-yet-synced row just cancels its queued items. Conflict policy is last-write-wins; server-rejected writes are dropped and surfaced in the shell's `#sync-banner` (updated in place by `updateSyncBanner`). `offline.js` deliberately mirrors two backend behaviors — `recomputeDetail` ↔ `withComputed` in `src/lib/stats.ts` (including the `hours` rule from `src/lib/wear.ts`), `cleanLaps` ↔ `sanitizeLaps` in `src/lib/validate.ts` — keep them in sync. `prefetch.js` warms the cache after a dashboard load: every event detail is prefetched, re-fetching only rows whose `updated_at` (new in migration 0011, trigger-maintained) differs from the cached copy. Signing out clears cache + queue.
- `js/record/` — **reference implementations, not app code**: the live lap recorder is native-only (NS-15…NS-18) and nothing under `public/` imports these modules, but they are the JS originals both native recorder ports are asserted against, so they are kept, unit-tested (`test/unit/record.test.js`, `record-remote.test.js`) and pinned by fixtures `contracts/logic.mjs` generates *from them* — deleting or changing them changes both ports' contract. `core.js` is the recorder's pure logic — fix validation/buffering, forgot-to-stop auto-stop (arms only after the car has been driven at track pace, so grid waits don't kill a recording), idle trimming, checkpoint (de)serialization (pinned by `contracts/logic/recorder.json`), and `toParsed()`, which emits the same `{kind: "live", gps, needsLine, laps: []}` shape as a file parser so a recording drops into the review/line-picker flow. `remote.js` is the remote-start attachment rule (`pickRecordingEvent`: attach to the event whose `start_date`+`days` cover today — never guesses further — else record with `eventId: null`, since recording is on-device and must not depend on the network or session), pinned by `contracts/logic/remote-attach.json`. `live-timing.js` is the on-track lap counter and predictive delta shown on the native record screens — the recorder has no start/finish line during a session, so it anchors its own gate at the first track-pace fix (the pit exit, on the racing line) and times crossings of it, comparing the running lap against the session's best by distance; ported as `LiveTiming` to the Kit and `:core`, pinned per-fix by `contracts/logic/live-timing.json`. The web recording UI that used to sit on top (`ui.js`, the `#/event/:id/record` route, the event page's record panel, the dashboard's unsaved-recording banner) was unreachable in a browser once the web-view shells were retired and was removed in #139.
- `js/import/` — the telemetry import feature: `channels.js` builds the per-lap channel data stored with imported sessions (`sessions.channels` JSON: each lap's speed — plus RPM/lateral G for PDR — resampled onto a 20 m driven-distance grid; the shape is validated server-side by `sanitizeChannels` in `src/lib/validate.ts` — keep the two in sync); `parse.js` dispatches a dropped file to a parser (`.vbo` → `vbo.js`, `.mp4` → PDR first, then GoPro `gpmf.js`); every parser returns `{kind, date, time, durationS, laps, gps, needsLine}`. `geo.js` projects GPS traces to local meters and derives laps from start/finish line crossings; `pdr-laps.js` recovers laps for beacon-less PDR recordings from latitude+odometer periodicity (autocorrelation lap length; start/finish phase anchored to a beacon-timed batch-mate via `anchorPdrBatch`); `ui.js` is the dropzone/review flow, including the click-a-map line picker for GPS sources without lap markers — GoPro, plain VBO (one picked line applies to the whole batch, with automatic longitude-sign mirroring for Racelogic's west-positive convention). Test fixtures for all formats are generated by `test/fixtures/build.mjs`. Real sample recordings for manual import testing live in the gitignored `telemetry-samples/` at the repo root — never commit footage.
- `pdr.js` — parses lap times, the GPS trace, and car metrics (top speed / max RPM / max lateral G) out of Corvette PDR (Cosworth) MP4 telemetry entirely in the browser via byte-range reads; the video is never uploaded. The beacon/odometer lap-derivation logic is reverse-engineered — see README before touching it. The stream is **delta-encoded** (framing matches ExifTool's GM.pm): each channel gets one full record, then 8-byte diffs against running decoder state that persists across samples — decoding the deltas is what yields ~11Hz lat/lon (radians, scaled via the `mrld` channel dictionary) and the Speed/RPM/acceleration channels. Coordinates only become a `gps` trace behind plausibility checks; when they don't decode, the raw latitude/odometer series returned as `channels` still feed lap recovery in `js/import/pdr-laps.js`.
- PWA: `manifest.webmanifest` + `sw.js` make the app installable and offline-capable (the service worker covers the app shell and last-known responses; structured offline reads/writes live in `js/offline.js` above). The service worker serves static files stale-while-revalidate (no build step, so no cache busting — changes land on the *second* load), navigations and `GET /api/*` network-first with cache fallback; `/auth/*` and non-GET are never intercepted. Signing out deletes the cached API data (`th-data-*` caches) so a shared device doesn't retain the previous user's logbook. Icons in `icons/` + `favicon.*` are generated from the brand mark — regenerate rather than hand-edit if the mark changes.

**Native clients** (`apps/`, the shipped iOS and Android apps — one spec per `NS-*` id in `docs/specs/native/`, which also records the fixed decisions and the deliberate web/native feature split): `apps/ios/` is a SwiftUI-lifecycle app (`App/`) plus a local SPM package `Packages/TrackEvolutionKit/` holding all pure logic — models, API client, recorder core, lap geometry, offline store — which **must never import UIKit or SwiftUI**; it builds for macOS as well as iOS, which is what lets `swift test` run the suite in seconds with no simulator. `TrackEvolution.xcodeproj` is generated from `project.yml` by XcodeGen *and committed* (a clean checkout, and CI, needs only Xcode), so project settings are changed in `project.yml` followed by `apps/ios/generate.sh` — never in Xcode's inspector, where the edit would be lost on the next generate; shared schemes XcodeGen can't express (the package's test scheme) live in `apps/ios/Schemes/` and are copied in by that script. Load-bearing: bundle id `app.trackevolution` (kept from the retired shell so the native build shipped as an in-place App Store update, preserving ratings and the Universal Links association — Xcode Cloud archives *this* project, and `MARKETING_VERSION` in `project.yml` is the shipping one), deployment target iOS 17, Swift 6 language mode with complete concurrency checking, and `com.apple.developer.carplay-driving-task` **is** checked in (Apple has granted it) — dropping the key fails no build and no test, it just makes the CarPlay scene stop attaching, so CI asserts its presence and lints every entitlements file. CarPlay itself is `App/CarPlay/`: a single-template `CPTemplateApplicationScene` driving the *same* recorder the phone UI does, reachable from UIKit via `AppServices`, with the event-attachment rule ported into the Kit's `RemoteRecording` and pinned against the web implementation by `contracts/logic/remote-attach.json`. `apps/android/` is a Gradle project split the same way: `:core` is pure Kotlin/JVM (no Android dependency, enforced by a `checkNoAndroidDependency` task that fails the build if one appears) and `:app` is the Compose shell — `applicationId`/`namespace` `app.trackevolution`, kept from the retired shell for the same in-place-update reason as iOS, `minSdk` 26, Java 17 bytecode while `:core` stays on 21. Every plugin version is declared once in the root `build.gradle.kts` with `apply false` (the Kotlin JVM and Kotlin Android plugins are the same artifact, so a second version declaration makes Gradle refuse to resolve either), and libraries live in `gradle/libs.versions.toml`. Building `:app` needs an SDK (`ANDROID_HOME` or a gitignored `local.properties`), but `:core:test` deliberately does not — AGP defers its SDK check to task execution, which is what keeps CI's core job SDK-free and under a minute; the `app` job installs the SDK and runs `:app:assembleDebug` plus `:app:testDebugUnitTest` (Robolectric, so still no emulator). Manifest permissions (location, background location, foreground service, `POST_NOTIFICATIONS`) are **declared, not requested** — the runtime request belongs to the feature that needs it, so the user is asked in context. The launcher icon is the adaptive icon inherited from the retired shell and the launch theme is `Theme.TrackEvolution.Splash` (androidx core-splashscreen, brand near-black `#0A0A0B`), swapped for the real theme by `installSplashScreen()`; the *window* theme underneath Compose follows the system's light/dark through `values-night/`, since it is drawn before Compose can consult the in-app override. `:core` carries the ported logic (`RecorderCore`, `GeoTrace`, `LapTime` — the port of `public/js/format.js`) plus `model/` and `api/`: `@Serializable` data classes with explicit `@SerialName` on every field (never a global snake_case strategy — a mismatch has to be visible at the field), and `ApiClient`, a Ktor client whose **engine is injected** so `:app` supplies OkHttp while tests drive the identical code through `MockEngine`. Two decisions there are load-bearing: responses decode with `ignoreUnknownKeys = false`, so a field the server adds and no model covers fails a test instead of vanishing, and `GoldenContractTest` decodes *and re-encodes* every entry in `contracts/golden/manifest.json`, which is what also catches a field the model has and the server doesn't. Failures map to a sealed `ApiException` carrying the server's own `{ error }` string — `Unauthorized` is its own case so re-auth is a type check, and `Transport` (no answer at all) is deliberately distinct from a status, because only one of the two is worth retrying. Epoch-millisecond columns are `Long`; Kotlin's `Int` is 32 bits, which is why NS-04 can spell `updated_at` as Swift's 64-bit `Int` and this cannot. Update requests use a three-state `Patch` (`Unchanged` omits the key, `Set(null)` sends an explicit null) because the server writes only the columns *present* in the body. `contracts/golden/` (regenerate with `npm run contracts:generate`, verify with `contracts:check`) pins every API response as JSON so both clients' decoders are tested against the real thing; `contracts/logic/` (`contracts:logic`) does the same one level down for *ported pure logic* — it runs the web implementation and commits its output, so the ports assert equality with the reference rather than with each other (the iOS lap-geometry port matches `public/js/import/geo.js` lap times to the millisecond). Design system: `public/style.css` stays the source of truth, and the iOS color tokens are *generated* from it by `apps/ios/Tools/generate-tokens.mjs` into an asset catalog (Any = the stylesheet's light values, Dark = its dark defaults) plus a token list for the debug-only gallery (`-tokenGallery` launch argument) — so use `Color(.bgPage)`, never a hex literal, and re-run the generator rather than editing either output. On iOS Geist isn't bundled (no font binaries in the repo), so `App/DesignSystem/Typography.swift` falls back to SF Pro/SF Mono behind a documented seam. Android has the same arrangement one directory over: `apps/android/tools/generate-tokens.mjs` reads the same two stylesheet blocks and writes `app/src/main/kotlin/app/trackevolution/ui/theme/ColorTokens.generated.kt` (a `TrackColors` data class plus the light and dark instances and a catalog for the gallery), consumed through `TrackTheme.colors` — with `TrackTypography`, `TrackRadii` and `TrackMotion` beside it and a Material `ColorScheme` derived from the tokens only so unwrapped Material components aren't the wrong color. **Dynamic color (Material You) is off on purpose** — the accent is the charts' "faster" signal — and `surfaceTint` is transparent so Material's tonal-elevation wash can't reintroduce depth the design system draws as a hairline plus one surface step (`TrackCard`). Geist and Geist Mono *are* bundled there, as single variable fonts pinned per weight with `FontVariation` (SIL OFL 1.1; the license ships in `assets/licenses/`), sizes in `sp` and tracking in `em` so both scale with the system font setting. The theme override (system/light/dark, mirroring `public/js/theme.js`) persists in DataStore via `ThemePreference`. The gallery is `TokenGalleryActivity` in the **`debug` source set** with its own manifest and launcher entry — not compiled into a release build at all, rather than merely unreachable. **Android sign-in** (NS-09) splits the same way: `:core` owns the pure half — `Pkce` (base64url-unpadded `S256`, using `java.util.Base64` rather than `android.util.Base64`, whose default flags append a newline and fail verification), the `/auth` client methods, and `DeepLink`, the routing-table port that is unit-tested rather than tapped through and which deliberately refuses `trackevolution://auth?code=…` so navigation can never race the sign-in flow for a code that is burned on first use. `:app` owns everything Android: a **Chrome Custom Tab** (never a WebView — Google blocks OAuth in embedded web views, and `CustomTabs.open` must be handed an *Activity*, since launching from the application context throws and `FLAG_ACTIVITY_NEW_TASK` would put the tab in the wrong task), and `AuthStore`, an `EncryptedSharedPreferences` file holding the token *and* the in-flight PKCE verifier — the verifier because the flow leaves the process when the browser opens, and both readable while the device is locked because the lap recorder runs locked and has to sync. `AuthController.handleRedirect` ignores a code with no pending flow behind it, which is what stops a redelivered intent after a recreate from burning a good session. The provider buttons come from `GET /auth/providers` and are cached **per server** (`AuthProvidersStore`), so a failed fetch is a no-op rather than a silent downgrade to Google-only, and pointing a debug build at `wrangler dev` and back never carries one deployment's answer to the other. The dev-server override and its cleartext exception (`10.0.2.2`, the emulator's alias for the host, where the server's `DEV_MODE` bypass answers) are gated to debug builds — the network-security config lives in the `debug` source set so no release build can ship one. **App Links** are verified against `public/.well-known/assetlinks.json`, which carries the **Play app-signing** SHA-256 — so verification succeeds only for a Play-signed build, never for a locally-signed debug one; check with `adb shell pm get-app-links app.trackevolution`. The file is served by the Worker from `public/`, so changing the signing key means redeploying the Worker, not shipping an app update. **The Android lap recorder** (NS-16) is `app/.../recording/`: a foreground `Service` with `foregroundServiceType="location"` that **owns the recording**, so the UI can be swiped out of recents without stopping it — and which is why the native app needs none of the legacy-bridge workaround the retired shell carried to stop Android halting its WebView's background location after five minutes. `startForeground` is called **before** any permission check or I/O, because the system kills the process if it hasn't happened within five seconds of `startForegroundService`. Deliberately `START_NOT_STICKY`: a service the system restarts with no recording state would post a notification claiming to record while capturing nothing, so restart is handled by recovering the journal instead. Durability is `RecordingJournal` in `:core` (plain `java.io`, so it unit-tests against a real temp file with no emulator) — an append-only JSONL file written **per accepted fix**, whose tuples are byte-identical to `RecorderCore.serializeRecording`'s; a **deviation from NS-16's "use Room"**, taken for the same reasons iOS deviated from NS-15, and documented at the class. It is flushed but not `fsync`ed, which covers a force-stop and a crash but not power loss — an fsync at 10 Hz is not worth the battery. `Location.toFix()` is where Android's "no reading" sentinels die: `hasSpeed()`/`hasAccuracy()` gate the values, because a 0 that means *unknown* is indistinguishable from one that means *stationary* once it is in the trace, and `location.time` (the fix's own) is used rather than the delivery clock so a batched delivery isn't rejected wholesale by `addFix`'s monotonic check. Permission staging is not a choice: Android **rejects** a combined fine + background request, so `RecorderPermissions` reads them separately and `POST_NOTIFICATIONS` is its own ask on API 33+ — without it the foreground notification is silently invisible, which was the second defect the retired shell shipped. The `Recorder` object is the observable seam (state plus the finished/recovered recording) that NS-18's screen and NS-20's Android Auto both read, and `RecorderHarnessActivity` in the `debug` source set is a bench for driving it directly. **Android Auto (NS-20) is built but does not ship**: Play rejected it under `PF-1` because Android has no category permitting a driving-task app (POI is the closest, and a lap timer has no point-of-interest functionality — there is no Android equivalent of the CarPlay entitlement Apple granted). Everything car therefore lives in the `debug` source set — sources, `res/xml/automotive_app_desc.xml`, the `<service>` and both `<meta-data>` blocks in `app/src/debug/AndroidManifest.xml`, and `androidx.car.app` as `debugImplementation` — because the *declarations* are what make an artifact car-compatible to the review pipeline, so merely unregistering it would not be enough. `:app:checkReleaseHasNoCarApp` fails the build if one reappears under `src/main`, since CI only ever builds the debug variant and nothing else would notice until a store review. The Android Auto **form factor must also stay opted out in the Play Console** — a non-compliant car artifact in the production track rejects the entire submission, phone updates included, and no build can guard Console state. **The recording UI** (NS-18) sits on top: `SignedInScaffold` keeps the recording banner *above* the destination so an in-progress or unsaved recording is visible from anywhere, and a `BackHandler` that navigates rather than stops — a recording must not be endable by a gesture. `RecordingFlow` holds the review state above the view tree, so a rotation cannot lose a pick. The picker's geometry is `TraceMap` in `:core` (fit, hit-test, and the y-flip that keeps north up — get it wrong and every circuit draws mirrored), and the pick itself is `LineReview`, which names the two ways a pick legitimately yields nothing — a stationary pick has no direction to build a gate across, a line crossed once has no lap — because each needs different advice and a silent empty list is the dead end the web app's wording exists to prevent. Saving posts `laps` as integer milliseconds plus the best lap's polyline, and **`channels` is explicitly null**: per-lap channels come from the telemetry importers, which are web-only, and `sanitizeChannels` rejects a half-formed shape with a 400. The journal is cleared only *after* the server accepts, so a failed save in a paddock costs a retry and never the session. **The Android charts** (NS-24) split the same way again: `:core` carries `ChartScale` (the port of the scale maths in `public/js/chart.js`) and `ChannelGraphs` (the non-drawing half of `channel-graphs.js`, with `matchLapsToChannels` pinned to `contracts/logic/channels.json`), while `app/.../ui/charts/` draws — `ProgressChart`, `TrackMap` and `LapChannelChart`, all hand-rolled on Compose `Canvas` rather than on Vico, since `LinePicker` already established the Canvas idiom and a charting library's axis defaults would have to be fought rather than used. Three things there are load-bearing. **Lower lap times plot lower** — `ChartScale.plottedFraction` returns a fraction measured *from the top*, and a Compose canvas already grows y downward, so it is used as-is; inverting a second time yields a chart that reads exactly backwards, which iOS shipped once. **The reference is the web, not iOS**: iOS's `ChartScale` chose 4% y-padding against `chart.js`'s 12%-with-a-500 ms-floor and returns `1` rather than `0.5` from `speedFraction` for a constant-speed trace, so the Kotlin port follows the JS and records the divergence at the class — NS-24 asks for parity of *meaning*, not of padding. And `ChannelGraphs.valueExtent` is deliberately separate from `valueDomain`: the domain is padded so the trace does not touch the frame, and 8% below a speed of zero is a *negative speed* — fine as an axis bound, nonsense in the screen-reader summary, which is what surfaced it. Every chart carries a `contentDescription` saying which way the trend goes, because down-is-better is precisely the convention a screen-reader user cannot see, and the lap chips carry number and time beside their colour dot so identity is never colour-alone. `ChartGalleryActivity` in the `debug` source set is the bench — all four in both themes, plus the 20,000-fix line picker, since a stored trace is capped at 300 points by `GeoTrace.lapTrace` and only a raw recording reaches that size. **The Android offline layer** (NS-22) is `:core`'s `offline/`, the port of `public/js/offline.js`: `OfflineStore` (response cache, write queue, temp ids, ordered replay), `applyLocal` in `OfflinePatch.kt` (the optimistic patches that keep the dashboard, event page and track page agreeing before a sync), and `OfflineMirrors` — `recomputeDetail`/`cleanLaps`, now the *fourth* copy of two server behaviors, which is why all four are tabulated at the class. Storage sits behind `OfflinePersistence`, whose only entry point is a transaction, so a queued write and the optimistic cache patch that makes it visible commit **together** — the win over IndexedDB that both native clients take; the in-memory implementation is what lets the replay algorithm unit-test on the JVM in milliseconds, and the durable half is `:app`'s `data/`. That half is a single Room database (`OfflineDatabase`; schema exported to `app/schemas/`) behind `RoomOfflinePersistence`, deliberately with **no destructive-migration fallback** — the cache is refetchable, but the queue holds recorded sessions that exist nowhere else until they replay, so a schema change owes this database a real migration rather than a silent wipe on an app update. Replay is `ReplayWorker`, a WorkManager `CoroutineWorker` behind a `CONNECTED` constraint that **only reports success on an empty queue** — anything else is `retry`, which is what stops a write queued *during* a flush from being stranded, since `OfflineStore.flush` snapshots the queue when it starts. `SyncScheduler` enqueues it as unique work with `KEEP` (never `REPLACE`, which would cancel a replay mid-queue) from two triggers: any pending write, and a `ConnectivityManager.NetworkCallback` — a callback rather than a poll, and treated as a hint only, since a captive portal reports connected too. All of it hangs off `AppServices`, the process-wide holder behind the new `TrackEvolutionApp`, and it is a singleton for a load-bearing reason: `OfflineStore` keeps the pending count and the flush lock **in memory**, so a second instance over the same database would let the worker and the UI replay the same queue concurrently and interleave writes. Durability is asserted against real SQLite, not the in-memory fake, by `:app`'s Robolectric suite (`./gradlew :app:testDebugUnitTest`, now a CI step) — the fake proves the logic reloads, which is a different claim from the file surviving. A temp id is a **negative Int**, not `tmp-N`: `Event.id` is an `Int` pinned by the golden contract, real server ids are always positive, and the value never reaches the server — the same call iOS made, so the representation differs while the behavior doesn't. `ApiClient` *is* the offline layer once it is given a store: reads are network-first and fall back to the cache only on a *transport* failure, never on a status (answering a 500 from a stale cache would hide it), a queueable write with nowhere to go becomes a queue entry plus a synthetic `{id}`/`{ok}` response, and a write made while others are pending queues too rather than jumping the line. Every case in `test/unit/offline.test.js` has a Kotlin counterpart in `OfflineStoreTest`, and `OfflineMirrorsTest` checks the recomputation against the `contracts/golden/` event details rather than against itself. **The Android logbook** (NS-26) is `app/.../screens/` — one model per screen owning its fetches and writes, the composables staying layout — with `app/.../navigation/` holding the graph. Routes are **type-safe** `@Serializable` classes (`Route`), so a renamed argument breaks the build rather than a tap, and `routeFor` maps the `:core` `DeepLink` table onto them; none of the retired shell's `backButton`/hash-router approximation is ported. Four decisions there are load-bearing. **A screen's model is scoped to its `NavBackStackEntry`, not `remember`ed** (`rememberScreenModel`): a `remember` is discarded on a configuration change, so rotating would re-fetch every screen and throw away a half-typed event form. **The event form's draft additionally goes through `SavedStateHandle`** (`SavedState`, plus a `hydrated` flag so a re-`load()` cannot overwrite a restored draft with the server's copy) — the system killing a backgrounded app is ordinary on Android, and the draft is the one thing on these screens that cannot be re-fetched. **Review is an overlay above the graph, not a destination**: "save or discard this recording" is modal, and putting it on the back stack would let a gesture bury an unsaved session behind the logbook — while the recording banner stays above the destination, so it is visible from every screen (both rules inherited from NS-18, which the scaffold now hosts a `NavHost` in place of its enum). And **back at the root minimizes rather than finishing the activity** (`moveTaskToBack`), because the task may have a recording notification attached to it — the same call the retired shell made. `FollowTempIds` watches the queue and replaces a destination parked on an offline-created id (`Route.remapTempId`) the moment the write flushes, popping the stale entry with it. `SharedLogbookScreen` exists even though it is not one of the spec's five screens: `/share/<slug>` is where an App Link lands, and without it a shared link opens a blank app. Two absences are deliberate and stated on screen rather than stubbed — the **setup notebook and the two-event lap overlay stay web-only**. The **garage is built** (NS-31, `screens/VehicleScreen.kt` + `VehicleModel.kt`), on the same terms as iOS: the wear math is not ported, since `GET /api/garage` arrives already computed by `src/lib/wear.ts`, and only the presentation is, pinned to `contracts/logic/garage-status.json`; its writes stay off the offline queue, so the garage is readable offline and not writable. Settings also carries the theme override, the share slug, the prep-checklist template and — required on every platform, since a native app renders no footer — the privacy policy and terms. The template itself reaches the editor through `ChecklistTemplateStore`, implemented by `AuthController`, so the list Settings writes and the one the event page's "Use my list" reads are one value rather than two copies; the interface exists so the editor's ordering logic is testable without standing up an encrypted token store. The dashboard now offers a **"Record laps" button** beside `+ Add event` (#108), matching iOS — so the recorder has two doors on Android, this and the event page, where the web has only the latter. It is **idle-only**: a live recording already has the scaffold's always-visible banner and an unsaved one has its card, and a third control would be a third answer to "what is the recorder doing". Which event it attaches to is `RemoteRecording.pickRecordingEvent` over the already-loaded event list — the *same* rule Android Auto and iOS use, pinned to `contracts/logic/remote-attach.json` — so it costs no request, works offline, and no two doors can disagree about where the laps belong. Null is the normal outcome on a day that isn't a track day: it records unattached rather than guessing at a near event, and the banner then offers the recording to the first event that opens it. The visible label stays two words and the **content description** carries the target ("Record laps at <track>"), because a subtitle would push the fold down on every non-track day. **The Android garage** (NS-31) came next: `:core`'s `Garage.kt` is the port of the consumable half of `public/js/garage.js` — `partStatus`, `fmtHours`, `fmtRemaining`, `fmtCost` and `garageAlerts`, pinned to `contracts/logic/garage-status.json`, the *same* fixture iOS asserts against, so both ports are checked against the web implementation rather than against each other. **The wear math is not ported on this platform either**, and adding it would make a fifth copy (server, web mirror, iOS presentation, offline mirror, this): `GET /api/garage` arrives with every part's estimate already computed by `src/lib/wear.ts`, and the client only decides how to say it. That is also why **garage writes stay off the offline queue** — retiring a part rewrites its neighbours' wear, a new part's expected life is defaulted server-side, and a refresh is a retire-plus-create whose successor id the client can't invent — so the garage reads offline through the cache and does not write; `GarageApiTest` pins their absence from `isQueueable`. `app/.../screens/VehicleScreen.kt` is the page (tiles, a card per consumable with its wear bar and one-line story, measurement logging, add/edit/retire/replace/delete, the retired list with cost per hour, and the track-hours ledger), the dashboard gained the collapsed maintenance strip and a card per car, and Settings' vehicle rows now open a car rather than linking out to the web. `TEWearBar` is drawn on a `Canvas` rather than a recoloured `LinearProgressIndicator` — and **a part with no basis for an estimate draws no bar at all**, saying so in words instead, because an empty bar reads as "new" rather than "unknown". The ledger lists only *driven* events (`isUpcoming` filtered), since an event that hasn't happened has accrued no hours and the server's wear window excludes it too — a ledger that listed it would not add up to the hours in the tile above it. `DeepLink.Vehicle` now resolves to the car instead of falling back to the dashboard. One shell-level fix came out of building it: the scaffold applies **`imePadding()`** as well as `systemBarsPadding()`, without which the keyboard draws over the content and the submit button of any form long enough to scroll — the event form, a wear measurement — sits behind it unreachable. **Android Auto** (NS-20) is `app/src/debug/.../auto/` — **debug builds only, because Play rejected it** (see the category paragraph below): a `CarAppService` + `Session` + one `Screen` on the Car App Library, driving the *same* `Recorder`/foreground service the phone does — so both surfaces observe one object and cannot disagree, and connecting or disconnecting the car cannot interrupt a recording it never owned. It sits in `:app` rather than the `:auto` module NS-20 asks for, and the reason is structural: requirement 3 forbids a bridge layer, `Recorder` lives in `:app`, and a Gradle *library* module cannot depend on an *application* one — so `:auto` could only reach it through the bridge the spec rules out. Documented at `TrackAutoService`, the same way NS-15 and NS-16 recorded their deviations. `AutoRecording` holds every string and the template assembly, so the one surface that can't be opened on a desk still has tests: the Car App Library enforces its distraction caps by *throwing* when a template exceeds them, which makes template construction worth asserting rather than eyeballing. Two behaviours there are deliberate — a blocker outranks an active recording (location switched off mid-session is what the driver needs to see, not a timer that has stopped meaning anything), and a **missing notification permission is not a blocker**, matching `RecordingService`: the recording works, it's just invisible, and refusing to record over that trades the irreplaceable thing for the recoverable one. The attachment rule is `RemoteRecording` in `:core` — the port of `public/js/record/remote.js`, pinned to `contracts/logic/remote-attach.json`, the same fixture iOS asserts against; `Event` implements its `EventCandidate` interface so logbook rows pass straight in. Fractional days **truncate** and a nonsensical day count still covers the start date, both because the JS does and all three clients must land a recording in the same event. **The category risk landed: Play rejected the app over it.** Android Auto has no driving-task category — the supported set is navigation, POI, IoT, weather, media and communication, and quality criterion `PC-1` forbids features outside them. NS-20 declared **POI** as the least-bad fit, on the reasoning that the category is only reviewed once the app opts in to the Android Auto form factor in the Play Console. That opt-in happened at NS-27 and the review fired: rejected under `PF-1` ("meaningful functionality relevant to driving" *in the declared category*), which a lap timer has none of and cannot acquire — so this is not a fixable finding, and NAVIGATION would fail the same criterion. Google's tooling still labels the POI bucket "Parking and Charging", the pre-1.3 category names, which is why the rejection reads as a parking app. Everything car therefore moved to the **`debug` source set** — sources, `res/xml/automotive_app_desc.xml`, the manifest block, and the `androidx.car.app` dependencies (`debugImplementation`), with `AutoRecordingTest` in `src/testDebug`. CI only ever builds the debug variant, so the invariant is invisible — `:app:checkReleaseHasNoCarApp` (wired into `check` and its own CI step, in the spirit of `:core`'s `checkNoAndroidDependency`) fails the build if a car declaration reappears under `src/main`. The **garage is native** (`App/Screens/VehicleScreen.swift` + the Kit's `Garage.swift`, spec NS-29): the wear math is *not* ported — `GET /api/garage` arrives with each part's estimate already computed by `src/lib/wear.ts`, and the client only decides how to say it, with the due/low thresholds and the "≈2 track days" phrasing pinned against the web implementation by `contracts/logic/garage-status.json`. Conventions: ported logic keeps the **same function and constant names** as its JS original so the two diff by eye, and ports its JS test cases with it; `src/` and `public/` must not change for this work. See `apps/ios/README.md`.

**Three clients, and "add it everywhere" is not the default.** The web app (`public/`), iOS (`apps/ios/`) and Android (`apps/android/`) are maintained in parallel against one backend, and the feature split between them is a decision already taken per feature — recorded in `docs/specs/native/README.md`, which is the file to consult (and to update) before adding something to "the app". The shape of it: **web-only** are the desk-bound long tail — `.vbo` and other logger-file import, year in review, compare, the setup notebook and its setup-vs-lap-times diff — plus the PWA install path; **native-only** are the live GPS lap recorder and CarPlay; **iOS-only so far** is video telemetry import (PDR/GoPro parsed on-device, NS-30), which Android has not ported. Everything else — the logbook, the garage, offline reads and writes, charts, sharing, settings — is on all three and should stay that way. A change to shared behavior therefore owes the ports their update: pure logic that exists in more than one language keeps the **same function and constant names** as its JS original so the copies diff by eye, carries its JS test cases with it, and is pinned by a fixture in `contracts/logic/` generated from the web implementation — assert against the reference, never against the other port. Response shapes are pinned the same way one level up by `contracts/golden/`.

The iOS and Android **shells that used to live in `mobile/`** — the web app wrapped in a WebView, with a `www/` sync step, a CarPlay bridge plugin and a CORS allowance in `src/` for its local origins — are gone (NS-27). Nothing in the tree should reference them; if you find something that does, it is stale rather than load-bearing. The platform seam they filled in (`public/js/platform.js`) and the recorder UI behind it were unwound in **#139**: the web app is same-origin/cookie-auth only, and `public/js/record/core.js` + `remote.js` remain solely as the reference implementations the Swift and Kotlin recorder ports are asserted against (`contracts/logic/recorder.json` and `remote-attach.json` are generated from them — see the `js/record/` bullet above). The NS-15…NS-17 specs still cite `js/record/ui.js` as the lifecycle reference; that file is deleted, so read it from git history if a port question ever needs it.

**Database** (`migrations/`, applied in order by wrangler): schema changes are new numbered migration files, never edits to existing ones. `tracks`/`events`/`sessions`/`vehicles` (and the garage tables from `0012_garage_logbook.sql`: `parts`, `part_measurements`, `setups`) carry an `updated_at` (ms) maintained entirely by triggers (`0011_updated_at.sql`, `0012_garage_logbook.sql`) — inserts and updates bump the row, and nested writes bump ancestors (laps → session → event; measurements → part → vehicle; setups → event) — so route code never touches it; it drives the frontend's offline-cache staleness checks.

**Seed** (`seed/generate.mjs`): reads `seed/data.personal.mjs` if present (gitignored — real personal data), else `seed/data.example.mjs`, and writes `seed/seed.sql`. Beyond tracks/events/sessions, the data file can export `VEHICLES` (garage vehicles with consumable parts + wear measurements), `SETUPS` (per-event-day setup sheets, referencing parts by key) and `DEFAULT_CAR` (applied to events without their own car) — all optional, so older personal data files still generate.

**CI / release workflows** (`.github/workflows/`): `ci.yml` (web + backend, `paths-ignore` so a new top-level directory still runs it), `ios.yml` and `android.yml` (the native clients, path-filtered), `pages.yml` (the docs site), and `android-release.yml` — **Play Store test track**, the only workflow that ships anything to a store. It is `workflow_dispatch` only (a version code is burned on upload even if the release is discarded), offers `internal`/`alpha`/`beta` and deliberately *not* production, and takes optional `versionCode` / `versionName` overrides plus a dry run. It runs `:app:checkReleaseHasNoCarApp` before anything else — a car declaration back under `src/main` must not reach a review — then the tests, then `:app:bundleRelease`, then verifies the bundle is actually signed before uploading with `r0adkll/upload-google-play`. Release signing is read from `TE_UPLOAD_KEYSTORE*` in the environment by `apps/android/app/build.gradle.kts`, which also honours `TE_VERSION_CODE` / `TE_VERSION_NAME`; with none of them set the release variant builds **unsigned** rather than falling back to the debug key, so only CI (with the real upload key from repository secrets) can produce a shippable artifact. The five secrets are listed in README. Two NS-27 preconditions no build can enforce: Android Auto must be opted out in the Play Console, and the recorder must survive a real track day before the rollout passes 10%. iOS has no counterpart — those builds go through Xcode Cloud.

**Marketing/docs site** (`site/`): see the Documentation section above for the page inventory and the keep-in-sync policy.

**Tests** (`test/`, Vitest with two projects — see `vitest.config.mts`):
- `test/unit/` — pure-function tests running in Node: `src/lib/*` plus the frontend modules (`public/js/format.js`, `chart.js`) and `pdr.js` internals.
- `test/api/` — the whole Worker under `@cloudflare/vitest-pool-workers`: real D1 with migrations applied per test (`setup.ts`), requests via `SELF.fetch`. `helpers.ts` creates users/sessions directly in D1 so multi-user ownership isolation is testable; DEV_MODE bindings live in `vitest.workers.config.mts`.
- New API behavior needs a test here; new pure logic belongs in `src/lib`/`public/js` where it's unit-testable.

## Conventions

- Lap times are integer milliseconds everywhere; the frontend formats/parses `m:ss.fff` via `fmtMs`/`parseTime`.
- API errors are `{ error: string }` with a meaningful status; the frontend surfaces `err.message` from that.
- Frontend and backend share no code — keep API response shapes in sync with the `app.js` consumers by hand.
- Docs (README, `site/`, this file) are updated in the same change as the code they describe — see the Documentation section.
