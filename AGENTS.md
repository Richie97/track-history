# AGENTS.md

Guidance for coding agents (and humans) working in this repository. This is the
canonical instructions file — `CLAUDE.md` just imports it, so edit this file,
not that one.

## What this is

A personal HPDE/track-day logbook on Cloudflare Workers + D1 (SQLite): tracks → events → sessions → laps, with progress charts and Google (plus optional Apple) OAuth sign-in. Multi-user — every domain row is scoped to a `user_id`. The hosted instance users are pointed to is https://trackevolution.app.

## Commands

```sh
npm install
npm run seed:generate       # writes seed/seed.sql from seed data (see below)
npm run db:migrate:local    # applies migrations/ to the local D1 SQLite
npm run db:seed:local       # loads seed/seed.sql locally
npm run dev                 # wrangler dev → http://localhost:8787
npm test                    # vitest: unit tests + API tests against a real D1 (miniflare)
npm run typecheck           # tsc over src/ and test/ (no linter is configured)
```

Local dev needs a gitignored `.dev.vars`:

```
DEV_MODE=1
DEV_USER_EMAIL=you@example.com   # must match the seed data's USER_EMAIL
DEV_USER_NAME=Your Name
GOOGLE_CLIENT_ID=dev
GOOGLE_CLIENT_SECRET=dev
```

`DEV_MODE=1` makes `GET /auth/login` sign in as a fixed local user (no Google OAuth) — navigate there once to get a session cookie. The bypass only answers on local dev hosts (`localhost`, `127.0.0.1`, `[::1]`, and the Android emulator's `10.0.2.2`); on any other hostname login falls through to real OAuth, so a leaked `DEV_MODE=1` fails closed. Still, never set it in production.

Deployment: `npm run deploy` (plus `db:migrate:remote` / `db:seed:remote`). Secrets are set via `npx wrangler secret put`.

Native clients (`apps/`, own build systems, not part of the npm project):

```sh
cd apps/ios/Packages/TrackEvolutionKit && swift test   # iOS pure logic, no simulator
# the iOS screens end to end; needs `npm run dev`, skips without it
xcodebuild test -project apps/ios/TrackEvolution.xcodeproj -scheme TrackEvolution \

cd apps/android && ./gradlew :app:bundleRelease         # the Play Store .aab, R8-minified (unsigned without TE_UPLOAD_KEYSTORE*)

```

## Issues close with the PR that finishes the work

Tracked work has a GitHub issue — the native rewrite has one per `NS-*` spec
under epic #63 (`gh issue list --search "NS-13" --state all`). **Closing it is
part of the change, not a follow-up:** put `Closes #<n>` in the PR body, one line
per issue, so merging does it.

A PR that only *partly* implements a ticket uses `Refs #<n>`, leaves the issue
open, and comments on it with what's outstanding. Never close an issue whose
acceptance criteria aren't all met — a ticket closed early is worse than no
ticket, because the remaining gap stops being visible.

## Architecture

One Worker serves both the API and the static frontend (`wrangler.jsonc`: `public/` is served as SPA assets; `/api/*`, `/auth/*` and `/share/*` hit the Worker first — the last so share pages can carry per-slug OG meta; the `ASSETS` binding is how the Worker reads `index.html` to do it).

**Backend** (`src/`, Hono):
- `index.ts` — composes the routers. Route order matters: `/api/share` (public, no auth) is registered before `/api` so `GET /api/share/:slug` stays unauthenticated while everything else under `/api` passes through `requireSession` (`middleware.ts`).
- `routes/` — one router per resource: `auth.ts` (Google OAuth or the DEV_MODE bypass → `auth_sessions` row → `session` cookie; a first sign-in claims a user row by matching email where that provider's sub column is NULL — which covers pre-seeded rows *and* cross-provider linking, so Google and Apple sign-ins with the same email share one account, and *because* accounts are claimed by email, both callbacks reject id_tokens whose email isn't verified (`isEmailVerified` in `lib/oidc.ts`); plus the native-app flow — `?client=app&code_challenge=…` runs OAuth in the system browser and redirects to `trackevolution://auth` with a single-use code that `POST /auth/exchange` trades for a bearer token, PKCE-verified. Sign in with Apple is feature-flagged by the four `APPLE_*` secrets — `GET /auth/providers` tells the login screen whether to draw the Apple button — and mirrors the Google flow under `/auth/apple/*` with two quirks: the client secret is a self-signed ES256 JWT from `lib/apple.ts`, and Apple's email-scope callback is a *cross-site POST* (`response_mode=form_post`), so its state/PKCE cookies are `SameSite=None` and the callback route is a POST), `me.ts` (the signed-in user and their totals, plus `PUT /me/checklist-template` — the per-user prep list new event checklists start from, `users.checklist_template`, null meaning "use the client's built-in default" — and `PUT /me/leaderboard`, the strictly-opt-in flag behind the per-track leaderboards, `users.leaderboard_opt_in`), `tracks.ts` (tracks + `GET /tracks/:id/setups`, the "setup vs. lap times" rows for a track, + `GET /tracks/:id/leaderboard` — opted-in users' best **device-timed** laps at the same catalog track, matched via `tracks.catalog_id`, exposing only name/best/date and never anything user-entered; it filters on `laps.device_timed` and deliberately ignores the manual `events.best_time_ms` and hand-entered laps, unlike every logbook stat — NS-33, `docs/specs/native/NS-33-leaderboard-device-timed-laps.md`), `events.ts` (events; per-event-day setup sheets — `PUT`/`DELETE /events/:id/setups/:day` upserting JSON validated by `sanitizeSetup`, plus `GET /events/:id/setups/prefill` for the copy-forward form prefill; `events.car` stays free text but is auto-matched to a garage vehicle by name into `events.vehicle_id` on create/update, and `events.track_hours` optionally overrides the on-track-hours estimate), `sessions.ts` (sessions + laps), `vehicles.ts` (the per-user garage backing Settings → Vehicles — at most one `is_default` row per user pre-fills new events — plus the garage logbook: `GET /garage` returns every vehicle with accrued hours and its parts, each carrying measurements and a computed `wear` estimate; parts CRUD under `/vehicles/:id/parts` + `/parts/:id`, one-tap replacement via `POST /parts/:id/refresh` — retires the part as of the swap date and inserts a same-spec successor — wear measurements under `/parts/:id/measurements`; a new part with no expected life defaults it from retired lifecycles of the same kind), `share.ts` (authed slug management, the public share endpoint — which returns stats/times but strips notes, email, per-lap data, and all garage/setup linkage — plus `sharePage`, the HTML route behind `GET /share/:slug`: it serves `index.html` through the `ASSETS` binding with per-slug OG title/description injected, because link scrapers never run JS; only already-public share data goes into the tags), `wellKnown.ts` (`/.well-known/apple-app-site-association` for iOS Universal Links; the Android `assetlinks.json` is a static file in `public/.well-known/`), and the two **billing** routers (NS-32, `docs/specs/native/NS-32-subscriptions.md` — the deliberate exception to the rewrite programme's "`src/` must not change" rule): `billing.ts` (authed, under `/api`: `POST /billing/apple` verifies a StoreKit 2 transaction JWS *locally* against the pinned Apple Root CA G3 — `lib/billing/jws.ts` + `apple-roots.ts` — and upserts a `subscriptions` row by `originalTransactionId`; `POST /billing/google` reads the purchase token from the Play Developer API with the `GOOGLE_PLAY_SERVICE_ACCOUNT` key and upserts by token, retiring a `linkedPurchaseToken`'s row; `POST /billing/apple/legacy` writes a permanent `legacy` row from a verified `AppTransaction`; `POST /billing/google/legacy` does the same for the Android transitional build — `X-TE-Client: android/<versionCode>` required — until `LEGACY_CUTOFF`, unset meaning open; every one answers `{ ok, entitlement }`, and a purchase already bound to another user is a 409, never a transfer) and `billingWebhooks.ts` (public, *outside* `/api`, in `run_worker_first`: `POST /billing/apple/notifications` for App Store Server Notifications V2 and `POST /billing/google/rtdn` for Pub/Sub push RTDN — both verify the sender (Apple's signature; Google's OIDC bearer against its JWKS with `aud` = the route URL and `email` = the service account) *before* touching D1, and both re-derive the row's state from the store's own payload or a fresh API read rather than from the notification type). `src/cron.ts` (`triggers.crons` in `wrangler.jsonc`, the Worker's `scheduled` handler) re-verifies every store-backed row expiring within 48 h or expired within 7 days once a day.
- `middleware.ts` `requireSession` accepts the session as the `session` cookie (web) **or** an `Authorization: Bearer` header (native apps) — same `auth_sessions` rows. The lookup (`sessionUser` in `lib/session.ts`) joins `users` and sets `entitledUntil` on the context alongside `userId` in the **same single statement**, so `requireEntitlement` — the Pro gate, `402 { error: "pro required" }` — is a pure comparison against `Date.now()` and issues no D1 statement. **It guards `GET /garage`, the parts/measurements routes and the setups routes, and nothing else** — `test/api/entitlement-gates.test.ts` enumerates that set by *handler identity* over the routers' `.routes`, so a gate added to a fourth router fails there even if no test happens to call it — and **no write route ever checks entitlement**: `POST`/`PUT`/`DELETE` on events, sessions, laps and tracks stay open to every signed-in account forever, because the offline layer drops rejected writes and a recording is the one irreplaceable thing in the system — `test/api/billing.test.ts` asserts a lapsed user's session save *with `channels`* is a 201. There is deliberately **no CORS**: the web app is same-origin and the native clients are HTTP clients that send no `Origin`, so nothing needs it (`lib/cors.ts` existed only for the retired web-view shells' local origins and was deleted with them — `test/api/native-auth.test.ts` now asserts that no origin gets a CORS header).
- `db.ts` — data-access helpers. All take `(db, userId, ...)` explicitly so ownership scoping is visible at call sites: `ownedEvent`/`ownedSession` guard nested writes, `resolveTrack` find-or-creates tracks by name (`COLLATE NOCASE`; the name carries the layout — "Virginia International Raceway (Full)" vs "(Patriot)" — so bests/goals never mix across layouts), and `eventSelect`/`listEvents`/`tracksSummary` produce event rows with lap aggregates (a single-pass LEFT JOIN + GROUP BY, not per-row subqueries). D1 pays a network round trip per statement, so helpers backing a single endpoint also expose prepared *statements* (`…Stmt`) that routes combine with `db.batch()` into one round trip, and ownership checks on simple writes are folded into the write itself (`WHERE … user_id = ?`, or `INSERT … SELECT` from an ownership-scoped query, with zero changed rows meaning 404) rather than issued as a separate `SELECT` first. Tracks stay per-user, but each row carries a nullable `catalog_id` into the seeded `track_catalog` table — a canonical identity matched by name (NOCASE) via `catalogIdForName` on create and rename, so the same physical track is recognizable across users without sharing user-entered data. The catalog also backs the track-name suggestions in the event form (`GET /api/catalog`); adding a track to it means a new migration.
- `lib/` — pure logic, unit-tested: `stats.ts` (`withComputed` derives `best_ms = MIN(manual best_time_ms, best logged lap)`, `consistency` — coefficient of variation, only with 3+ laps — and `hours` via `eventHours`), `wear.ts` (the garage's math: `eventHours` — override, else `max(days × 2h, logged lap time)`; `wearEstimate` — accrued hours/heat cycles per part plus remaining-life projection, least-squares from 2+ measurements else expected-hours prior), `validate.ts` (slug/goal/lap validation, `sanitizeSetup` for setup sheets, `sanitizeChecklist`/`sanitizeChecklistTemplate` — the second takes plain strings, since a template carries no done flags, and treats an empty list as "cleared" so deleting every item leaves the built-in default rather than nothing, part kind/date validation), `session.ts` (session token + cookie plumbing; session tokens and one-time auth codes are stored SHA-256-hashed — `sha256Hex` — so the DB never holds usable credentials), `oidc.ts` (id_token decode + `isEmailVerified`), `apple.ts` (Sign in with Apple: the ES256 client-secret JWT — built on `signES256`, which the App Store Server API token reuses — and the first-auth `user` name field), `entitlement.ts` (the tier rule: `LEGACY_ENTITLED_UNTIL_MS`, the 3-day `ENTITLEMENT_SLACK_MS`, `entitledUntilContribution` — the readable statement of the rule migration 0017's triggers implement in SQL, keep the two in step — `entitlementResponse` for `GET /api/me`, whose source ranking puts an entitling *store* row above a legacy one so a grandfathered user who is also being charged still gets a "Manage" target, `stripProFields`, which nulls `channels` and keeps `trace` on a session for a free account and is wired to the event detail — the only response that carries `channels` — so a lapse hides the field and never deletes it, and `legacyClaimOpen`), and `billing/` (`jws.ts` — dependency-free x5c JWS verification: DER/X.509 parsing, chain to a pinned root, Apple's WWDR and receipt-signing extension OIDs, leaf validity at `signedDate`, ES256 under WebCrypto; `apple-roots.ts` — Apple Root CA G3, base64 DER; `apple.ts` — transaction/renewal/AppTransaction verification, `appleSubscriptionState`, the Server API token and `fetchAppleSubscription`; `google.ts` — service-account access token, `fetchGoogleSubscription`, `googleSubscriptionState`, `verifyGoogleOidcToken`; `store.ts` — the D1 statements; `sync.ts` — `syncAppleRow`/`reverifyAppleRow`/`syncGoogleRow`, the "bring one row up to date with its store" sequence the notification webhooks and the cron share, so the retire-the-superseded-token follow-up cannot be remembered in one and forgotten in the other). Normalised row statuses are `active | grace | legacy` (entitling) and `billing_retry | expired | revoked | paused | pending` (not); a `grace` row's `expires_at` is the grace period's end.

**Frontend** (`public/`, dependency-free vanilla JS as native ES modules — no build step):
- `app.js` — the module entry (`<script type="module">`): app state, `shell()`, the views and the hash router (`#/`, `#/new`, `#/event/:id`, `#/event/:id/edit`, `#/track/:id`, `#/track/:id/compare` — the two-event lap overlay — `#/track/:id/lap-compare` — the cross-event two-lap telemetry compare (#165): picker, head-to-head table, delta + channel charts over an `alignLapPair` pair — `#/vehicle/:id` — the garage page: consumables with wear bars/projections, measurement logging, the add-part form and the track-hours ledger — `#/settings` — vehicle garage management plus the privacy/terms links, reached from the account dropdown — plus public `/share/<slug>` pages with their own hash routes). The event page carries the per-day setup notebook (copy-forward prefill, changed-value highlighting), the track page a "Setup vs. lap times" diff table, and the dashboard a maintenance-due strip + garage cards fed by `GET /api/garage`. Two layout rules the three clients share, and which a change to any one of them owes the other two: **the dashboard lists upcoming events, tracks and the garage — and no recent-events table**, because the Tracks grid already orders by recency and the table was the same logbook said twice (the one thing it used to be load-bearing for is written up under *Offline support* in README); and **every way of getting laps into an event is one "Add a session" card** at the bottom of the event page — import, hand entry, and on the native clients the recorder — rather than a stack of separate panels, with hand entry collapsed behind a button since it is the fallback of the three. Each route re-renders the whole view via `shell()`, so element handles go stale after any navigation; module-level listeners are used where per-render listeners would accumulate. HTML is built with template strings — always pipe user data through `esc()`.
- `js/` — extracted modules, importable by unit tests: `checklist.js` (`DEFAULT_CHECKLIST`, the prep list a new event's checklist starts from — its own module so `contracts/logic/checklist.json` can import it and pin the iOS port `EventDates.DEFAULT_CHECKLIST` to it; a user who edits the list in Settings gets their own, served by `GET /api/me`), `entitlement.js` (the tier predicates — `isPro`, `canRecord`, `canViewChannels`, `canUseGarage`, `canUseSetups`, `canViewYearInReview`, `canCompareEvents` — plus `manageUrl` and `entitlementSummary`, over the `entitlement` object from `GET /api/me`; they read the tier and never the clock, so the cached answer stands offline; pinned by `contracts/logic/entitlement.json`, which both ports assert against. **A new Pro decision gets a predicate here first**, then the port, then the fixture — including one no port uses, `canCompareEvents`, so the names stay diffable by eye. The converse holds too: a feature that stops being a decision loses its predicate rather than keeping one that always answers true, which is why there is no `canImport` — **telemetry import is free on every client**, and the tier line for it falls entirely on `channels`, which the server strips. `app.js` reads them through `state.entitlement`, filled by `ensureMe()`, and every gated web surface renders `proPanelHtml` instead of its content: the web has no purchase surface by design, so that panel points at the phone apps rather than offering a checkout), `format.js` (`fmtMs`/`parseTime`/`esc`…), `garage.js` (the garage/setup helpers: the setup-sheet field spec — mirrors `sanitizeSetup` in `src/lib/validate.ts`, keep in sync — `flattenSetup`/`diffSetups` for the correlation views, and part-kind/wear-status/remaining-life formatting), `chart.js` (hand-rolled SVG `lineChart` + `multiLineChart` lap overlay; lower lap time plotted lower = improvement trends downward), `channel-graphs.js` (an imported session's lap list as chips plus per-lap speed/throttle/brake/steering/RPM/lateral-G overlay charts — whichever channels the session stored — in a collapsible `<details>`, on a shared driven-distance axis; up to 3 laps highlighted via the chips in the `--chart-line`/`-b`/`-c` slot colors, the rest a dim envelope; with 2+ laps highlighted a lap **delta chart** renders above the channels — `lapTimeSeries`/`deltaSeries` integrate elapsed time from the stored speed samples, scaled to the timed lap, pinned for ports by `contracts/logic/lap-delta.json`; the panel is **one question per tab** — `TABS` Time / Inputs / Grip / Car, `TAB_OF` mapping each channel to its tab, only populated tabs rendered and a single one rendered flat — because the epic #193 rule is that the analysis area takes tabs, never another stacked section; two hooks let app.js hang more analysis on the panel without the panel knowing about it — `renderExtras` for markup above a tab's charts (a string lands on Time, an object places per tab) and `renderAfter` for a chart slotted under a named channel's chart), `compare-laps.js` (the pure half of the two-lap compare — `comparableLaps`/`defaultComparePicks`/`resampleChannelLap`/`alignLapPair`/`lengthMismatchRatio`/`lapMetrics`; ported to the iOS Kit and Android `:core` as `CompareLaps`, pinned by `contracts/logic/compare-laps.json`), `sectors.js` (sector splits + theoretical best, #146 — `sectorTimes` cuts a stored channel lap into `SECTOR_COUNT` equal slices of *its own* driven distance off `lapTimeSeries`, rounding so the splits sum exactly to the lap time, and `sessionSectors` reduces a session (or an `alignLapPair` pair) to best-per-sector, theoretical best and the gap to the actual best; ported as `Sectors` to the Kit and `:core`, pinned by `contracts/logic/sectors.json`; `sectorTableHtml` is the web-only table that `bindChannelGraphs` slots above the charts via its `renderExtras` hook and the compare view renders under its head-to-head — the theoretical best also joins the session stats line on every client), `gears.js` (gear ribbon + shift points, #187, the first of epic #193's channel visualizations — `gearSegments` cuts a stored `gear` series into runs, `lapShifts` reads the rpm at the last sample in the old gear and skips a clutch-in blip between two gears, `shiftPoints` reduces a session's upshifts to min/median/max rpm per gear, `shiftNotes` turns that into factual sentences (report, don't scold), `gearDisagreements` finds the runs ≥ `MIN_DISAGREE_POINTS` where highlighted laps sit in different gears; pinned by `contracts/logic/gears.json` for the ports, which don't exist yet — web only so far; `gearRibbonSvg` is the web ribbon `bindChannelGraphs` slots under the RPM chart via its `renderAfter` hook, one stepped band per highlighted lap with gear 0 as a gap and disagreements outlined, and `shiftTableHtml` the per-gear table rendered after the sector table via `renderExtras`; the compare view draws the ribbon too when both laps stored `gear` — `resampleChannelLap` doesn't carry `gear`, so it drops out when the two sessions' grids differ), `limits.js` (where the car is at its limit, #188 — `wheelSlip` beyond ±`WHEELSPIN_PCT`/`LOCKUP_PCT` and the `flags` bits `FLAG_ABS`/`FLAG_TC`/`FLAG_VSC` reduced to `limitRuns` per lap, merged across `MERGE_GAP_POINTS` clear points so an ABS pulse train is one braking zone, `sessionLimits`/`limitSummary` counting *places* on track across laps ("ABS in 3 places" / "no interventions"), `activeLimitLabels` for the tooltip suffix, and `limitMarkers` placing a lap's runs on the stored best-lap trace by driven-distance fraction — the trace is the best lap only, so only the best lap's entry is ever placed on it; `LIMIT_KINDS` fixes colour by *side* (`--limit-brake` for ABS/lockup, `--limit-power` for TC/wheelspin, stability in text-strong) with shape + fill as the second encoding; pinned by `contracts/logic/limits.json`, web only so far; the web half is `limitGlyphSvg` for legends — `channelChartSvg` shades the bands itself and `renderTrackMap` takes `{ markers }`), `lap-stats.js` (per-session analysis: best-N avg, pace slope, warmup), `year-review.js` (year-in-review aggregation), `api.js` (fetch wrapper throwing `ApiError` with status — same-origin requests with cookie auth; routes everything through the offline layer below), `theme.js`, `pull-refresh.js` (touch pull-to-refresh: dampened pull past a threshold re-runs the current route's fetches, with the brand chevron sweeping left→right in a pill while refreshing; `initPullRefresh` is wired at the bottom of `app.js`).
- `js/offline.js` + `js/prefetch.js` — the offline-first layer (also the reference the native apps' offline stores are ported from — NS-21/NS-22). `offline.js` keeps an IndexedDB cache of GET `/api` responses (in-memory backend in Node, so it's unit-testable) plus a persistent queue of writes made offline: `api.js` GETs are network-first with cache fallback, and queueable mutations (events/sessions/laps/setup-sheet/track edits — the whitelist is `QUEUEABLE`; vehicle and garage-part writes need a live server and fail offline normally) are stored, patched into the affected cached responses so the UI shows them immediately, and replayed in order on reconnect, with temp ids (`tmp-N`) mapped to real ids; `app.js` then remaps any `#/event/tmp-N` hash. Deleting a not-yet-synced row just cancels its queued items. Conflict policy is last-write-wins; server-rejected writes are dropped and surfaced in the shell's `#sync-banner` (updated in place by `updateSyncBanner`). `offline.js` deliberately mirrors two backend behaviors — `recomputeDetail` ↔ `withComputed` in `src/lib/stats.ts` (including the `hours` rule from `src/lib/wear.ts`), `cleanLaps` ↔ `sanitizeLaps` in `src/lib/validate.ts` — keep them in sync. `prefetch.js` warms the cache after a dashboard load: every event detail is prefetched, re-fetching only rows whose `updated_at` (new in migration 0011, trigger-maintained) differs from the cached copy. Signing out clears cache + queue.
- `js/record/` — **reference implementations, not app code**: the live lap recorder is native-only (NS-15…NS-18) and nothing under `public/` imports these modules, but they are the JS originals both native recorder ports are asserted against, so they are kept, unit-tested (`test/unit/record.test.js`, `record-remote.test.js`) and pinned by fixtures `contracts/logic.mjs` generates *from them* — deleting or changing them changes both ports' contract. `core.js` is the recorder's pure logic — fix validation/buffering, forgot-to-stop auto-stop (arms only after the car has been driven at track pace, so grid waits don't kill a recording), idle trimming, checkpoint (de)serialization (pinned by `contracts/logic/recorder.json`), and `toParsed()`, which emits the same `{kind: "live", gps, needsLine, laps: []}` shape as a file parser so a recording drops into the review/line-picker flow. `remote.js` is the remote-start attachment rule (`pickRecordingEvent`: attach to the event whose `start_date`+`days` cover today — never guesses further — else record with `eventId: null`, since recording is on-device and must not depend on the network or session), pinned by `contracts/logic/remote-attach.json`. `live-timing.js` is the on-track lap counter and predictive delta shown on the native record screens — the recorder has no start/finish line during a session, so it anchors its own gate at the first track-pace fix (the pit exit, on the racing line) and times crossings of it, comparing the running lap against the session's best by distance; ported as `LiveTiming` to the Kit and `:core`, pinned per-fix by `contracts/logic/live-timing.json`. The web recording UI that used to sit on top (`ui.js`, the `#/event/:id/record` route, the event page's record panel, the dashboard's unsaved-recording banner) was unreachable in a browser once the web-view shells were retired and was removed in #139.
- `js/import/` — the telemetry import feature: `channels.js` builds the per-lap channel data stored with imported sessions (`sessions.channels` JSON; the shape is validated server-side by `sanitizeChannels` in `src/lib/validate.ts` — keep the two in sync). **Sample rate picks the storage shape**, and a PDR file's 66 channels make the split obvious: anything ≥ ~5 Hz is a *gridded trace* resampled onto a 20 m driven-distance grid (`CHANNEL_NAMES`: speed, rpm, latG, throttle, brake, steering, longG, yaw, gear, wheelSlip, boost, flags), anything slower produces one real sample every 40–90 m and so becomes a *per-lap scalar* instead (`SCALAR_NAMES`: oil/coolant/trans temps, oil pressure, fuel, battery, tyre pressures ×4 and temps ×4, each with its own `max`/`min`/`end` reduction), and four numbers describing the whole recording become the blob's `meta` (`META_NAMES`: ambientC, intakeC, elevationM, odometerKm — the last is the *car's lifetime odometer*, not the session's distance). Three rules there are load-bearing. `CHANNEL_NAMES` order is both render order *and* priority: the six original channels keep their positions so existing graphs are unchanged, and `trimToBudget` drops from the **tail** until a session fits `MAX_TOTAL_VALUES` rather than returning null and losing every graph — which at 12 channels is now reachable (~38 VIR laps, where 6 channels never got close). And two channels are states, not measurements, so they get their own samplers: `STEP_HOLD` (`gear` — interpolating 3 and 4 yields 3.5) and `WINDOW_MAX` (`flags` — a half-second ABS event is narrower than 20 m and a point sample misses it). Nothing renders the added channels yet; they are captured because the video never leaves the device, so a reading not derived at import is gone; `parse.js` dispatches a dropped file to a parser (`.vbo` → `vbo.js`, `.mp4` → PDR first, then GoPro `gpmf.js`); every parser returns `{kind, date, time, durationS, laps, gps, needsLine}`. `geo.js` projects GPS traces to local meters and derives laps from start/finish line crossings; `pdr-laps.js` recovers laps for beacon-less PDR recordings from latitude+odometer periodicity (autocorrelation lap length; start/finish phase anchored to a beacon-timed batch-mate via `anchorPdrBatch`); `ui.js` is the dropzone/review flow, including the click-a-map line picker for GPS sources without lap markers — GoPro, plain VBO (one picked line applies to the whole batch, with automatic longitude-sign mirroring for Racelogic's west-positive convention). Test fixtures for all formats are generated by `test/fixtures/build.mjs`. Real sample recordings for manual import testing live in the gitignored `telemetry-samples/` at the repo root — never commit footage.
- `pdr.js` — parses lap times, the GPS trace, and car metrics (top speed / max RPM / max lateral G) out of Corvette PDR (Cosworth) MP4 telemetry entirely in the browser via byte-range reads; the video is never uploaded. The beacon/odometer lap-derivation logic is reverse-engineered — see README before touching it. The stream is **delta-encoded** (framing matches ExifTool's GM.pm): each channel gets one full record, then 8-byte diffs against running decoder state that persists across samples — decoding the deltas is what yields ~11Hz lat/lon (radians, scaled via the `mrld` channel dictionary) and the car channels (steering is radians with an empty units string in real firmware — pdr.js converts to degrees itself). Which of the file's 66 channels are read is the `CHANNEL_TAGS` table, which also records what is deliberately *not* read (recorder CPU/disk housekeeping, session constants, redundant or derivable channels, and the suspension/clutch channels whose scaling needs a second car to validate). Three of the units in `UNIT_CONV` are the ones that bite: the dictionary names a **display** unit while storing SI, so `°C` channels hold **Kelvin** — which is why the table is `[factor, offset]` and not just a factor; ship a temperature without the offset and 130 °C oil reads as 403 °C — `kPa` channels hold **Pascals**, and `km` channels hold **metres**. The recording odometer is deliberately *not* run through `UNIT_CONV`: `odoPts` stays raw because it is the driven-distance axis for `channels.js`, not a displayed value. `gear` is an enum, not a measurement (1–8 are gears; 13 is the clutch-in state, mapped to 0 — never plot it as a thirteenth gear), `wheelSlip` is derived from the four wheelspeeds as one channel rather than four, and ABS/traction/stability are packed into one `flags` bitfield. Coordinates only become a `gps` trace behind plausibility checks; when they don't decode, the raw latitude/odometer series returned as `channels` still feed lap recovery in `js/import/pdr-laps.js`.
- PWA: `manifest.webmanifest` + `sw.js` make the app installable and offline-capable (the service worker covers the app shell and last-known responses; structured offline reads/writes live in `js/offline.js` above). The service worker serves static files stale-while-revalidate (no build step, so no cache busting — changes land on the *second* load), navigations and `GET /api/*` network-first with cache fallback; `/auth/*` and non-GET are never intercepted. Signing out deletes the cached API data (`th-data-*` caches) so a shared device doesn't retain the previous user's logbook. Icons in `icons/` + `favicon.*` are generated from the brand mark — regenerate rather than hand-edit if the mark changes.

**Native clients** (`apps/`, the shipped iOS and Android apps — one spec per `NS-*` id in `docs/specs/native/`, which also records the fixed decisions and the deliberate web/native feature split): `apps/ios/` is a SwiftUI-lifecycle app (`App/`) plus a local SPM package `Packages/TrackEvolutionKit/` holding all pure logic — models, API client, recorder core, lap geometry, offline store — which **must never import UIKit or SwiftUI**; it builds for macOS as well as iOS, which is what lets `swift test` run the suite in seconds with no simulator. `TrackEvolution.xcodeproj` is generated from `project.yml` by XcodeGen *and committed* (a clean checkout, and CI, needs only Xcode), so project settings are changed in `project.yml` followed by `apps/ios/generate.sh` — never in Xcode's inspector, where the edit would be lost on the next generate; shared schemes XcodeGen can't express (the package's test scheme) live in `apps/ios/Schemes/` and are copied in by that script. Load-bearing: bundle id `app.trackevolution` (kept from the retired shell so the native build shipped as an in-place App Store update, preserving ratings and the Universal Links association — Xcode Cloud archives *this* project, and `MARKETING_VERSION` in `project.yml` is the shipping one), deployment target iOS 17, Swift 6 language mode with complete concurrency checking, and `com.apple.developer.carplay-driving-task` **is** checked in (Apple has granted it) — dropping the key fails no build and no test, it just makes the CarPlay scene stop attaching, so CI asserts its presence and lints every entitlements file. CarPlay itself is `App/CarPlay/`: a single-template `CPTemplateApplicationScene` driving the *same* recorder the phone UI does, reachable from UIKit via `AppServices`, with the event-attachment rule ported into the Kit's `RemoteRecording` and pinned against the web implementation by `contracts/logic/remote-attach.json`. `apps/android/` is a Gradle project split the same way: `:core` is pure Kotlin/JVM (no Android dependency, enforced by a `checkNoAndroidDependency` task that fails the build if one appears) and `:app` is the Compose shell — `applicationId`/`namespace` `app.trackevolution`, kept from the retired shell for the same in-place-update reason as iOS, `minSdk` 26, Java 17 bytecode while `:core` stays on 21. Every plugin version is declared once in the root `build.gradle.kts` with `apply false` (the Kotlin JVM and Kotlin Android plugins are the same artifact, so a second version declaration makes Gradle refuse to resolve either), and libraries live in `gradle/libs.versions.toml`. Building `:app` needs an SDK (`ANDROID_HOME` or a gitignored `local.properties`), but `:core:test` deliberately does not — AGP defers its SDK check to task execution, which is what keeps CI's core job SDK-free and under a minute; the `app` job installs the SDK and runs `:app:assembleDebug` plus `:app:testDebugUnitTest` (Robolectric, so still no emulator). Manifest permissions (location, background location, foreground service, `POST_NOTIFICATIONS`) are **declared, not requested** — the runtime request belongs to the feature that needs it, so the user is asked in context. The launcher icon is the adaptive icon inherited from the retired shell and the launch theme is `Theme.TrackEvolution.Splash` (androidx core-splashscreen, brand near-black `#0A0A0B`), swapped for the real theme by `installSplashScreen()`; the *window* theme underneath Compose follows the system's light/dark through `values-night/`, since it is drawn before Compose can consult the in-app override. `:core` carries the ported logic (`RecorderCore`, `GeoTrace`, `LapTime` — the port of `public/js/format.js`) plus `model/` and `api/`: `@Serializable` data classes with explicit `@SerialName` on every field (never a global snake_case strategy — a mismatch has to be visible at the field), and `ApiClient`, a Ktor client whose **engine is injected** so `:app` supplies OkHttp while tests drive the identical code through `MockEngine`. Two decisions there are load-bearing: responses decode with `ignoreUnknownKeys = false`, so a field the server adds and no model covers fails a test instead of vanishing, and `GoldenContractTest` decodes *and re-encodes* every entry in `contracts/golden/manifest.json`, which is what also catches a field the model has and the server doesn't. Failures map to a sealed `ApiException` carrying the server's own `{ error }` string — `Unauthorized` is its own case so re-auth is a type check, and `Transport` (no answer at all) is deliberately distinct from a status, because only one of the two is worth retrying. Epoch-millisecond columns are `Long`; Kotlin's `Int` is 32 bits, which is why NS-04 can spell `updated_at` as Swift's 64-bit `Int` and this cannot. Update requests use a three-state `Patch` (`Unchanged` omits the key, `Set(null)` sends an explicit null) because the server writes only the columns *present* in the body. `contracts/golden/` (regenerate with `npm run contracts:generate`, verify with `contracts:check`) pins every API response as JSON so both clients' decoders are tested against the real thing; `contracts/logic/` (`contracts:logic`) does the same one level down for *ported pure logic* — it runs the web implementation and commits its output, so the ports assert equality with the reference rather than with each other (the iOS lap-geometry port matches `public/js/import/geo.js` lap times to the millisecond). Design system: `public/style.css` stays the source of truth, and the iOS color tokens are *generated* from it by `apps/ios/Tools/generate-tokens.mjs` into an asset catalog (Any = the stylesheet's light values, Dark = its dark defaults) plus a token list for the debug-only gallery (`-tokenGallery` launch argument) — so use `Color(.bgPage)`, never a hex literal, and re-run the generator rather than editing either output. On iOS Geist isn't bundled (no font binaries in the repo), so `App/DesignSystem/Typography.swift` falls back to SF Pro/SF Mono behind a documented seam. Android has the same arrangement one directory over: `apps/android/tools/generate-tokens.mjs` reads the same two stylesheet blocks and writes `app/src/main/kotlin/app/trackevolution/ui/theme/ColorTokens.generated.kt` (a `TrackColors` data class plus the light and dark instances and a catalog for the gallery), consumed through `TrackTheme.colors` — with `TrackTypography`, `TrackRadii` and `TrackMotion` beside it and a Material `ColorScheme` derived from the tokens only so unwrapped Material components aren't the wrong color. **Dynamic color (Material You) is off on purpose** — the accent is the charts' "faster" signal — and `surfaceTint` is transparent so Material's tonal-elevation wash can't reintroduce depth the design system draws as a hairline plus one surface step (`TrackCard`). Geist and Geist Mono *are* bundled there, as single variable fonts pinned per weight with `FontVariation` (SIL OFL 1.1; the license ships in `assets/licenses/`), sizes in `sp` and tracking in `em` so both scale with the system font setting. The theme override (system/light/dark, mirroring `public/js/theme.js`) persists in DataStore via `ThemePreference`. The gallery is `TokenGalleryActivity` in the **`debug` source set** with its own manifest and launcher entry — not compiled into a release build at all, rather than merely unreachable. **Android sign-in** (NS-09) splits the same way: `:core` owns the pure half — `Pkce` (base64url-unpadded `S256`, using `java.util.Base64` rather than `android.util.Base64`, whose default flags append a newline and fail verification), the `/auth` client methods, and `DeepLink`, the routing-table port that is unit-tested rather than tapped through and which deliberately refuses `trackevolution://auth?code=…` so navigation can never race the sign-in flow for a code that is burned on first use. `:app` owns everything Android: a **Chrome Custom Tab** (never a WebView — Google blocks OAuth in embedded web views, and `CustomTabs.open` must be handed an *Activity*, since launching from the application context throws and `FLAG_ACTIVITY_NEW_TASK` would put the tab in the wrong task), and `AuthStore`, an `EncryptedSharedPreferences` file holding the token *and* the in-flight PKCE verifier — the verifier because the flow leaves the process when the browser opens, and both readable while the device is locked because the lap recorder runs locked and has to sync. `AuthController.handleRedirect` ignores a code with no pending flow behind it, which is what stops a redelivered intent after a recreate from burning a good session. The provider buttons come from `GET /auth/providers` and are cached **per server** (`AuthProvidersStore`), so a failed fetch is a no-op rather than a silent downgrade to Google-only, and pointing a debug build at `wrangler dev` and back never carries one deployment's answer to the other. The dev-server override and its cleartext exception (`10.0.2.2`, the emulator's alias for the host, where the server's `DEV_MODE` bypass answers) are gated to debug builds — the network-security config lives in the `debug` source set so no release build can ship one. **Android billing** (NS-32 phase C) is `app/.../billing/`, in `:app` only — `:core` carries the `Entitlement` model with the tier predicates (`isPro`, `canRecord`, `canViewChannels`, `canUseGarage`, `canUseSetups`, `canViewYearInReview`, `manageUrl`, `entitlementSummary` — the port of `public/js/entitlement.js` under the same names, pinned to `contracts/logic/entitlement.json`, the fixture the iOS Kit asserts against too), the `/billing` client methods (`postGooglePurchase`, `claimGoogleLegacy`) and a 402 `ApiException.PaymentRequired` case beside `Unauthorized`, and `checkNoAndroidDependency` keeps the store SDK out of it. `BillingController` is process-wide on `AppServices` (started from `TrackEvolutionApp.onCreate`) because two of its jobs belong to no screen: **`queryPurchasesAsync` runs on every cold start**, re-posting anything the server doesn't yet know about and anything still unacknowledged, and a purchase Play reports **with no signed-in user is held until sign-in, not dropped** (`onSignedIn`, which `MainActivity` drives off the auth state). The one rule there that costs money is **acknowledge only after `POST /api/billing/google` returns 200** — Play refunds an unacknowledged subscription after three days, acknowledging first is how a paying user ends up free when the post fails, and a 409 (the token is another account's) is never acknowledged from this one; that decision is pure in `PurchaseSync` and plain-JUnit tested, as are `LegacyClaim` (done on 2xx/403/409, retry on anything else), `PaywallPlans` (ISO period → words, an introductory-trial offer preferred over the bare base plan, the yearly savings badge) and `Backoff` (the `SERVICE_DISCONNECTED` reconnect schedule, doubling from 1 s to a 60 s cap). `ApiClient` takes `defaultHeaders`, which is how `AppServices` puts **`X-TE-Client: android/<versionCode>`** on every request without `:core` seeing `BuildConfig`, and the **once-per-install legacy claim** (`POST /api/billing/google/legacy`; the flag lives in `BillingPrefs` on the shared DataStore and survives sign-out on purpose) runs each time the app becomes signed in — from launch, never from the code exchange, since thirty-day sessions never re-exchange. Every billing answer's `entitlement` lands on `AuthState.SignedIn` through `AuthController.setEntitlement`, so the gates, Settings' *Subscription* card (`entitlementSummary`/`manageUrl` — Subscribe when free, Manage when a store sold it, nothing for a legacy grant, which has no subscription behind it) and `PaywallSheet` (price and billing period from Play's own `ProductDetails`, both legal links, Restore) read one value rather than copies. **The gates are on since phase D**: `Entitlement.GATES_ENABLED = true`, with `recordGate` — the only one, since import is free — taking the flag as a parameter so `EntitlementTest` covers both values; the recorder's Start (`AppNavHost`'s `Route.Record`) goes through it — the event page's *Import video…* and the share-sheet import in `SignedInScaffold` do not, since importing is free — and offline the cached `/api/me` entitlement stands — a driver who was Pro at the last sync records. Nothing about tier is persisted client-side beyond that cache. **App Links** are verified against `public/.well-known/assetlinks.json`, which carries the **Play app-signing** SHA-256 — so verification succeeds only for a Play-signed build, never for a locally-signed debug one; check with `adb shell pm get-app-links app.trackevolution`. The file is served by the Worker from `public/`, so changing the signing key means redeploying the Worker, not shipping an app update. **The Android lap recorder** (NS-16) is `app/.../recording/`: a foreground `Service` with `foregroundServiceType="location"` that **owns the recording**, so the UI can be swiped out of recents without stopping it — and which is why the native app needs none of the legacy-bridge workaround the retired shell carried to stop Android halting its WebView's background location after five minutes. `startForeground` is called **before** any permission check or I/O, because the system kills the process if it hasn't happened within five seconds of `startForegroundService`. Deliberately `START_NOT_STICKY`: a service the system restarts with no recording state would post a notification claiming to record while capturing nothing, so restart is handled by recovering the journal instead. Durability is `RecordingJournal` in `:core` (plain `java.io`, so it unit-tests against a real temp file with no emulator) — an append-only JSONL file written **per accepted fix**, whose tuples are byte-identical to `RecorderCore.serializeRecording`'s; a **deviation from NS-16's "use Room"**, taken for the same reasons iOS deviated from NS-15, and documented at the class. It is flushed but not `fsync`ed, which covers a force-stop and a crash but not power loss — an fsync at 10 Hz is not worth the battery. `Location.toFix()` is where Android's "no reading" sentinels die: `hasSpeed()`/`hasAccuracy()` gate the values, because a 0 that means *unknown* is indistinguishable from one that means *stationary* once it is in the trace, and `location.time` (the fix's own) is used rather than the delivery clock so a batched delivery isn't rejected wholesale by `addFix`'s monotonic check. Permission staging is not a choice: Android **rejects** a combined fine + background request, so `RecorderPermissions` reads them separately and `POST_NOTIFICATIONS` is its own ask on API 33+ — without it the foreground notification is silently invisible, which was the second defect the retired shell shipped. The `Recorder` object is the observable seam (state plus the finished/recovered recording) that NS-18's screen and NS-20's Android Auto both read, and `RecorderHarnessActivity` in the `debug` source set is a bench for driving it directly. **Android Auto (NS-20) is built but does not ship**: Play rejected it under `PF-1` because Android has no category permitting a driving-task app (POI is the closest, and a lap timer has no point-of-interest functionality — there is no Android equivalent of the CarPlay entitlement Apple granted). Everything car therefore lives in the `debug` source set — sources, `res/xml/automotive_app_desc.xml`, the `<service>` and both `<meta-data>` blocks in `app/src/debug/AndroidManifest.xml`, and `androidx.car.app` as `debugImplementation` — because the *declarations* are what make an artifact car-compatible to the review pipeline, so merely unregistering it would not be enough. `:app:checkReleaseHasNoCarApp` fails the build if one reappears under `src/main`, since CI only ever builds the debug variant and nothing else would notice until a store review. The Android Auto **form factor must also stay opted out in the Play Console** — a non-compliant car artifact in the production track rejects the entire submission, phone updates included, and no build can guard Console state. **The recording UI** (NS-18) sits on top: `SignedInScaffold` keeps the recording banner *above* the destination so an in-progress or unsaved recording is visible from anywhere, and a `BackHandler` that navigates rather than stops — a recording must not be endable by a gesture. `RecordingFlow` holds the review state above the view tree, so a rotation cannot lose a pick. The picker's geometry is `TraceMap` in `:core` (fit, hit-test, and the y-flip that keeps north up — get it wrong and every circuit draws mirrored), and the pick itself is `LineReview`, which names the two ways a pick legitimately yields nothing — a stationary pick has no direction to build a gate across, a line crossed once has no lap — because each needs different advice and a silent empty list is the dead end the web app's wording exists to prevent. Saving posts `laps` as integer milliseconds plus the best lap's polyline and — since the video importer landed (NS-32) — the per-lap **`channels`** that `TelemetryChannels.buildLapChannels` cuts from the phone's own fixes, the same side effect NS-30 had on iOS; a source that yields none posts `channels: null`, never a half-formed shape, because `sanitizeChannels` rejects one with a 400. The journal is cleared only *after* the server accepts, so a failed save in a paddock costs a retry and never the session. **The Android charts** (NS-24) split the same way again: `:core` carries `ChartScale` (the port of the scale maths in `public/js/chart.js`) and `ChannelGraphs` (the non-drawing half of `channel-graphs.js`, with `matchLapsToChannels` pinned to `contracts/logic/channels.json`), while `app/.../ui/charts/` draws — `ProgressChart`, `TrackMap` and `LapChannelChart`, all hand-rolled on Compose `Canvas` rather than on Vico, since `LinePicker` already established the Canvas idiom and a charting library's axis defaults would have to be fought rather than used. Three things there are load-bearing. **Lower lap times plot lower** — `ChartScale.plottedFraction` returns a fraction measured *from the top*, and a Compose canvas already grows y downward, so it is used as-is; inverting a second time yields a chart that reads exactly backwards, which iOS shipped once. **The reference is the web, not iOS**: iOS's `ChartScale` chose 4% y-padding against `chart.js`'s 12%-with-a-500 ms-floor and returns `1` rather than `0.5` from `speedFraction` for a constant-speed trace, so the Kotlin port follows the JS and records the divergence at the class — NS-24 asks for parity of *meaning*, not of padding. And `ChannelGraphs.valueExtent` is deliberately separate from `valueDomain`: the domain is padded so the trace does not touch the frame, and 8% below a speed of zero is a *negative speed* — fine as an axis bound, nonsense in the screen-reader summary, which is what surfaced it. Every chart carries a `contentDescription` saying which way the trend goes, because down-is-better is precisely the convention a screen-reader user cannot see, and the lap chips carry number and time beside their colour dot so identity is never colour-alone. `ChartGalleryActivity` in the `debug` source set is the bench — all four in both themes, plus the 20,000-fix line picker, since a stored trace is capped at 300 points by `GeoTrace.lapTrace` and only a raw recording reaches that size. **The Android offline layer** (NS-22) is `:core`'s `offline/`, the port of `public/js/offline.js`: `OfflineStore` (response cache, write queue, temp ids, ordered replay), `applyLocal` in `OfflinePatch.kt` (the optimistic patches that keep the dashboard, event page and track page agreeing before a sync), and `OfflineMirrors` — `recomputeDetail`/`cleanLaps`, now the *fourth* copy of two server behaviors, which is why all four are tabulated at the class. Storage sits behind `OfflinePersistence`, whose only entry point is a transaction, so a queued write and the optimistic cache patch that makes it visible commit **together** — the win over IndexedDB that both native clients take; the in-memory implementation is what lets the replay algorithm unit-test on the JVM in milliseconds, and the durable half is `:app`'s `data/`. That half is a single Room database (`OfflineDatabase`; schema exported to `app/schemas/`) behind `RoomOfflinePersistence`, deliberately with **no destructive-migration fallback** — the cache is refetchable, but the queue holds recorded sessions that exist nowhere else until they replay, so a schema change owes this database a real migration rather than a silent wipe on an app update. Replay is `ReplayWorker`, a WorkManager `CoroutineWorker` behind a `CONNECTED` constraint that **only reports success on an empty queue** — anything else is `retry`, which is what stops a write queued *during* a flush from being stranded, since `OfflineStore.flush` snapshots the queue when it starts. `SyncScheduler` enqueues it as unique work with `KEEP` (never `REPLACE`, which would cancel a replay mid-queue) from two triggers: any pending write, and a `ConnectivityManager.NetworkCallback` — a callback rather than a poll, and treated as a hint only, since a captive portal reports connected too. All of it hangs off `AppServices`, the process-wide holder behind the new `TrackEvolutionApp`, and it is a singleton for a load-bearing reason: `OfflineStore` keeps the pending count and the flush lock **in memory**, so a second instance over the same database would let the worker and the UI replay the same queue concurrently and interleave writes. Durability is asserted against real SQLite, not the in-memory fake, by `:app`'s Robolectric suite (`./gradlew :app:testDebugUnitTest`, now a CI step) — the fake proves the logic reloads, which is a different claim from the file surviving. A temp id is a **negative Int**, not `tmp-N`: `Event.id` is an `Int` pinned by the golden contract, real server ids are always positive, and the value never reaches the server — the same call iOS made, so the representation differs while the behavior doesn't. `ApiClient` *is* the offline layer once it is given a store: reads are network-first and fall back to the cache only on a *transport* failure, never on a status (answering a 500 from a stale cache would hide it), a queueable write with nowhere to go becomes a queue entry plus a synthetic `{id}`/`{ok}` response, and a write made while others are pending queues too rather than jumping the line. It fires on every merge to `main` touching the Android client (same path filter as `android.yml`), uploading to the **internal** track, and via `workflow_dispatch`, which offers `internal`/`alpha`/`beta` — deliberately *not* production — plus optional `versionCode` / `versionName` overrides and a dry run. The `versionCode` is derived from the ref's commit count (monotonic on `main`; a version code is burned on upload even if the release is discarded, so automatic uploads must never reuse one), with the dispatch input as the override; the value checked into `build.gradle.kts` is only what local builds get. It runs `:app:checkReleaseHasNoCarApp` before anything else — a car declaration back under `src/main` must not reach a review — then the tests, then `:app:bundleRelease`, then verifies the bundle is actually signed **and minified** — the release build type runs R8 (`isMinifyEnabled` + `isShrinkResources`), because Play scores obfuscation and shrinking per app and an unminified bundle drew a "below 25%, may impact visibility and publishing" notice — before uploading with `r0adkll/upload-google-play`, passing `build/outputs/mapping/release/mapping.txt` so the Console deobfuscates crashes. Play's other per-bundle warning — "contains native code, and you've not uploaded debug symbols" — is not actionable and stays: the only `.so` files are AndroidX's, shipped already stripped, so `ndk.debugSymbolLevel` extracts nothing (don't add it; the release build type says why). An upload failure reading "a change was made to the application outside of this Edit" is a Console session saving concurrently, not a build problem; the edit is discarded and the job can simply be re-run. Keep rules live in `apps/android/app/proguard-rules.pro` and should stay near-empty: everything reached by reflection (Room, WorkManager, kotlinx.serialization's `serializer()` lookups, Tink) is covered by the libraries' own consumer rules, and a blanket `-keep class app.trackevolution.**` would hand back the obfuscation score. Release signing is read from `TE_UPLOAD_KEYSTORE*` in the environment by `apps/android/app/build.gradle.kts`, which also honours `TE_VERSION_CODE` / `TE_VERSION_NAME`; with none of them set the release variant builds **unsigned** rather than falling back to the debug key, so only CI (with the real upload key from repository secrets) can produce a shippable artifact. The five secrets are listed in README. Two NS-27 preconditions no build can enforce: Android Auto must be opted out in the Play Console, and the recorder must survive a real track day before the rollout passes 10%. iOS has no counterpart — those builds go through Xcode Cloud.

**Marketing/docs site** (`site/`): see the Documentation section above for the page inventory and the keep-in-sync policy.

**Tests** (`test/`, Vitest with two projects — see `vitest.config.mts`):
- `test/unit/` — pure-function tests running in Node: `src/lib/*` plus the frontend modules (`public/js/format.js`, `chart.js`) and `pdr.js` internals.
- `test/api/` — the whole Worker under `@cloudflare/vitest-pool-workers`: real D1 with migrations applied per test (`setup.ts`), requests via `SELF.fetch`. `helpers.ts` creates users/sessions directly in D1 so multi-user ownership isolation is testable; DEV_MODE bindings live in `vitest.workers.config.mts`.
- New API behavior needs a test here; new pure logic belongs in `src/lib`/`public/js` where it's unit-testable.
- Billing (`test/api/billing.test.ts`, `test/unit/billing-jws.test.ts`, `test/unit/entitlement.test.ts`) signs Apple-shaped payloads with the synthetic chain in `test/fixtures/billing/` (root → WWDR-marked intermediate → receipt-signing leaf, plus a wrong-root chain and an OID-less leaf; regenerate with `build.sh`, keys are PKCS#8). The Worker trusts that root only under `DEV_MODE` via `APPLE_IAP_TEST_ROOT_PEM`. The App Store Server API, Play Developer API, Google token endpoint and Google JWKS are `fetchMock` interceptors in `vitest.workers.config.mts`, driven by the id/token in the request path (contracts in `test/billing-helpers.ts`); workerd has no filesystem, so the PEMs reach the API tests as bindings.

## Conventions

- Lap times are integer milliseconds everywhere; the frontend formats/parses `m:ss.fff` via `fmtMs`/`parseTime`.
- API errors are `{ error: string }` with a meaningful status; the frontend surfaces `err.message` from that.
- Frontend and backend share no code — keep API response shapes in sync with the `app.js` consumers by hand.
- Docs (README, `site/`, this file) are updated in the same change as the code they describe — see the Documentation section.
- **DEV_MODE shortcuts are gated on the hostname, not just the flag** (`src/lib/dev.ts` `isDevHost`, used by the login bypass and by the extra Apple trust anchor whose private key is committed under `test/fixtures/billing/`). A `DEV_MODE=1` that leaks into a deployed environment must grant nothing. The cron is the one exception and says why: its payloads come from Apple's Server API over TLS, so nothing user-supplied reaches the verifier (`appleStoreApiRootsDer`).
- **No write route checks entitlement.** A Pro gate goes on a read (`requireEntitlement`) or on one stripped field (`stripProFields`), or on the client at the point of use — never on a `POST`/`PUT`/`DELETE` to the logbook. The setup-sheet writes are the one stated exception (NS-32 rule 5: a dropped setup sheet is a form, not a session). Every feature gets a row in the NS-32 tier table before it merges, and `test/api/entitlement-gates.test.ts` enumerates the guarded set so adding a gate anywhere else fails a test rather than a user's recording.
- **A 402 is not an error, it is an offer.** `{ error: "pro required" }` renders the paywall on every client — the web's `proPanelHtml`, iOS's `LoadState.paywall`/`ProUpsellCard`, Android's `LoadState.Paywall` — never the generic "couldn't load this" or the offline sync banner. That is why `APIError.proRequired` / `ApiException.PaymentRequired` are their own cases beside `unauthorized`.
