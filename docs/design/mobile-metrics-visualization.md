# Visualizing the PDR metrics on a phone

Design doc for epic [#193](https://github.com/Richie97/track-history/issues/193)
and its tickets #186–#192. It answers one question the tickets leave open:
**how do the performance metrics and the car metrics become usable on a
phone**, where the screen is 390 pt wide, the reader is standing in a paddock
between sessions, and the sun is on the glass.

The tickets say *what* each view answers and *which* platforms get it. This
doc settles the shared shape the views live in, then the phone treatment of
each one, so the first ticket to ship lays the surface the rest ride on
rather than adding a sixth panel to the event page.

Status: **proposal.** Nothing here is built. Where it takes a position the
tickets did not, the position is marked and the open questions are collected
at the end.

Rendered phone mockups of every screen in this doc, drawn with the app's own
tokens on synthetic lap data:
https://claude.ai/code/artifact/a4ba6bcc-7460-40bb-9ff1-a39f1283d6da
(the event-page door, then the Time, Inputs, Grip and Car tabs; the dashed
line across each board is the fold on an 844 pt phone).

---

## 1. What exists today

The three clients already draw the same analysis surfaces, in three different
containers. The differences are the starting constraint.

| | Web (`public/`) | iOS (`apps/ios/`) | Android (`apps/android/`) |
|---|---|---|---|
| Channel panel | `<details>` inside the session card: chips, sector table, delta chart, six channel charts | A **sheet** (`LapChannelChart`) opened from a "Channel graphs" row in the session card | **Inline** in the session card, inside the event page's `LazyColumn` |
| Chart drawing | Hand-rolled SVG strings, hover tooltip | Swift Charts, tap-to-park read-out | Compose `Canvas`, no read-out yet |
| Track map | Canvas, best lap, speed-painted, replay dot | `Canvas`, best lap, 220 pt tall card | `Canvas`, best lap |
| Progress chart | SVG, per track | Swift Charts, per track **and** every lap of the event in order | `Canvas`, per track |
| Stats line | `best 3 avg · up to speed by lap N · pace ±/lap · theoretical best` | same string (`statsSummary`) | same string |
| Selection model | 3 highlight slots (`--chart-line`/`-b`/`-c`), best lap preselected, chips are the legend | same | same, survives rotation |

Three facts from the code that constrain the design more than any layout
preference:

1. **iOS cannot draw big charts inside the `List`.** `LapChannelChart.swift`
   documents it: a chart of this many marks inside a `List` row never settles,
   which is why the panel is a sheet. Swift Charts also needs one homogeneous
   `ForEach` per chart and per-mark accessibility suppression, so anything with
   thousands of marks (a friction-circle envelope) wants `Canvas`, like the
   track map.
2. **Android draws everything inline** in the session card. That works for one
   collapsed chart stack and will not survive four more, both for scroll length
   and for recomposition cost inside a `LazyColumn`.
3. **The read-out is a tap, not a drag**, on both native clients, because a
   drag over a plot steals the scroll. Any interaction this doc proposes has to
   be a tap.

And two facts about the data:

- `sessions.trace` is the **best lap only**, ~300 points, time-sampled.
  Channels are **per lap** on a 20 m distance grid. Anything that puts a
  channel on the map is therefore best-lap-only until a per-lap trace exists
  (#188 says so and this doc does not change it).
- `channels` is the one field `stripProFields` nulls for a free account, and
  `meta` (ambient, intake, elevation, odometer) lives inside it. A free account
  sees none of this, which is the intended tier line for the charts and an
  accident for the odometer and the weather. See open questions.

## 2. Principles for the phone

The epic fixes two constraints: the event page cannot absorb five more
panels, and every view must compare against the driver's own best lap and
resolve to a place on the track. On a phone those two turn into six rules.

1. **One question per screen.** A phone shows one thing at a time. The
   epic's tabs (Time / Inputs / Grip / Car) are the right cut, and on native
   they are tabs on a **screen of their own**, not sections of the event page.
2. **The sentence comes first, the chart second.** A driver between sessions
   reads a line, not a plot. Every tab opens with a one-line read
   (*"ABS in 3 corners, wheelspin on 2 exits"*) generated by the same pure
   module on all three clients, and that string doubles as the chart's
   accessibility summary. The chart is the evidence for the sentence.
3. **One cursor, everywhere.** A single "where on the lap" position, parked by
   a tap on any chart, on the friction circle, or on the map, and shown on all
   of them at once. This is how "this dot" answers "which corner" without
   hover. iOS already has the state (`readout`); it becomes shared across tabs
   and the map strip.
4. **The map is the "where".** A small track-map strip pinned above the tabs
   carries the cursor and the limit markers. It is the one element that is on
   screen whichever tab is open.
5. **Absent, not empty.** A tab renders only when the session carries what it
   needs. A hand-entered session has no Analysis screen at all; a GoPro import
   has Time and Inputs (speed only) and no Car tab. Never an empty axis.
6. **Report, don't scold, and never colour-alone.** Markers are coloured by
   *kind* (braking / traction / stability), never by severity; every mark has
   a shape as well as a colour; thresholds shade, they do not alarm.

## 3. Information architecture

### 3.1 The Analysis screen (native)

One screen per session that carries channel data, reached from the session
card. iOS keeps the sheet it already has (the `List` hazard is real); Android
moves the inline chart stack to a destination, `Route.Analysis(sessionId)`,
with the session card keeping the chips as its lap list and gaining the same
"Analysis" row iOS has.

```
┌──────────────────────────────────────┐
│ ‹ Session 2 · VIR (Full)      2:06.41 │  title: label · track · best
├──────────────────────────────────────┤
│  ○ L1 2:09.1  ● L3 2:06.4★ ● L5 2:07.0 →  chips (horizontal scroll, legend)
├──────────────────────────────────────┤
│   ┌────────────────────────────┐     │
│   │        track map strip     │     │  best lap, speed-painted,
│   │   ▲ABS  ●TC   ┃cursor      │     │  limit markers (#188),
│   └────────────────────────────┘     │  cursor at 1.2 km
│   1.2 km · T5 exit  ·  L3 vs L5      │  cursor read-out line
├──────────────────────────────────────┤
│ [ Time ] [ Inputs ] [ Grip ] [ Car ] │  segmented control / tab row
├──────────────────────────────────────┤
│  "L5 loses 0.4 s in S2, mostly T5"   │  one-line read for the tab
│                                      │
│  sector table                        │
│  delta chart          ┃              │  cursor rule on every chart
│  speed                ┃              │
│  …                                   │  scrolls within the tab
└──────────────────────────────────────┘
```

What stays fixed while the tabs change: the chips (selection), the map strip
(location), and the cursor. What changes: the one-line read and the chart
stack.

Heights that fit a 390 × 844 pt phone: chips 36, map strip 150 (shorter than
the event page's 220 pt card, because it is context here, not the subject),
cursor line 20, tab row 40. That leaves ~450 pt of chart before scrolling,
which is three 150 pt charts, the same height the charts are today.

### 3.2 The four tabs

| Tab | Question | Content, top to bottom | Renders when |
|---|---|---|---|
| **Time** | Where did the time go? | sector table · delta chart · speed | always (every channel lap has `speed`) |
| **Inputs** | What did I do with my hands and feet? | throttle · brake · **gear ribbon** (#187) · rpm · shift-point read-out · steering | any of throttle / brake / steering / gear / rpm |
| **Grip** | How much of the car was I using? | **friction circle** (#186) · quadrant tiles · lateral G · longitudinal G · yaw · **balance summary** (#189) | `latG` present (circle needs `longG` too) |
| **Car** | Is the car okay, set up right, and what were the conditions? | **health strip** (#190) · boost · conditions (#191) · odometer line (#192) | any scalar or `meta` present |

The limit markers from #188 are not a tab. They live on the map strip (all
tabs) and as shaded bands on the Inputs traces, because "where is the car at
its limit" is the spatial layer every other question is asked against.

### 3.3 Web

The same four tabs, inside the existing `<details>` panel in place of the
current single stack. The chips stay above the tabs as they are now, the map
strip is the existing best-lap canvas made smaller and given the cursor, and
hover replaces tap. Nothing about the web's containers changes; the point of
settling the IA here is that the web version and the phone version are one
design at two widths, not two designs.

### 3.4 Tier and offline

The Analysis screen is what `canViewChannels` gates. A free account has
`channels: null` and so has no door, which is the existing behaviour; a 402 on
the way in renders the paywall, never the sync banner. Everything the screen
needs is in the cached event detail, so it works offline with no new fetch.

## 4. The cursor

The cursor is a grid index `k` (distance `k × dStepM`) shared by the map
strip, every chart on every tab, the friction circle and the balance view.
It is the single mechanism that satisfies the epic's "resolves to a place on
the track" on a screen with no hover.

- **Set by** a tap on any chart (nearest grid point by x), a tap on a
  friction-circle dot, a tap on a limit marker, or a tap on the map strip
  (nearest trace point, mapped back to a grid index).
- **Shown as** a vertical rule on every distance-axis chart, a ring on the
  friction circle and balance scatter, and a dot on the map strip.
- **Read out as** one line under the map strip: distance, then one value
  per highlighted lap for the *active tab's first chart* (`1.2 km · L3 92 mph ·
  L5 88 mph`), which is what the iOS read-out already formats.
- **Cleared by** tapping the same point again, as on iOS today.

Mapping a grid index to a trace point needs one pure helper, because the two
series have different lengths and the GPS trace's cumulative length is
inflated by noise: compute cumulative distance along `sessions.trace`,
normalise both series to a **fraction of their own total length**, and match
by fraction, the same trick `lapTimeSeries` uses to pin the speed integral to
the timed lap. Proposed as `traceIndexAtDistance` in a new
`public/js/trace-distance.js`, pinned by `contracts/logic/trace-distance.json`,
ported as `TraceDistance` to the Kit and `:core`. It is best-lap-only by
construction; for any other highlighted lap the map dot shows the best lap's
position at the same *fraction*, and the read-out says so once (`map: best
lap`).

Haptic detent on every cursor change on native, as the record screens do.

## 5. The views, one by one

Each subsection gives the phone layout, the one-line read, the interaction,
what is deliberately left off the phone, and the pure module that carries the
maths so the three clients agree.

### 5.1 #188 — Limit markers on the map and bands on the traces

*Where is the car at its limit?* The first thing to build, because it rides
two surfaces every client already has.

**Map strip.** Markers along the best lap's line, one per contiguous run of
grid points where a condition holds, placed at the run's start:

| Kind | Condition | Mark | Colour token |
|---|---|---|---|
| Braking limit | `flags & 1` (ABS) or `wheelSlip < LOCKUP_PCT` | short bar across the line | `--mark-brake` |
| Traction limit | `flags & 2` (TC) or `wheelSlip > WHEELSPIN_PCT` | filled dot | `--mark-traction` |
| Stability | `flags & 4` (VSC) | ring | `--mark-stability` |

Three kinds, three shapes, three colours. ABS and lockup are the same
*kind* to a driver (the front let go under braking) so they share a mark; the
read-out distinguishes them in words. The tokens are new: the chart slot
colours mean *laps* on this screen and cannot be reused for *kinds*. They go
in `public/style.css` for both themes and reach the apps through the two
token generators, never as literals. Proposed dark values, checked for
colour-vision separation against each other and for contrast on the card
surface: `--mark-brake: #ff8a5c`, `--mark-traction: #f4c542`,
`--mark-stability: #b58cff`. The light theme needs its own three, stepped
darker the way the slot colours are.

At 150 pt tall a VIR map is ~140 pt across and a marker is ~8 pt. Runs closer
than 12 pt collapse into one marker with a count badge (`×3`), and a tap on a
marker parks the cursor at its start and moves the Inputs tab into view of
that distance.

**Bands.** On the throttle and brake traces, a translucent rectangle (the kind
colour at ~18% alpha) spanning each run's grid points, for every highlighted
lap. Bands are per lap; markers are best lap only. The map strip carries a
`best lap` caption whenever a non-best lap is highlighted so the mismatch is
stated.

**One-line read.** `ABS in 3 corners · wheelspin on 2 exits` from the best
lap; `no interventions` when nothing fires (TC/VSC read zero with the systems
off and that is not distinguishable from "never needed").

**Pure module.** `public/js/limits.js`: `limitRuns(lap, dStepM)` →
`[{kind, fromK, toK}]`, `limitSummary(runs)` → the sentence, with
`WHEELSPIN_PCT = 2`, `LOCKUP_PCT = -2` beside `FULL_THROTTLE_PCT` /
`BRAKING_PCT` and tuned against real footage before shipping. Fixture
`contracts/logic/limits.json`; ports `Limits`.

### 5.2 #187 — Gear ribbon and shift points

*Was I in the right gear?* Second to build; rides the Inputs tab.

**Ribbon.** A 28 pt band directly under the brake trace, sharing its
distance axis, one block per gear run, the gear number centred in any block
wider than 18 pt, gear 0 drawn as a gap. Fill is the lap's slot colour at 35%
alpha with the number in `--text-strong`, so the ribbon reads on a sunlit
screen where a thin line would not.

With two or three laps highlighted the ribbons stack (14 pt each, up to 42),
and any distance where the highlighted laps disagree **for at least
`GEAR_DISAGREE_MIN_M = 100` m** gets a `--text-strong` hairline outline
spanning the stack. The minimum run is load-bearing: two laps that brake a
car-length apart shift a grid point apart, and outlining every one of those
buries the one corner taken in a different gear under a picket fence of
timing noise (the mockup did exactly that before the rule). The cursor read-out at such a point is
the whole feature: `1.4 km · L3 4th · L5 3rd`.

```
 brake  ───╮        ╭───
           ╰────────╯
 gear   L3 ▐ 4 ▌▐  3  ▌▐ 4 ▌▐    5    ▌
        L5 ▐ 4 ▌▐ 3 ▌▐  4   ▌▐   5    ▌
              ┊ outlined: laps disagree
```

**Shift-point read-out.** Under the ribbon, one row per upshift with the
median and range of the RPM at the sample before the step:

```
 2→3  6,650 rpm  (6,400–6,800)   ≈
 3→4  6,700 rpm  (6,550–6,750)   ≈
 4→5  6,200 rpm  (5,900–6,700)   ≈  short-shifted twice
```

The `≈` is the ticket's "label it approximate": a shift takes about one grid
point at speed and can fall between samples. The trailing note is the
sentence worth a piece of advice, from two named constants: `SHORT_SHIFT_RPM`
below the session's own median and a `LIMITER_RPM` guess from the session's
max `rpm`.

**One-line read.** `Same gears as your best lap` or `L5 took T5 in 3rd, best
lap took it in 4th` (first disagreement, resolved to a corner via the sector
number until corner segmentation from #189 exists).

**Phone-specific.** Nothing is left off; this is the view that translates
best to a small screen. The ribbon is a `Canvas` on Android and, on iOS, a
`Canvas` too rather than Swift Charts `RectangleMark`s, so it sits in the
same `VStack` as the charts without the mark-count hazard.

**Pure module.** `public/js/gears.js`: `gearRuns`, `shiftPoints`,
`gearDisagreements`, `gearSummary`. Fixture `contracts/logic/gears.json`;
ports `Gears`.

### 5.3 #190 — Session health strip

*Is the car okay, and set up right?* The Car tab. This is the view most at
risk of being a table nobody reads on a phone, so it is grouped by what a
driver checks, not by column.

```
 ┌ Tyres (hot, end of lap) ─────────────────┐
 │   LF 31.3 psi  ▁▃▅▆▇▇▇     RF 30.8  ▁▃▅▆▇▇▇ │   2×2 in car layout,
 │      88 °C                    92 °C        │   pressure end + temp max,
 │   LR 29.9      ▁▃▅▆▇▇▇     RR 30.1  ▁▃▅▆▇▇▇ │   sparkline across laps
 │      81 °C                    84 °C        │
 │   spread: L–R +0.5 psi · F–R 4 °C hotter   │   the derived line
 └────────────────────────────────────────────┘
 ┌ Temperatures (peak per lap) ──────────────┐
 │  Oil 130 °C ▁▃▅▆▇▇▇▓   Coolant 98  ▁▂▃▃▃▃ │   ▓ = above threshold,
 │  Trans 104   ▁▂▃▄▄▄▄                       │   shaded not alarmed
 └────────────────────────────────────────────┘
 ┌ Pressure · electrical · fuel ─────────────┐
 │  Oil min 210 kPa   Battery min 13.1 V      │
 │  Fuel 41% · ≈0.9%/lap · ~12 laps left      │   burn for free
 │  Boost peak 12.1 psi ▁▃▅▅▅▅▅               │
 └────────────────────────────────────────────┘
```

- **The gear ribbon's hysteresis** is a rendering concern too: `gear` is
  stored as sampled, and a car holding a speed on a shift threshold reads as
  alternating gears. The ribbon draws the stored values; it does not smooth
  them, and a session that genuinely hunts between gears should look like it.
- **Sparklines are across laps, not distance.** Lap number on x, the
  session's own min–max on y, final value in text beside it. Seven laps make
  seven bars; the value is always written, so the sparkline is decoration for
  a number that stands alone.
- **Threshold shading** reuses the garage's wear vocabulary: `ok` (accent),
  `low` (the accent/danger mix the wear bar uses), `due` (danger). A tile is
  `due` when the lap crosses a constant (oil above `OIL_C_MAX = 130`, battery
  below `BATT_V_MIN = 12.5`, oil pressure below `OIL_KPA_MIN`) and `low`
  within a margin of it. Initial values, tuned before shipping.
- **Spread lines** are the coaching output: LF−RF and front−rear deltas per
  lap, shown for the last lap with a sparkline of the delta. Camber and
  balance evidence in one line.
- **Tap a tile** to expand it into a full-width per-lap chart with the
  threshold band drawn; tap again to collapse. No separate screen.
- **Units.** Tyre pressures are stored in kPa and the setup sheet's cold
  pressures in psi; display psi, converting at the edge like speed. See open
  questions for temperature.
- **The setup loop stays web-only**, as the ticket says. Native shows the hot
  pressures and, where the event day has a setup sheet with `tp_cold`, a
  read-only `cold 22.6 → hot 31.3` on each tyre tile, since `GET /events/:id`
  already carries the sheets. The *suggestion* ("drop 2 psi") is the web's.

**One-line read.** `Oil peaked at 130 °C on lap 6 · tyres +8.7 psi hot ·
~12 laps of fuel` — the three numbers a driver checks before the next session.

**Absent, not empty.** A session with no scalars renders no Car tab. A
session with scalars but no `meta` renders the strip and no conditions block.

**Pure module.** `public/js/health.js`: `healthTiles(channels)` (grouped,
with status per tile), `tyreSpread`, `fuelBurn`, `healthSummary`, and the
constants. Fixture `contracts/logic/health.json`; ports `Health`.

### 5.4 #191 — Conditions

*Was it actually a hot afternoon?* Small on every client.

- **Session header.** `27 °C ambient` (or °F, see open questions) appended to
  the session's stats line on all three clients, since that string already
  exists on each. Recorded value first; the event's manual `temp_f` as
  fallback; never write one into the other.
- **Progress chart band.** On the track page's per-event chart, a faint band
  behind the line whose height follows each event's ambient. On iOS this is
  a `RectangleMark` series in the same `ForEach` as the line (small mark
  count, no hazard); on Android a rectangle pass before the line in
  `ProgressChart`; on web a `<rect>` layer in `lineChart`. The band has no
  axis and no label beyond a `hotter` caption at its top, because it is
  context, not a series.
- **Car tab.** Ambient, intake and elevation as one text row at the bottom of
  the health strip. Intake belongs here as a heat-soak signal, as the ticket
  says.
- **Track page.** Elevation range as one line in the summary.

**One-line read (Car tab).** `Ambient 27 °C · intake 41 °C · 180 m of
elevation`.

No new module; conversion helpers in `format.js` and its ports.

### 5.5 #186 — Friction circle

*How much of the tyre am I using?* Web first per the ticket; designed for
the phone now so the Grip tab is shaped for it.

- **Square, full width**: 358 pt on a 390 pt phone. Lateral G on x (left
  and right), longitudinal on y (braking down, power up). A square is not
  negotiable; a circle that draws as an ellipse reads wrong.
- **Envelope** of every lap as a single low-alpha point cloud, drawn in one
  pass. Highlighted laps as 3 pt dots in slot colours. The reference arc at
  the session's 99th-percentile combined G, labelled once (`1.5 G today`).
- **Quadrant tiles** beneath, two numbers side by side, each with its own
  sentence: `Trail braking 31% of cornering samples` · `Throttle on exit
  24%`. These are the coaching point and they are readable without the
  chart.
- **Cursor** as a ring on the current sample of each highlighted lap, so
  parking the cursor on T5 in the Inputs tab and switching to Grip shows where
  T5 sits on the circle. Tapping a dot parks the cursor there.

**Phone-specific.** Drawing: on iOS this is `Canvas`, not Swift Charts; a
30-lap session is ~7,500 envelope points and Swift Charts wedges on that
count. On Android, `Canvas` as everything else. On both, the envelope is
drawn as one `Path` of points, not one shape per point, and laps beyond
`ENVELOPE_MAX_LAPS = 20` are subsampled every other grid point.

**One-line read.** `Filling 68% of the circle vs 74% on your best lap` where
the percentage is the area of the sample hull over the reference disc, the
one number the shape reduces to.

**Pure module.** `public/js/friction.js`: `combinedEnvelope` (the p99
radius), `quadrantShares`, `circleFill`, `frictionSummary`. Fixture
`contracts/logic/friction.json`; ports `Friction` when it graduates.

### 5.6 #189 — Balance

*Am I understeering or oversteering?* Web first for the scatter; the phone
gets the sentence.

- **On the phone, v1 is the per-corner list**, not the scatter:

  ```
   T1   understeer   ▮▮▮▯▯
   T3   neutral      ▮▯▯▯▯
   T7   oversteer    ▮▮▯▯▯   slight
  ```

  One row per corner, tendency in words, magnitude as five blocks, best lap
  vs the highlighted lap when one is selected (`T7 · best neutral · L5 slight
  oversteer`). Tapping a row parks the cursor at the corner's apex.
- The `yaw` trace joins the Grip tab on all three clients cheaply.
- The scatter itself stays web-only until the relative version has proven
  it says something; on a phone it is a cloud with no room for a legend.

**Corner segmentation** (sustained `|latG|` above `CORNER_G`) is its own
module, `public/js/corners.js`, because the limit read-out, the gear
disagreement sentence and the balance list all want "which corner is this
distance in". Once it exists, every sentence in this doc that says `T5` uses
it instead of a sector number. Fixture `contracts/logic/corners.json`; ports
`Corners`.

### 5.7 #192 — Odometer

*How far has this car actually gone?* Server and garage; the phone shows a
line.

- **Session header (Car tab).** `Odometer 71,130 km`.
- **Vehicle page ledger.** Beside the estimated hours for each event that
  has a recorded session: `+1,180 km since last recorded session`, and
  `since your last recorded session` as the standing caption so a partial
  record never reads as complete. A decrease renders as `different car?`,
  not as an error.

Once `GET /garage` carries the figure the native garage pages show it for
free; the storage and reconciliation are the server's, as the ticket says.

## 6. Shared mechanics

**Rendering budget.** A tab renders only when it is active, and a chart only
when it is on screen (the web's lazy-on-expand rule, generalised). Nothing on
the Analysis screen draws until the driver opens it. The friction-circle
envelope and the limit bands are the two things that can exceed a few thousand
marks; both are drawn as single paths.

**Accessibility.** Each chart is one element whose value is the tab's or
chart's one-line read, the same string the sighted driver sees, generated by
the pure module and pinned by its fixture. The gear ribbon's blocks carry
their numbers; markers carry their kind in words; the cursor read-out is
announced on change. Nothing new is colour-alone: three marker shapes, block
numbers on the ribbon, words on the balance list.

**Landscape.** Not designed for in v1. The tabs and the cursor work at any
width; a later pass can let a chart go full-screen on rotation.

**Theme.** Every new colour is a token in `public/style.css` (both blocks),
regenerated into both apps. Three new marker tokens and nothing else; the
health strip reuses the wear vocabulary and the chart slots stay what they
are.

**Tier.** No new gate. The Analysis screen exists only for a session with
`channels`, which the server strips for a free account; NS-32's tier table
gets one row per ticket saying "channels".

## 7. Modules, fixtures and ports

Every sentence and every threshold is computed once, in JavaScript, pinned by
a fixture generated from that implementation, and ported under the same name.
This is the existing rule; the table is what it means for these tickets.

| Ticket | Pure module (`public/js/`) | Fixture (`contracts/logic/`) | Kit / `:core` | Draws on web / iOS / Android |
|---|---|---|---|---|
| cursor | `trace-distance.js` | `trace-distance.json` | `TraceDistance` | `trackmap.js` / `TrackMapView` / `TrackMap` |
| #188 | `limits.js` | `limits.json` | `Limits` | map strip + bands in the channel panels |
| #187 | `gears.js` | `gears.json` | `Gears` | `channel-graphs.js` / `Canvas` ribbon / `Canvas` ribbon |
| #190 | `health.js` | `health.json` | `Health` | new health strip on each |
| #191 | `format.js` (conversion only) | — | `LapTime`/`Format` | `chart.js` / `ProgressChart` / `ProgressChart` |
| #186 | `friction.js` | `friction.json` | `Friction` (on graduation) | new square chart, `Canvas` on both apps |
| #189 | `corners.js`, `balance.js` | `corners.json`, `balance.json` | `Corners`, `Balance` | list on native; scatter web-only |
| #192 | server (`src/`) | golden contract | `Vehicle` model | garage ledger on each |

The IA itself (tabs, which tab is present, the cursor state) is a pure

## 9. Open questions

1. **Temperature display unit.** The manual field is °F, every channel is
   °C, and the audience is US. Recommendation: display °F everywhere, convert
   at the edge like speed, keep storage as is. Needs a yes.
2. **Pressure display unit.** Stored kPa, setup sheet psi. Recommendation:
   psi. Needs a yes.
3. **`meta` and the tier line.** Ambient and odometer sit inside `channels`,
   which is stripped for free accounts. If the weather on the progress chart
   is meant to be free, `meta` (or `ambientC` alone) needs to be lifted out
   of the stripped field, which is a server change and a tier-table row.
   #192 already proposes a column for the odometer.
4. **Android: destination or sheet?** This doc says destination, for the
   back-stack and rotation reasons NS-26 records. A `ModalBottomSheet` would
   match iOS more closely but fights the scroller.
5. **Thresholds.** Every constant above is an initial value. They need a
   pass over real footage before the first one ships, and they live in one
   place per module so that pass is one edit.
6. **A per-lap trace.** Every "best lap only" caveat in this doc goes away
   if `sessions` stores a small trace per lap. It is a storage and contract
   change and not part of any ticket here; worth deciding before #186
   graduates, since the friction circle is where "which corner" matters most.
