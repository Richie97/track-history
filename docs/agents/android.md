# Android app (`apps/android/`)

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

`:core` is pure Kotlin/JVM; `:app` is the Compose shell. Rules shared with iOS and the web are in `clients.md`.

## Project, modules and the ported core

`apps/android/` is a Gradle project split the same way: `:core` is pure Kotlin/JVM (no Android dependency, enforced by a `checkNoAndroidDependency` task that fails the build if one appears) and `:app` is the Compose shell — `applicationId`/`namespace` `app.trackevolution`, kept from the retired shell for the same in-place-update reason as iOS, `minSdk` 26, Java 17 bytecode while `:core` stays on 21. Every plugin version is declared once in the root `build.gradle.kts` with `apply false` (the Kotlin JVM and Kotlin Android plugins are the same artifact, so a second version declaration makes Gradle refuse to resolve either), and libraries live in `gradle/libs.versions.toml`. Building `:app` needs an SDK (`ANDROID_HOME` or a gitignored `local.properties`), but `:core:test` deliberately does not — AGP defers its SDK check to task execution, which is what keeps CI's core job SDK-free and under a minute; the `app` job installs the SDK and runs `:app:assembleDebug` plus `:app:testDebugUnitTest` (Robolectric, so still no emulator). Manifest permissions (location, foreground service, `POST_NOTIFICATIONS`) are **declared, not requested** — the runtime request belongs to the feature that needs it, so the user is asked in context.

**`ACCESS_BACKGROUND_LOCATION` is declared in the `debug` manifest only** (the recorder harness asks for it): Play rejected a release that declared it under the Prominent Disclosure policy, and the recorder never needed it — a recording starts from the visible app and its location-typed foreground service keeps receiving fixes on "while using the app". `:app:checkReleaseHasNoCarApp` fails the build if it reappears under `src/main`; a feature that really needs "allow all the time" owes a prominent in-app disclosure before the system prompt and Play's location declaration first. The launcher icon is the adaptive icon inherited from the retired shell and the launch theme is `Theme.TrackEvolution.Splash` (androidx core-splashscreen, brand near-black `#0A0A0B`), swapped for the real theme by `installSplashScreen()`; the *window* theme underneath Compose follows the system's light/dark through `values-night/`, since it is drawn before Compose can consult the in-app override. `:core` carries the ported logic (`RecorderCore`, `GeoTrace`, `LapTime` — the port of `public/js/format.js`) plus `model/` and `api/`: `@Serializable` data classes with explicit `@SerialName` on every field (never a global snake_case strategy — a mismatch has to be visible at the field), and `ApiClient`, a Ktor client whose **engine is injected** so `:app` supplies OkHttp while tests drive the identical code through `MockEngine`. Two decisions there are load-bearing: `GoldenContractTest` decodes every golden with `ignoreUnknownKeys = false`, so a field the server adds and no model covers fails a test instead of vanishing — while the shipped `ApiClient` decodes with `ignoreUnknownKeys = true`, because the server deploys ahead of the Play rollout and a strict client turned #192's `odometer` on `/garage` into a screen-wide error on every installed build that predated it (iOS's `JSONDecoder` ignores unknown keys by default, so it never had the problem) — and the harness also decodes *and re-encodes* every entry in `contracts/golden/manifest.json`, which is what also catches a field the model has and the server doesn't. Failures map to a sealed `ApiException` carrying the server's own `{ error }` string — `Unauthorized` is its own case so re-auth is a type check, and `Transport` (no answer at all) is deliberately distinct from a status, because only one of the two is worth retrying. Epoch-millisecond columns are `Long`; Kotlin's `Int` is 32 bits, which is why NS-04 can spell `updated_at` as Swift's 64-bit `Int` and this cannot. Update requests use a three-state `Patch` (`Unchanged` omits the key, `Set(null)` sends an explicit null) because the server writes only the columns *present* in the body. `contracts/golden/` (regenerate with `npm run contracts:generate`, verify with `contracts:check`) pins every API response as JSON so both clients' decoders are tested against the real thing; `contracts/logic/` (`contracts:logic`) does the same one level down for *ported pure logic* — it runs the web implementation and commits its output, so the ports assert equality with the reference rather than with each other (the iOS lap-geometry port matches `public/js/import/geo.js` lap times to the millisecond). Design system: `public/style.css` stays the source of truth, and the iOS color tokens are *generated* from it by `apps/ios/Tools/generate-tokens.mjs` into an asset catalog (Any = the stylesheet's light values, Dark = its dark defaults) plus a token list for the debug-only gallery (`-tokenGallery` launch argument) — so use `Color(.bgPage)`, never a hex literal, and re-run the generator rather than editing either output. On iOS Geist isn't bundled (no font binaries in the repo), so `App/DesignSystem/Typography.swift` falls back to SF Pro/SF Mono behind a documented seam. Android has the same arrangement one directory over: `apps/android/tools/generate-tokens.mjs` reads the same two stylesheet blocks and writes `app/src/main/kotlin/app/trackevolution/ui/theme/ColorTokens.generated.kt` (a `TrackColors` data class plus the light and dark instances and a catalog for the gallery), consumed through `TrackTheme.colors` — with `TrackTypography`, `TrackRadii` and `TrackMotion` beside it and a Material `ColorScheme` derived from the tokens only so unwrapped Material components aren't the wrong color.

**Dynamic color (Material You) is off on purpose** — the accent is the charts' "faster" signal — and `surfaceTint` is transparent so Material's tonal-elevation wash can't reintroduce depth the design system draws as a hairline plus one surface step (`TrackCard`). Geist and Geist Mono *are* bundled there, as single variable fonts pinned per weight with `FontVariation` (SIL OFL 1.1; the license ships in `assets/licenses/`), sizes in `sp` and tracking in `em` so both scale with the system font setting. The theme override (system/light/dark, mirroring `public/js/theme.js`) persists in DataStore via `ThemePreference`. The gallery is `TokenGalleryActivity` in the **`debug` source set** with its own manifest and launcher entry — not compiled into a release build at all, rather than merely unreachable.

**Android sign-in** (NS-09) splits the same way: `:core` owns the pure half — `Pkce` (base64url-unpadded `S256`, using `java.util.Base64` rather than `android.util.Base64`, whose default flags append a newline and fail verification), the `/auth` client methods, and `DeepLink`, the routing-table port that is unit-tested rather than tapped through and which deliberately refuses `trackevolution://auth?code=…` so navigation can never race the sign-in flow for a code that is burned on first use. `:app` owns everything Android: a **Chrome Custom Tab** (never a WebView — Google blocks OAuth in embedded web views, and `CustomTabs.open` must be handed an *Activity*, since launching from the application context throws and `FLAG_ACTIVITY_NEW_TASK` would put the tab in the wrong task), and `AuthStore`, an `EncryptedSharedPreferences` file holding the token *and* the in-flight PKCE verifier — the verifier because the flow leaves the process when the browser opens, and both readable while the device is locked because the lap recorder runs locked and has to sync.

**An undecryptable store is treated as empty rather than fatal** (`EncryptedPrefs`): the ciphertext and the AndroidKeyStore key that unwraps it can come apart — most often because Auto Backup carries the prefs file and never the key — and Tink then throws `AEADBadTagException` out of `EncryptedSharedPreferences.create`, which, since `isSignedIn` is read by the cold-start billing sync, was a launch crash loop no user could escape without clearing app data. The store now wipes the file *and* the master key alias and reopens once, costing a sign-in and nothing else; the retry is not retried, and its failure is thrown carrying the original. The common cause is closed at the source by `res/xml/backup_rules.xml` + `data_extraction_rules.xml`, which exclude `auth.xml` from cloud backup **and** device transfer — **the two files say the same thing for different API levels and have to be edited together**. The decision is split out from the Jetpack call because Robolectric has no AndroidKeyStore provider, so the real store cannot be opened on the JVM and only the pure half is assertable (`EncryptedPrefsTest`). `AuthController.handleRedirect` ignores a code with no pending flow behind it, which is what stops a redelivered intent after a recreate from burning a good session. The provider buttons come from `GET /auth/providers` and are cached **per server** (`AuthProvidersStore`), so a failed fetch is a no-op rather than a silent downgrade to Google-only, and pointing a debug build at `wrangler dev` and back never carries one deployment's answer to the other. The dev-server override and its cleartext exception (`10.0.2.2`, the emulator's alias for the host, where the server's `DEV_MODE` bypass answers) are gated to debug builds — the network-security config lives in the `debug` source set so no release build can ship one.

**Android billing** (NS-32 phase C) is `app/.../billing/`, in `:app` only — `:core` carries the `Entitlement` model with the tier predicates (`isPro`, `canRecord`, `canViewChannels`, `canUseGarage`, `canUseSetups`, `canViewYearInReview`, `canViewSpend` — NS-37, read by the track page's spend line since NS-40 — `manageUrl`, `entitlementSummary` — the port of `public/js/entitlement.js` under the same names, pinned to `contracts/logic/entitlement.json`, the fixture the iOS Kit asserts against too), the `/billing` client methods (`postGooglePurchase`, `claimGoogleLegacy`) and a 402 `ApiException.PaymentRequired` case beside `Unauthorized`, and `checkNoAndroidDependency` keeps the store SDK out of it. `BillingController` is process-wide on `AppServices` (started from `TrackEvolutionApp.onCreate`) because two of its jobs belong to no screen: **`queryPurchasesAsync` runs on every cold start**, re-posting anything the server doesn't yet know about and anything still unacknowledged, and a purchase Play reports **with no signed-in user is held until sign-in, not dropped** (`onSignedIn`, which `MainActivity` drives off the auth state). The one rule there that costs money is **acknowledge only after `POST /api/billing/google` returns 200** — Play refunds an unacknowledged subscription after three days, acknowledging first is how a paying user ends up free when the post fails, and a 409 (the token is another account's) is never acknowledged from this one; that decision is pure in `PurchaseSync` and plain-JUnit tested, as are `LegacyClaim` (done on 2xx/403/409, retry on anything else), `PaywallPlans` (ISO period → words, an introductory-trial offer preferred over the bare base plan, the yearly savings badge) and `Backoff` (the `SERVICE_DISCONNECTED` reconnect schedule, doubling from 1 s to a 60 s cap). `ApiClient` takes `defaultHeaders`, which is how `AppServices` puts **`X-TE-Client: android/<versionCode>`** on every request without `:core` seeing `BuildConfig`, and the **once-per-install legacy claim** (`POST /api/billing/google/legacy`; the flag lives in `BillingPrefs` on the shared DataStore and survives sign-out on purpose) runs each time the app becomes signed in — from launch, never from the code exchange, since thirty-day sessions never re-exchange. Every billing answer's `entitlement` lands on `AuthState.SignedIn` through `AuthController.setEntitlement`, so the gates, Settings' *Subscription* card (`entitlementSummary`/`manageUrl` — Subscribe when free, Manage when a store sold it, nothing for a legacy grant, which has no subscription behind it) and `PaywallSheet` (price and billing period from Play's own `ProductDetails`, both legal links, Restore) read one value rather than copies.

**The gates are on since phase D**: `Entitlement.GATES_ENABLED = true`, with `recordGate` — the only one, since import is free — taking the flag as a parameter so `EntitlementTest` covers both values; the recorder's Start (`AppNavHost`'s `Route.Record`) goes through it — the event page's *Import video…* and the share-sheet import in `SignedInScaffold` do not, since importing is free — and offline the cached `/api/me` entitlement stands — a driver who was Pro at the last sync records. Nothing about tier is persisted client-side beyond that cache.

**App Links** are verified against `public/.well-known/assetlinks.json`, which carries the **Play app-signing** SHA-256 — so verification succeeds only for a Play-signed build, never for a locally-signed debug one; check with `adb shell pm get-app-links app.trackevolution`. The file is served by the Worker from `public/`, so changing the signing key means redeploying the Worker, not shipping an app update.

**The Android lap recorder** (NS-16) is `app/.../recording/`: a foreground `Service` with `foregroundServiceType="location"` that **owns the recording**, so the UI can be swiped out of recents without stopping it — and which is why the native app needs none of the legacy-bridge workaround the retired shell carried to stop Android halting its WebView's background location after five minutes. `startForeground` is called **before** any permission check or I/O, because the system kills the process if it hasn't happened within five seconds of `startForegroundService`. Deliberately `START_NOT_STICKY`: a service the system restarts with no recording state would post a notification claiming to record while capturing nothing, so restart is handled by recovering the journal instead. Durability is `RecordingJournal` in `:core` (plain `java.io`, so it unit-tests against a real temp file with no emulator) — an append-only JSONL file written **per accepted fix**, whose tuples are byte-identical to `RecorderCore.serializeRecording`'s; a **deviation from NS-16's "use Room"**, taken for the same reasons iOS deviated from NS-15, and documented at the class. It is flushed but not `fsync`ed, which covers a force-stop and a crash but not power loss — an fsync at 10 Hz is not worth the battery. `Location.toFix()` is where Android's "no reading" sentinels die: `hasSpeed()`/`hasAccuracy()` gate the values, because a 0 that means *unknown* is indistinguishable from one that means *stationary* once it is in the trace, and `location.time` (the fix's own) is used rather than the delivery clock so a batched delivery isn't rejected wholesale by `addFix`'s monotonic check. Permission staging is not a choice: Android **rejects** a combined fine + background request, so `RecorderPermissions` reads them separately and `POST_NOTIFICATIONS` is its own ask on API 33+ — without it the foreground notification is silently invisible, which was the second defect the retired shell shipped. The `Recorder` object is the observable seam (state plus the finished/recovered recording) that NS-18's screen and NS-20's Android Auto both read, and `RecorderHarnessActivity` in the `debug` source set is a bench for driving it directly.

**Android Auto (NS-20) is built but does not ship**: Play rejected it under `PF-1` because Android has no category permitting a driving-task app (POI is the closest, and a lap timer has no point-of-interest functionality — there is no Android equivalent of the CarPlay entitlement Apple granted). Everything car therefore lives in the `debug` source set — sources, `res/xml/automotive_app_desc.xml`, the `<service>` and both `<meta-data>` blocks in `app/src/debug/AndroidManifest.xml`, and `androidx.car.app` as `debugImplementation` — because the *declarations* are what make an artifact car-compatible to the review pipeline, so merely unregistering it would not be enough. `:app:checkReleaseHasNoCarApp` fails the build if one reappears under `src/main`, since CI only ever builds the debug variant and nothing else would notice until a store review. The Android Auto **form factor must also stay opted out in the Play Console** — a non-compliant car artifact in the production track rejects the entire submission, phone updates included, and no build can guard Console state.

**The recording UI** (NS-18) sits on top: `SignedInScaffold` keeps the recording banner *above* the destination so an in-progress or unsaved recording is visible from anywhere, and a `BackHandler` that navigates rather than stops — a recording must not be endable by a gesture. `RecordingFlow` holds the review state above the view tree, so a rotation cannot lose a pick. The picker's geometry is `TraceMap` in `:core` (fit, hit-test, and the y-flip that keeps north up — get it wrong and every circuit draws mirrored), and the pick itself is `LineReview`, which names the two ways a pick legitimately yields nothing — a stationary pick has no direction to build a gate across, a line crossed once has no lap — because each needs different advice and a silent empty list is the dead end the web app's wording exists to prevent. Saving posts `laps` as integer milliseconds plus the best lap's polyline and — since the video importer landed (NS-32) — the per-lap **`channels`** that `TelemetryChannels.buildLapChannels` cuts from the phone's own fixes, the same side effect NS-30 had on iOS; a source that yields none posts `channels: null`, never a half-formed shape, because `sanitizeChannels` rejects one with a 400. The journal is cleared only *after* the server accepts, so a failed save in a paddock costs a retry and never the session.

**The Android charts** (NS-24) split the same way again: `:core` carries `ChartScale` (the port of the scale maths in `public/js/chart.js`) and `ChannelGraphs` (the non-drawing half of `channel-graphs.js`, with `matchLapsToChannels` pinned to `contracts/logic/channels.json`), while `app/.../ui/charts/` draws — `ProgressChart`, `TrackMap` and `LapChannelChart`, all hand-rolled on Compose `Canvas` rather than on Vico, since `LinePicker` already established the Canvas idiom and a charting library's axis defaults would have to be fought rather than used. Three things there are load-bearing.

**Lower lap times plot lower** — `ChartScale.plottedFraction` returns a fraction measured *from the top*, and a Compose canvas already grows y downward, so it is used as-is; inverting a second time yields a chart that reads exactly backwards, which iOS shipped once.

**The reference is the web, not iOS**: iOS's `ChartScale` chose 4% y-padding against `chart.js`'s 12%-with-a-500 ms-floor and returns `1` rather than `0.5` from `speedFraction` for a constant-speed trace, so the Kotlin port follows the JS and records the divergence at the class — NS-24 asks for parity of *meaning*, not of padding. And `ChannelGraphs.valueExtent` is deliberately separate from `valueDomain`: the domain is padded so the trace does not touch the frame, and 8% below a speed of zero is a *negative speed* — fine as an axis bound, nonsense in the screen-reader summary, which is what surfaced it. Every chart carries a `contentDescription` saying which way the trend goes, because down-is-better is precisely the convention a screen-reader user cannot see, and the lap chips carry number and time beside their colour dot so identity is never colour-alone. `ChartGalleryActivity` in the `debug` source set is the bench — all four in both themes, plus the 20,000-fix line picker, since a stored trace is capped at 300 points by `GeoTrace.lapTrace` and only a raw recording reaches that size.

**The Android offline layer** (NS-22) is `:core`'s `offline/`, the port of `public/js/offline.js`: `OfflineStore` (response cache, write queue, temp ids, ordered replay), `applyLocal` in `OfflinePatch.kt` (the optimistic patches that keep the dashboard, event page and track page agreeing before a sync), and `OfflineMirrors` — `recomputeDetail`/`cleanLaps`, now the *fourth* copy of two server behaviors, which is why all four are tabulated at the class. Storage sits behind `OfflinePersistence`, whose only entry point is a transaction, so a queued write and the optimistic cache patch that makes it visible commit **together** — the win over IndexedDB that both native clients take; the in-memory implementation is what lets the replay algorithm unit-test on the JVM in milliseconds, and the durable half is `:app`'s `data/`. That half is a single Room database (`OfflineDatabase`; schema exported to `app/schemas/`) behind `RoomOfflinePersistence`, deliberately with **no destructive-migration fallback** — the cache is refetchable, but the queue holds recorded sessions that exist nowhere else until they replay, so a schema change owes this database a real migration rather than a silent wipe on an app update. Replay is `ReplayWorker`, a WorkManager `CoroutineWorker` behind a `CONNECTED` constraint that **only reports success on an empty queue** — anything else is `retry`, which is what stops a write queued *during* a flush from being stranded, since `OfflineStore.flush` snapshots the queue when it starts. `SyncScheduler` enqueues it as unique work with `KEEP` (never `REPLACE`, which would cancel a replay mid-queue) from two triggers: any pending write, and a `ConnectivityManager.NetworkCallback` — a callback rather than a poll, and treated as a hint only, since a captive portal reports connected too. All of it hangs off `AppServices`, the process-wide holder behind the new `TrackEvolutionApp`, and it is a singleton for a load-bearing reason: `OfflineStore` keeps the pending count and the flush lock **in memory**, so a second instance over the same database would let the worker and the UI replay the same queue concurrently and interleave writes. Durability is asserted against real SQLite, not the in-memory fake, by `:app`'s Robolectric suite (`./gradlew :app:testDebugUnitTest`, now a CI step) — the fake proves the logic reloads, which is a different claim from the file surviving. A temp id is a **negative Int**, not `tmp-N`: `Event.id` is an `Int` pinned by the golden contract, real server ids are always positive, and the value never reaches the server — the same call iOS made, so the representation differs while the behavior doesn't. `ApiClient` *is* the offline layer once it is given a store: reads are network-first and fall back to the cache only on a *transport* failure, never on a status (answering a 500 from a stale cache would hide it), a queueable write with nowhere to go becomes a queue entry plus a synthetic `{id}`/`{ok}` response, and a write made while others are pending queues too rather than jumping the line. Every case in `test/unit/offline.test.js` has a Kotlin counterpart in `OfflineStoreTest`, and `OfflineMirrorsTest` checks the recomputation against the `contracts/golden/` event details rather than against itself.

**The Android logbook** (NS-26) is `app/.../screens/` — one model per screen owning its fetches and writes, the composables staying layout — with `app/.../navigation/` holding the graph.

**The signed-in shell is two tabs** (NS-37, `navigation/Tabs.kt`): `AppNavigationSuite` — Material's `NavigationSuiteScaffold` from `material3-adaptive-navigation-suite`, BOM-versioned because it ships in the `material3` group rather than on the `material3Adaptive` train, a bottom bar at compact width and a rail wider — around `TwoPaneShell`, and the one `NavHost` split into two nested graphs, `EventsGraph` (start `Route.Dashboard`; every logbook route and Settings) and `GarageGraph` (start `Route.Garage`; the garage list and `Route.Vehicle`). `selectTab` is the multiple-back-stacks idiom (`popUpTo(findStartDestination()) { saveState }`, `launchSingleTop`, `restoreState`), `Route.tab` names each route's home, and `show` — which `showDeepLink` now is — switches to that tab and resets it to its root beneath the target, so `/vehicle/:id` lands in the Garage at every width and a car page's links to its events arrive in Events; `go` is a plain push within a tab and a `show` across one. Back at the Garage root selects Events, back at the Events root still `moveTaskToBack`s, the suite draws no bar (`NavigationSuiteType.None`) for the recorder, the importer and Wrapped, and it sits inside the banners and under the review overlay, so a tab switch can neither hide a recording nor bury an unsaved one. At expanded width the list pane is the tab's own list (`DashboardPane` or `GaragePane`) and `Route.Garage` draws *"Pick a car"* (`garageAsDetailPlaceholder`). The Garage item's badge is `GarageBadge` — `Garage.garageAlerts` counted from whichever screen last read `/garage`, refreshed by the scaffold at most once a minute, shown for Pro only and said as the item's `stateDescription`, since Material clears a badge's own semantics. Routes are **type-safe** `@Serializable` classes (`Route`), so a renamed argument breaks the build rather than a tap, and `routeFor` maps the `:core` `DeepLink` table onto them; none of the retired shell's `backButton`/hash-router approximation is ported. Four decisions there are load-bearing.

**A screen's model is scoped to its `NavBackStackEntry`, not `remember`ed** (`rememberScreenModel`): a `remember` is discarded on a configuration change, so rotating would re-fetch every screen and throw away a half-typed event form.

**The event form's draft additionally goes through `SavedStateHandle`** (`SavedState`, plus a `hydrated` flag so a re-`load()` cannot overwrite a restored draft with the server's copy) — the system killing a backgrounded app is ordinary on Android, and the draft is the one thing on these screens that cannot be re-fetched.

**Review is an overlay above the graph, not a destination**: "save or discard this recording" is modal, and putting it on the back stack would let a gesture bury an unsaved session behind the logbook — while the recording banner stays above the destination, so it is visible from every screen (both rules inherited from NS-18, which the scaffold now hosts a `NavHost` in place of its enum). And **back at the root minimizes rather than finishing the activity** (`moveTaskToBack`), because the task may have a recording notification attached to it — the same call the retired shell made. `FollowTempIds` watches the queue and replaces a destination parked on an offline-created id (`Route.remapTempId`) the moment the write flushes, popping the stale entry with it.

**Season Wrapped is native here too** (NS-36, `screens/WrappedScreen.kt` + `WrappedModel.kt` + `WrappedPoster.kt`, `Route.Wrapped(year)`): the port of the web story and of iOS's `WrappedScreen`, a plain `composable` that **owns the window** — `SignedInScaffold` drops to one pane for it as for the recorder — opened from the dashboard's November banner (dismissals in a `wrapped` SharedPreferences file via `WrappedDismissStore`). The card in view lives on the model, so a rotation or a fold keeps it; navigation is the thirds, a swipe, the arrow buttons and the progress segments, with TalkBack custom actions. The poster is drawn on an `android.graphics.Canvas` in the bundled Geist and shared as a PNG from the cache's `wrapped/` directory through the manifest's `FileProvider` (`${applicationId}.wrapped`, `res/xml/wrapped_paths.xml`) — the only FileProvider in the app, scoped to that one directory. **The share link's preview image** (#155) goes up from here too: `AppNavHost` hands `WrappedScreen` a `sendPreview` lambda when the account has a share slug, a `LaunchedEffect` on the loaded season's year calls it, and `WrappedPreviewUpload.send` (in `WrappedPoster.kt`) draws `WrappedPoster.previewJpeg` — the wide poster over `WrappedStory.previewData` (`pro` nulled), `share = true`, always `DarkTrackColors`, JPEG at 90 — and calls `ApiClient.putWrappedImage(year, jpeg)`, a `ByteArrayContent` PUT behind `ownOnly()`, never queued. It is skipped while `WrappedStory.previewSignature` (with the slug) matches what the `wrapped_preview` SharedPreferences file holds for the year, and fails silently.

**Share with a coach is native here too** (NS-38 ticket 4): `:core` carries the ports — `Coaching` (`studentLine`, `lastViewedText`, `inviteExpiryText`; not to be confused with `model.Coaching`, the `GET /api/coaching` response) and `Profile` (`PROFILE_GROUPS`, `profileSections`, `profileBody`, plus `formValues`, its reverse) under the JS names, pinned by `CoachingTest` against `contracts/logic/coaching.json` — and every coaching route on `ApiClient` (`profile`, `updateProfile`, `coaching`, `createCoachInvite`, `withdrawCoachInvite`, `removeCoach`, `leaveStudent`, `coachInvite` — which reads **past the cache** (`cached = false`), since its path carries the single-use token — and `acceptCoachInvite`), all live writes off the offline whitelist, which `OfflineStoreTest` pins.

**`LogbookOwner`** (`core/api/`, `Me` / `Student(id, name, pro)`) is the seam: `ApiClient.forOwner(owner)` is a view over the *same* transport, token and offline store whose every `/api` path gets `/students/<id>` in front — so the student's responses are cached under the prefix, apart from the coach's, and derive their own `?track_id=` lists — and which throws `ApiException.ReadOnly` for any write **before** the offline layer could queue it or the network carry it (`CoachingApiTest`); `owner.entitlement(viewer)` is the tier the channel gates read, the **student's** for a student. `ApiClient.forgetStudent(id)` is `OfflineStore.removeCachedPrefix`. In `:app` the owner routes carry an optional `student` (`Route.Event`, `Lap`, `SessionCompare`, `Track`, `CompareLaps` — `Route.studentId` is the one place that knows which, and `remapTempId` `copy`s so it survives), beside `Route.Student(id)` (the student home, a pushed destination on the Events tab — never a third tab) and `Route.StudentVehicle` (its own route because `Route.Vehicle` lives in the Garage graph); each of those destinations wraps the **owner's own screen** in `LogbookOwnerScope` (`screens/StudentLogbook.kt`), which resolves the student from their `/me/profile` under the mount through a keyed `StudentGateModel`, draws the *"You're viewing …'s logbook · read-only"* banner, publishes `LocalLogbookOwner` (read only by the channel panel, whose Pro card becomes `studentFreeNote` for a free student — the upgrade is theirs, not the coach's) and hands down the scoped client; `EventScreen` / `TrackScreen` take `readOnly` and `VehicleModel` reads it off `api.owner`, dropping every write control, the recorder and import doors, the checklist, the course notes, the leaderboard and share buttons and the car page's whole Pro half (no `/garage` under the mount). A 404 from that profile purges the student and says so (`studentGone`). **The video is never copied**: `ContentByteSource` wraps the seekable descriptor `ContentResolver.openFileDescriptor` returns for a `content://` URI and reads by position, which on Android is the default rather than something to engineer around (iOS had to route around `PhotosPicker`, which copies) — the picker is the SAF `OpenMultipleDocuments` (Files, USB sticks, and every photo app with a documents provider) plus the photo picker as a second door, and an `ACTION_SEND`/`SEND_MULTIPLE` intent filter for `video/*` and the three CSV types lets Files or Photos share a clip — or Porsche Track Precision share its CSV — straight in (`MainActivity.sharedFiles` parks the URIs the way deep links are parked; `ContentByteSource.nameForType` adds `.csv` to a bare shared name the provider types as CSV, since the parser dispatches on the name). A `.vbo` has no MIME type of its own and is not a share target. The parse runs on `Dispatchers.IO` in one job, and cancellation reaches the parsers through the byte source — `read` throws `CancellationException` when the job dies — so the `:core` code stays identical to the JS.

**The review flow is not rebuilt**: `RecordingFlow`/`ReviewScreen` were generalised from one `Recording` to a list of `ReviewItem`s over `ParsedTelemetry` (a `ParsedRecording` converts via `asTelemetry()`), so a PDR clip with beacons arrives with exact laps and skips the picker, a GoPro clip needs a line, one picked line applies to every clip in the batch in a shared projection frame with the JS's longitude-sign mirroring, and the save posts one session per included clip with the web importer's exact notes line. `ImportScreen` is only the chooser (`Route.Import(eventId)`); once parsed, the scaffold hands the clips to the review overlay and pops the chooser, and a saved import lands back on the event it came from.

**Batch anchoring is stage 2 included**: `TelemetryImporter.finish` sorts clips by the clock the file wrote, runs `PDRLaps.anchorPdrBatch` and re-cuts channels for anything whose laps moved, as `ui.js` does. `RecordingFlowImportTest` (Robolectric, `MockEngine`) pins the request shape — laps, trace, channels, notes, and that a *recorded* session now carries channels — and `ContentByteSourceTest` proves the no-copy seam over a real file.

**Android Auto** (NS-20) is `app/src/debug/.../auto/` — **debug builds only, because Play rejected it** (see the category paragraph below): a `CarAppService` + `Session` + one `Screen` on the Car App Library, driving the *same* `Recorder`/foreground service the phone does — so both surfaces observe one object and cannot disagree, and connecting or disconnecting the car cannot interrupt a recording it never owned. It sits in `:app` rather than the `:auto` module NS-20 asks for, and the reason is structural: requirement 3 forbids a bridge layer, `Recorder` lives in `:app`, and a Gradle *library* module cannot depend on an *application* one — so `:auto` could only reach it through the bridge the spec rules out. Documented at `TrackAutoService`, the same way NS-15 and NS-16 recorded their deviations. `AutoRecording` holds every string and the template assembly, so the one surface that can't be opened on a desk still has tests: the Car App Library enforces its distraction caps by *throwing* when a template exceeds them, which makes template construction worth asserting rather than eyeballing. Two behaviours there are deliberate — a blocker outranks an active recording (location switched off mid-session is what the driver needs to see, not a timer that has stopped meaning anything), and a **missing notification permission is not a blocker**, matching `RecordingService`: the recording works, it's just invisible, and refusing to record over that trades the irreplaceable thing for the recoverable one. The attachment rule is `RemoteRecording` in `:core` — the port of `public/js/record/remote.js`, pinned to `contracts/logic/remote-attach.json`, the same fixture iOS asserts against; `Event` implements its `EventCandidate` interface so logbook rows pass straight in. Fractional days **truncate** and a nonsensical day count still covers the start date, both because the JS does and all three clients must land a recording in the same event.

**The category risk landed: Play rejected the app over it.** Android Auto has no driving-task category — the supported set is navigation, POI, IoT, weather, media and communication, and quality criterion `PC-1` forbids features outside them. NS-20 declared **POI** as the least-bad fit, on the reasoning that the category is only reviewed once the app opts in to the Android Auto form factor in the Play Console. That opt-in happened at NS-27 and the review fired: rejected under `PF-1` ("meaningful functionality relevant to driving" *in the declared category*), which a lap timer has none of and cannot acquire — so this is not a fixable finding, and NAVIGATION would fail the same criterion. Google's tooling still labels the POI bucket "Parking and Charging", the pre-1.3 category names, which is why the rejection reads as a parking app. Everything car therefore moved to the **`debug` source set** — sources, `res/xml/automotive_app_desc.xml`, the manifest block, and the `androidx.car.app` dependencies (`debugImplementation`), with `AutoRecordingTest` in `src/testDebug`. A release APK must not merely fail to reach that code, it must not contain it: the review fires on any submission carrying a car-compatible artifact while the form factor is opted in, and a failure in the *production* track rejects the whole submission, freezing ordinary phone updates too. CI only ever builds the debug variant, so the invariant is invisible — `:app:checkReleaseHasNoCarApp` (wired into `check` and its own CI step, in the spirit of `:core`'s `checkNoAndroidDependency`) fails the build if a car declaration reappears under `src/main`. The fallback NS-20 documented is what ships instead, and already existed: the recording notification's Stop action plus the driving-sized `RecordScreen`. Re-promoting any of it is a Play-policy decision, not a build one. `automotive_app_desc.xml` and the `com.google.android.gms.car.application` meta-data remain load-bearing and silent when wrong — without them Android Auto never discovers the service, nothing fails to build, and no test notices, exactly like iOS's CarPlay entitlement.
