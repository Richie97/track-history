# CI and release workflows

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

**CI / release workflows** (`.github/workflows/`): `ci.yml` (web + backend, `paths-ignore` so a new top-level directory still runs it), `ios.yml` and `android.yml` (the native clients, path-filtered — `ios.yml` is two parallel jobs, `kit` (`swift test`, no simulator) and `app`, which builds the app **once** with `build-for-testing` for the simulator its unit tests then run on with `test-without-building`; the two steps must keep the same destination, `-derivedDataPath` and `-only-testing`, or the second compiles everything again, which is what used to push the job past 15 minutes. Package checkouts are cached on `Package.resolved`, and both jobs carry `timeout-minutes`), `pages.yml` (the docs site), `play-production.yml` and `app-store-review.yml` (store submission, dispatch-only — see the end of this paragraph), and `android-release.yml` — **Play Store test track**, the only workflow that ships anything to a store *automatically*. It fires on every merge to `main` touching the Android client (same path filter as `android.yml`), uploading to the **internal** track, and via `workflow_dispatch`, which offers `internal`/`alpha`/`beta` — deliberately *not* production — plus optional `versionCode` / `versionName` overrides and a dry run. The `versionCode` is derived from the ref's commit count (monotonic on `main`; a version code is burned on upload even if the release is discarded, so automatic uploads must never reuse one), with the dispatch input as the override; the value checked into `build.gradle.kts` is only what local builds get. It runs `:app:checkReleaseHasNoCarApp` before anything else — a car declaration back under `src/main` must not reach a review — then the tests, then `:app:bundleRelease`, then verifies the bundle is actually signed **and minified** — the release build type runs R8 (`isMinifyEnabled` + `isShrinkResources`), because Play scores obfuscation and shrinking per app and an unminified bundle drew a "below 25%, may impact visibility and publishing" notice — before uploading with `r0adkll/upload-google-play`, passing `build/outputs/mapping/release/mapping.txt` so the Console deobfuscates crashes. Play's other per-bundle warning — "contains native code, and you've not uploaded debug symbols" — is not actionable and stays: the only `.so` files are AndroidX's, shipped already stripped, so `ndk.debugSymbolLevel` extracts nothing (don't add it; the release build type says why). An upload failure reading "a change was made to the application outside of this Edit" is a Console session saving concurrently, not a build problem; the edit is discarded and the job can simply be re-run. Keep rules live in `apps/android/app/proguard-rules.pro` and should stay near-empty: everything reached by reflection (Room, WorkManager, kotlinx.serialization's `serializer()` lookups, Tink) is covered by the libraries' own consumer rules, and a blanket `-keep class app.trackevolution.**` would hand back the obfuscation score. Release signing is read from `TE_UPLOAD_KEYSTORE*` in the environment by `apps/android/app/build.gradle.kts`, which also honours `TE_VERSION_CODE` / `TE_VERSION_NAME`; with none of them set the release variant builds **unsigned** rather than falling back to the debug key, so only CI (with the real upload key from repository secrets) can produce a shippable artifact. The five secrets are listed in README. Two NS-27 preconditions no build can enforce: Android Auto must be opted out in the Play Console, and the recorder must survive a real track day before the rollout passes 10%. iOS has no counterpart — those builds go through Xcode Cloud.

**Store submission** is two more workflows, both `workflow_dispatch`-only so no merge reaches a store review on its own, and neither builds anything — each moves a build testers already have: `play-production.yml` (`release/play.mjs`: `status` / `start` — a test-track `versionCode` onto production at a rollout percentage — / `increase` / `halt` / `resume` / `complete`, all inside one Play edit, dry run = Play's own `validate`; it shares `android-release.yml`'s `play-release` concurrency group, because two open edits make the second commit fail) and `app-store-review.yml` (`release/app-store.mjs` on a Linux runner against the App Store Connect API: `status` / `submit` — the version's newest Xcode Cloud build, waited for while it processes, attached to a created-or-reused App Store version with What's New, release type and phased release, then submitted — / `release` / `pause-phased` / `resume-phased` / `complete-phased`; secrets `APP_STORE_CONNECT_ISSUER_ID` / `_KEY_ID` / `_PRIVATE_KEY`). The scripts are dependency-free Node (fetch and `node:crypto` sign the ES256 / RS256 JWTs), and every rule about what may be promoted or which store state refuses is a pure function in `release/lib/` tested by `test/unit/release.test.js` — add a refusal there, not inline in a script.

**Release notes** are the dispatch's `release_notes` input when it is filled in (a literal `\n` is a new line, since GitHub's input box is one line), else `release/notes/<version>.txt`, one file for both stores — `resolveNotes` in `release/lib/notes.mjs` is that rule, and either source is held to 500 characters, Play's limit. The file fallback is why that test also pins Android's `versionName` equal to iOS's `MARKETING_VERSION`: bump both together. Neither workflow answers App Review, Play's Data safety form or the App Privacy label, and neither declares export compliance — `ITSAppUsesNonExemptEncryption` in `apps/ios/App/Info.plist` does, and a build without it is refused. README → *Store submission* is the user-facing write-up.
