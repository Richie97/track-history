# Backend (`src/`)

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

One Worker serves both the API and the static frontend (`wrangler.jsonc`: `public/` is served as SPA assets; `/api/*`, `/auth/*`, `/share/*` and `/get` hit the Worker first, among the paths listed in `run_worker_first` — `/` itself too, exact and without a wildcard, so the home page can be the landing page for a visitor with no session and the app shell otherwise (`src/routes/landing.ts`) — `/share/*` so share pages can carry per-slug OG meta, the `ASSETS` binding being how the Worker reads `index.html` to do it, and `/get` so the store redirect can answer per User-Agent instead of the SPA fallback answering it with the sign-in screen, and `/clips/*` so a signed best-lap video URL reaches the Worker that serves it (NS-45), and `/youtube/*` so connecting YouTube's consent round trip with Google (NS-46) isn't answered with the SPA shell, and `/tracks` + `/tracks/*` for the public track pages (#457)).

## Entry and middleware

- `index.ts` — composes the routers. Route order matters: `/api/share` (public, no auth) is registered before `/api` so `GET /api/share/:slug` stays unauthenticated while everything else under `/api` passes through `requireSession` (`middleware.ts`). The `/api` router itself is built by `apiApp(auth)` in `api.ts`, which takes the auth middleware as an argument: `index.ts` mounts it behind `requireSession`, and the MCP tools build a second, private copy of it (see the AI bullet below), and `index.ts` mounts a **third** at `/api/students/:studentId` behind `requireCoachGrant` — a coach's read-only view of a student's logbook (NS-38, see the `coaching.ts` bullet), registered before `/api` like `/api/share`. A new `/api` router is added to the list in `api.ts` — and to `API_ROUTERS` in `test/api/entitlement-gates.test.ts`. The one `/api` router that is deliberately *not* in that list is the AI Coach's, mounted on its own at `/api/ai` (see the AI Coach bullet).

- `middleware.ts` `requireSession` accepts the session as the `session` cookie (web) **or** an `Authorization: Bearer` header (native apps) — same `auth_sessions` rows. The lookup (`sessionUser` in `lib/session.ts`) joins `users` and sets `entitledUntil` on the context alongside `userId` in the **same single statement** — plus `authTransport` (`cookie` or `bearer`, which credential it took), read by `GET /me` and `freshEntitlement` to **mask a `stripe` source as `null` on anything but the cookie** (`maskEntitlementSource` in `lib/entitlement.ts`, NS-49 rule 4): both native `Entitlement.Source` enums are closed, so a fourth value would fail `/me` decoding on every installed phone app, and an app that can't tell a web subscription from any other can't steer a user to one either; tier, expiry and renewal stay intact, and an unset transport (the coach mount, the MCP tools' copy) masks too, so `requireEntitlement` — the Pro gate, `402 { error: "pro required" }` — is a pure comparison against `Date.now()` and issues no D1 statement. **It guards `GET /garage`, the parts/measurements routes, the setups routes, the coach invite and the best-lap video create / url / download and the YouTube draft / create (NS-46), and the AI Coach's two POSTs (#318), and nothing else** — `test/api/entitlement-gates.test.ts` enumerates that set by *handler identity* over the routers' `.routes`, so a gate added to a fourth router fails there even if no test happens to call it — and **no write route ever checks entitlement**: `POST`/`PUT`/`DELETE` on events, sessions, laps and tracks stay open to every signed-in account forever, because the offline layer drops rejected writes and a recording is the one irreplaceable thing in the system — `test/api/billing.test.ts` asserts a lapsed user's session save *with `channels`* is a 201. There is deliberately **no CORS**: the web app is same-origin and the native clients are HTTP clients that send no `Origin`, so nothing needs it (`lib/cors.ts` existed only for the retired web-view shells' local origins and was deleted with them — `test/api/native-auth.test.ts` now asserts that no origin gets a CORS header). The MCP surface is the one exception, and a different kind of thing: `/mcp`, `/oauth/token|register|revoke` and the two OAuth discovery documents answer `Access-Control-Allow-Origin: *` without credentials (`bearerCors` in `routes/oauth.ts`), because they authenticate with a bearer token the caller holds rather than an ambient cookie, and browser-based MCP clients can't reach them otherwise. `/api` and the cookie-authenticated consent page answer none.

- `db.ts` — data-access helpers. All take `(db, userId, ...)` explicitly so ownership scoping is visible at call sites: `ownedEvent`/`ownedSession` guard nested writes, `resolveTrack` find-or-creates tracks by name (`COLLATE NOCASE`; the name carries the layout — "Virginia International Raceway (Full)" vs "(Patriot)" — so bests/goals never mix across layouts), and `eventSelect`/`listEvents`/`tracksSummary` produce event rows with lap aggregates (a single-pass LEFT JOIN + GROUP BY, not per-row subqueries). D1 pays a network round trip per statement, so helpers backing a single endpoint also expose prepared *statements* (`…Stmt`) that routes combine with `db.batch()` into one round trip, and ownership checks on simple writes are folded into the write itself (`WHERE … user_id = ?`, or `INSERT … SELECT` from an ownership-scoped query, with zero changed rows meaning 404) rather than issued as a separate `SELECT` first. Tracks stay per-user, but each row carries a nullable `catalog_id` into the seeded `track_catalog` table — a canonical identity matched by name (NOCASE) via `catalogIdForName` on create and rename, so the same physical track is recognizable across users without sharing user-entered data. The catalog also backs the track-name suggestions in the event form (`GET /api/catalog`); adding a track to it means a new migration.

## Routes (`src/routes/`)

- `routes/` — one router per resource:

- `auth.ts` (Google OAuth or the DEV_MODE bypass → `auth_sessions` row → `session` cookie; a first sign-in claims a user row by matching email where that provider's sub column is NULL — which covers pre-seeded rows *and* cross-provider linking, so Google and Apple sign-ins with the same email share one account, and *because* accounts are claimed by email, both callbacks reject id_tokens whose email isn't verified (`isEmailVerified` in `lib/oidc.ts`); plus `POST /auth/dev/entitlement`, a DEV_MODE + dev-host-only tier control that writes or clears a `legacy` subscriptions row for the signed-in user, so a UI test can declare the tier it exercises instead of inheriting whatever the shared dev database holds — it owns one external id (`dev:<userId>`) and so never touches a real purchase, and on any other host it answers 404 rather than 403, reading as absent; plus the native-app flow — `?client=app&code_challenge=…` runs OAuth in the system browser and redirects to `trackevolution://auth` with a single-use code that `POST /auth/exchange` trades for a bearer token, PKCE-verified. Sign in with Apple is feature-flagged by the four `APPLE_*` secrets — `GET /auth/providers` tells the login screen whether to draw the Apple button — and mirrors the Google flow under `/auth/apple/*` with two quirks: the client secret is a self-signed ES256 JWT from `lib/apple.ts`, and Apple's email-scope callback is a *cross-site POST* (`response_mode=form_post`), so its state/PKCE cookies are `SameSite=None` and the callback route is a POST)

- `me.ts` (the signed-in user and their totals, plus `PUT /me/checklist-template` — the per-user prep list new event checklists start from, `users.checklist_template`, null meaning "use the client's built-in default" — `GET` / `PUT /me/profile` — the driver profile (NS-38), `users.profile` validated by `sanitizeProfile` in `lib/profile.ts`, answered as `{ id, name, picture, pro, profile }` because the same route under `/api/students/:id` is how a coach reads it and `pro` is then the student's tier; free, and never on the share page, the leaderboards or the MCP tools — and `PUT /me/units` — the unit system the logbook is shown in, `users.units`, `"imperial"` or `"metric"`; `GET /me` always answers a concrete value, imperial when the row is NULL or unrecognised, so the default lives in one place rather than in three clients. Display-only: nothing stored changes with it — `events.temp_f` stays whole °F, channel speeds km/h, setup pressures psi, fuel gallons — and `isValidTemp`'s range is the °F one — and `PUT /me/leaderboard`, the two strictly-opt-in flags behind the per-track leaderboards, `users.leaderboard_opt_in` and `users.leaderboard_share_laps` — the second optional in the body, so a shipped older client's `{ opt_in }` cannot clear a consent it doesn't know about, and cleared in the same statement when `opt_in` goes false)

- `tracks.ts` (tracks + `GET /tracks/:id/setups`, the "setup vs. lap times" rows for a track, + `GET /tracks/:id/leaderboard` — opted-in users' best **device-timed** laps at the same catalog track, matched via `tracks.catalog_id`, exposing only name/best/date and never anything user-entered; it filters on `laps.device_timed` and deliberately ignores the manual `events.best_time_ms` and hand-entered laps, unlike every logbook stat — NS-33, `docs/specs/native/NS-33-leaderboard-device-timed-laps.md` — plus its sibling `GET /tracks/:id/leaderboard/laps/:lapId`, which **opens** a row (NS-35, `docs/specs/native/NS-35-leaderboard-lap-detail.md`): the ranked lap's racing line and gridded channel traces, for a driver who set `leaderboard_share_laps`. An entry's `lap_id` is non-null only when its owner did, and everything the row satisfied is re-checked on the way in rather than trusted — the viewer must own a catalog track, the lap must be at that catalog and device-timed, its owner must hold both consents, and **its time must equal that owner's minimum device-timed time there**, which is the condition that keeps one lap per driver per track reachable rather than the logbook behind it; every refusal is a 404, never a 403, which would confirm the lap exists. What it carries is `lib/leaderboard.ts`: `publicLapChannels` builds the entry by *copying* `GRIDDED_CHANNEL_NAMES` rather than deleting what must not ship, so a scalar appended to `SCALAR_SPECS` later stays private with no edit there — the per-lap scalars are the car's condition and `meta.odometerKm` is its lifetime mileage, and neither is about the lap. `channels` is the one Pro field, `stripProFields`-ed exactly as on the event detail; the trace, the time and the recorded `ambient_c`/`elevation_m` are free)

- `events.ts` (events; per-event-day setup sheets — `PUT`/`DELETE /events/:id/setups/:day` upserting JSON validated by `sanitizeSetup`, plus `GET /events/:id/setups/prefill` for the copy-forward form prefill; `events.car` stays free text but is auto-matched to a garage vehicle by name into `events.vehicle_id` on create/update, `events.track_hours` optionally overrides the on-track-hours estimate, and the four **cost line items** (#147, migration 0025 — `cost_entry_cents` / `cost_fuel_cents` / `cost_travel_cents` / `cost_misc_cents`, whole cents validated by `isValidCostCents` in `lib/costs.ts`) are plain route-set columns whose computed total, `cost_cents`, `withComputed` adds to every event response — null, never zero, when nothing was entered, so an uncosted day drops out of every roll-up rather than reading as free)

- `sessions.ts` (sessions + laps; the create stores `trace_geo` beside `trace` — where the trace lies, NS-53, see the `geo.ts` bullet under `lib/` — and `PUT /sessions/:id` writes **only the keys present** — `label` / `notes`, trimmed, an empty string or explicit null clearing — since NS-40, the `PUT /events/:id` rule, and `offline.js` plus both native `OfflinePatch`es patch the same way; a body with neither is a 400)

- `vehicles.ts` (the per-user garage behind the Garage tab / `#/garage` (NS-37) — at most one `is_default` row per user pre-fills new events, and each row carries an optional `target_hot_psi`, the hot tire pressure the health strip's pressure loop aims at, validated by `normTargetPsi` and returned by the list, the create and `GET /garage` — plus, since #208/#221, the car's two spec-sheet constants `wheelbase_mm` / `steering_ratio` (validated by `isValidWheelbaseMm` / `isValidSteeringRatio` in `lib/validate.ts`, the ratio kept to two decimals) and a nullable `catalog_id` into `car_catalog`. The pick rule lives in `prefillFromCatalog`: a non-null `catalog_id` in a `POST` or `PUT` body pre-fills **both** numbers from the row — a null catalog ratio included, so a car re-picked from a C7 to a 992 never keeps the C7's ratio — unless the same body carries its own value (or explicit null) for one; unlinking with `catalog_id: null` leaves the numbers alone, and a body without the key never touches them, so the catalog is consulted at pick time and never again. Every vehicle response selects `VEHICLE_COLUMNS`, so the list, the create and the garage cannot drift — plus the garage logbook: `GET /garage` returns every vehicle with accrued hours and its parts, each carrying measurements and a computed `wear` estimate, plus what the car has cost (#147) — `event_cost_cents`, the entered costs of its *past* linked events (the same rows the hours accrue from, so an upcoming day isn't spent yet), and `parts_cost_cents`, every part ever fitted, retired ones included; both sums, so zero rather than null — and the car's own odometer (#192): `odometer` on each vehicle (its latest reading, `{ km, on, readings, other_car }`) and on each part (`{ km, from, to, readings }`, the distance between the first and last reading in its service window, null under two), from `lib/odometer.ts` over `sessions.odometer_km`, **reported beside the hours and never an input to `wearEstimate`**; parts CRUD under `/vehicles/:id/parts` + `/parts/:id` (each part carries an optional free-text `size`, and tires are a full set `tires` or a `tires_front` / `tires_rear` pair), one-tap replacement via `POST /parts/:id/refresh` — retires the part as of the swap date and inserts a same-spec successor, which inherits its size and, for a spare, its place on the shelf; on an already-*retired* part it retires nothing and just inserts the copy, equipped unless `equipped: false`, taking off what shares its place when `swap: true` (the web's Retired parts table offers it per row) —, the **Equipped switch** (migration 0029): `POST /parts/:id/equip` (`{ on? }`) opens a mount and closes the open mounts of every unretired part `equipSwapKinds` says shares its place (same kind; a full set against either pair; `other` never), answering `{ ok, unequipped }`, and `POST /parts/:id/unequip` closes it — a part is `equipped` (open mount), on the shelf (unretired, none) or retired, and `GET /garage` returns `size`, `equipped` and `mounts` on each; a create takes `equipped: false` (straight to the shelf, by deleting the trigger's mount) and `swap: true`, and its `installed_on` is optional — defaulting to today, so an undated part not equipped is a spare that has never been on the car, which every client words as *Added* rather than *Installed* (a spare with no mounts) — wear measurements under `/parts/:id/measurements`; a new part with no expected life defaults it from retired lifecycles of the same kind; plus `GET /vehicles/:id/steering-fit` (#223) — the per-session steering fits behind every vehicle form's *"Measured from 6 sessions: 15.8:1"* line: `steeringFit` from `lib/steering.ts` over the car's most recent `MAX_FIT_SESSIONS` (8) channel-carrying sessions, newest first, answering `{ fits: [{ session_id, event_id, start_date, gain0, K, samples, r2 }] }` with only the sessions that fit. **Its own route, not a field on `GET /garage`**, because the dashboard reads the garage on every load and eight channel blobs per car is a read worth making only while the form that shows the line is open; the clients pool the fits with `estimateSteeringRatio` against the wheelbase *in the form*, which may not be the stored one yet, so the ratio itself is never in the response. Pro like the rest of the garage, and enumerated in `test/api/entitlement-gates.test.ts`)

- `carCatalog.ts` (`GET /api/car-catalog`, #221 — every `car_catalog` row, ordered make / model / first year for a picker, small enough to ship whole so the pickers (#222) read it offline from the response cache; it is the car analogue of `GET /api/catalog` and, like it, seeded rather than user-editable. **The picker is on all three clients** (#222): one searchable field on the vehicle forms — the web's `bindCatalogPicker` over `bindCombo`, iOS's `CatalogCarPicker` sheet, Android's `CatalogCarPicker` dialog — with the ranking, the row label and the per-field pre-fill decision pure in `public/js/garage.js` and pinned by `contracts/logic/car-catalog-match.json`, see the `garage.js` bullet. The clients always send `catalog_id` *and* both numbers on a `PUT`, so what is on the form is what is saved and the server's pre-fill only ever runs for the Settings add flow, which sends the pick alone)

- `share.ts` (authed slug management, the public share endpoint — which returns stats/times but strips notes, email, per-lap data, all garage/setup linkage and what the days cost (the four line items and `cost_cents`, asserted by `test/api/share.test.ts`) — plus `sharePage`, the HTML route behind `GET /share/:slug`: it serves `index.html` through the `ASSETS` binding with per-slug OG title/description injected, because link scrapers never run JS; only already-public share data goes into the tags — and the Season Wrapped pair (NS-36): `GET /api/share/:slug/wrapped/:year`, the public season in `GET /wrapped/:year`'s shape **without the `pro` key**, and `sharePage`'s `/:slug/wrapped/:year`, registered ahead of `/*`, whose OG title is "<name>'s <year> on Track Evolution" and description `wrappedSummary` in the owner's units; the SPA's `SHARE_MATCH` parses the year out of the path and `shareWrapped` renders the story through the same `wrappedStoryHtml` as the authed view. **Its OG image is the owner's own poster** (#155) once one is stored: the page's owner lookup carries `wrapped_images.updated_at` as a subquery and, when there is a row, points `og:image` at `/share/:slug/wrapped/:year/og.jpg?v=<updated_at>` — `?v=` because scrapers cache an image by URL — and leaves the brand card otherwise. `sharePage`'s `/:slug/wrapped/:year/og.jpg` serves the stored JPEG in one statement that joins through the live share slug *and* requires a past event in that year, so removing the link or the season takes the image down with the page; anything else is a bare 404. The logbook page `/share/:slug` keeps the brand card)

- `itemShare.ts` + `itemSharePublic.ts` (share one event or one session, NS-48, `docs/specs/native/NS-48-share-event-session.md` — the owner's half is an ordinary `/api` router: `POST` / `GET` / `DELETE` on `/events/:id/share` and `/sessions/:id/share`, each answering `{ kind, token, url, created_at }`, POST idempotent (one `item_shares` row per item, so *Stop sharing* is one delete), **free** and in `API_ROUTERS` with no gate, live writes off every offline queue. The public half is mounted ahead of `publicShare` / `sharePage` in `index.ts`: `GET /api/share/(e|s)/:token` answers `{ kind, name, pro, session_id, event }`, reading the event **as its owner** through a private `apiApp` copy (the MCP tools' WeakMap pattern — `itemSharePublic.ts` must stay out of `api.ts`'s import graph, which is why the owner routes live in a file of their own) and narrowing it with `sharedEvent` in `lib/itemShare.ts`: the coach allow-list (`coachEventDetail`, exported for this) plus `vehicle_id` / `track_hours` nulled, every `clip` nulled unless the **owner** is Pro, and for a session link that session alone with the header's `best_ms`, `lap_count`, `session_count`, `consistency` and ambient worked out from it (`best_time_ms` null). `pro` is the owner's tier, which the clients open the channel panel by, as a coach's view uses the student's. `GET /api/share/(e|s)/:token/clips/:clipId/url` signs only a clip on a lap the link shows, and `itemSharePage` serves `/share/(e|s)/:token` with per-item OG tags. Every refusal is a 404; `no-store` throughout. The one-letter prefixes can never be a slug (three characters minimum), and `/share/*` is already in the AASA and the App Links filter. **NS-56 (`docs/specs/native/NS-56-share-lap-compare.md`) adds two kinds to the same routers and table**: a lap (`/share/l/<token>`, owner routes `/laps/:id/share`) and two laps compared (`/share/c/<token>`, `/laps/:id/compare/:otherId/share` — both the caller's, at one track, ordered A then B, a 400 otherwise). `shareKindOfRow` reads a row's kind from the columns it fills (migration 0039), and every event/session statement says `lap_id IS NULL`, because a lap's row carries its session's id. `sharedLap` cuts `sharedEvent`'s session view down to the one lap — its row, its own channel entry found by `matchLapsToChannels` over the **whole** session before the cut, the header's figures its own — and keeps `trace` only for the session's best lap, the lap the stored line was drawn from. The lap answer is NS-48's shape plus `lap_id` (which `/share/e` and `/share/s` now carry as null); a comparison answers `{ kind, name, pro, a, b }`, each side `{ session_id, lap_id, event }` resolved separately, so the two laps may share a session or sit in different events. The compare is a Pro view and the link follows the owner's tier like everything shared: `pro: false` and every client shows the two times and one sentence, never an upsell)

- `wrapped.ts` (Season Wrapped, NS-36 — `GET /wrapped/:year`: one calendar year's numbers, past events only, computed server-side by `seasonWrapped` in `lib/wrapped.ts` from one `DB.batch` — the user's events, each track's `track_catalog.length_m`, and, for the year's tracks the catalog has no length for, one driven distance per channel-carrying lap read *in SQL* through `json_each` (so no channel blob crosses into the Worker) plus the best-lap traces. Four-digit year or 400; a year with no past event is 404 `{ error: "no events in <year>" }`. `pro` is the one tier-dependent field, decided from `entitledUntil` like `stripProFields` decides `channels` — `null` for a free account, and for Pro `{ tire, top_speed }` with each null when there is no data, whose three statements (tire parts, `vehicleHoursEventsStmt`, a `json_each` walk for the year's top speed) join the same batch only when entitled; it is a per-field strip on a read, so `entitlement-gates.test.ts` does not list the route. Pinned by `contracts/golden/wrapped.json`, captured *last* in the harness because it adds an event, and decoded by both native `Wrapped` models though no native screen reads it — a native Wrapped is a screen, not a port. `PUT /wrapped/:year/image` (#155) stores the season's link-preview image: the Worker has no rasteriser, so the owner's browser draws the 1200×630 poster and sends it as a JPEG body, checked by `wrappedImageError` in `lib/wrappedImage.ts` — a size cap, then `jpegSize` walking the segment headers to the frame header, a format-and-dimensions check and not a decode; what the pixels say is the owner's own share card. One row per account and year in `wrapped_images`, upserted, with the *is there a season* check folded into the insert (`WHERE EXISTS` a past event that year, else the GET's 404). Free and ungated like every write; sent by all three clients, none of which reads the `{ ok: true }` it answers, so it has no golden)

- `coaching.ts` (share with a coach, NS-38 / #338, `docs/specs/native/NS-38-coach-sharing.md` — a Pro driver gives an instructor or coach read-only access to their whole logbook. The management half is an ordinary `/api` router: `POST /coaching/invites` (Pro, `requireEntitlement` — the stated exception beside the setups writes, since an invite is not a recording) mints a single-use, 7-day link `https://<host>/coach/<token>` whose token is stored SHA-256-hashed and so shown only in that response; `GET /coaching/invites/:token` previews it (`own`, `already_coach`); `POST …/accept` inserts the grant and burns the link in **one D1 batch**, re-checking inside it that the invite still exists and the student has room under `MAX_COACHES` (10) — so of two people accepting one link exactly one gets it, concurrent accepts of different links can't pass the cap, and a refusal (your own link, already a coach, no room) leaves the link unburned; `GET /coaching` lists both directions (`coaches` with `last_viewed_at`, `students` with past-event count and last date, open `invites`); `DELETE /coaching/invites/:id`, `/coaching/coaches/:coachId` (the student revokes) and `/coaching/students/:studentId` (the coach leaves). The read half is `requireCoachGrant`, the middleware of the third `apiApp` mount: one statement resolves the session **and** the grant (no session 401; no grant, a non-GET or a path off the table 404 — never 403, which would confirm the student exists), then the chain runs with `userId` = the student and `entitledUntil` = **the student's**, so ownership, `withComputed` and `stripProFields` are exactly the student's own and a free coach of a Pro student sees the full channel panel. Which paths, and what each answers, is `COACH_ROUTES` in `lib/coaching.ts` — one table of path + view, every view an allow-list that *copies* permitted fields (the `publicLapChannels` rule) and sends the hidden ones that have a place in the shape (notes, checklist, the cost line items, `setups`) as null / `[]` so both native models decode a coach's response unchanged. A session's `channels` is rebuilt the same way (`COACH_CHANNEL_FIELDS`, `COACH_META_FIELDS`): the per-lap entries whole, since they are the lap data a coach is invited to read, but `meta` cut to `ambientC` / `elevationM` — `odometerKm` is the car's lifetime odometer and stays out of reach with the rest of the garage, as `publicLapChannels` keeps it off the leaderboard. Only the two seeded catalogs pass through unfiltered. A lap's `clip` (NS-45) is copied through its own `COACH_CLIP_FIELDS` (`id`, `duration_ms`, `lap_offset_ms` — `size_bytes` is the student's bookkeeping), and `GET /clips/:id/url` is on the table, so a coach **watches** a student's best-lap videos with the student's tier and never downloads, deletes or uploads one; a URL already handed out plays until it expires, at most an hour after the grant goes. Shared: events, sessions, laps, trace, channels, conditions, `/vehicles` (whose `notes` hold the modifications), the steering fit, `/me/profile`, the two catalogs; never `/me`, `/garage`, setups, the leaderboards, Wrapped or any write. `last_viewed_at` is touched through `waitUntil` at most hourly; expired invites are swept by the daily cron. `/coach/*` is in the iOS association file since the iOS ticket (`wellKnown.ts`), and the Android App Link intent filter lands with Android's — an installed app that claimed the path before it could handle it would swallow every invite, and Apple's CDN caches the file, so **deploy the AASA change only once the iOS build that parses `/coach/<token>` is live**)

- `export.ts` (export your logbook, NS-44, `docs/specs/native/NS-44-web-export.md` — `GET /export/laps.csv`, `/export/events.csv` and `/export/logbook.json?telemetry=1`, Settings → *Your data* on the web. **Free and complete for every account**: a free account's file carries the channels, garage and setup sheets the app only draws with Pro, so no route is gated and none calls `stripProFields`; the router is in `API_ROUTERS` with no gate. Successful tool results have JSON Schemas in `ai/output-schemas.ts`; every `Tool` requires an `outputSchema`, published by `tools/list` only from protocol 2025-06-18 alongside support for `structuredContent`. Error results remain outside the success schema. Every tool result is an object (MCP's `structuredContent` must be), in **stored units with the unit in the key**, a summary rather than the channel blob, and bounded (`TELEMETRY_MAX_VALUES`, `MAX_RESULT_CHARS`).

**Pro is checked per `tools/call`** from the `entitled_until` loaded with the token — a lapsed account's assistant gets a tool error that says why, and `tools/list` still answers. `routes/oauth.ts` is the OAuth 2.1 authorization server the clients sign in through (pure rules in `lib/oauth.ts`): discovery (`/.well-known/oauth-protected-resource[/mcp]`, `/.well-known/oauth-authorization-server`, mounted as `oauthWellKnown` beside `wellKnown.ts`), dynamic client registration (public clients only — the answer always says `token_endpoint_auth_method: "none"`) **and** client-ID metadata documents (an https `client_id` fetched, validated against its own URL and upserted on every authorization), the consent page (`GET`/`POST /oauth/authorize`: server-rendered HTML on the login card's CSS with a strict CSP and `frame-ancestors 'none'`, a double-submit CSRF cookie on top of the session cookie's `SameSite=Lax`, the redirect host shown beside the self-declared client name, and a free account refused), `POST /oauth/token` (code with mandatory PKCE S256, rotating refresh tokens) and `POST /oauth/revoke`. Rate limits are Workers' rate-limiting binding, not WAF rules — assistants call from shared provider IPs, so only the Worker can tell users apart: `MCP_CALLS` per grant on `/mcp`, `OAUTH_TOKEN` per client id, `OAUTH_REGISTER` per `CF-Connecting-IP` (and, outside MCP, `EXPORT` per user on the logbook export and `AI_COACH` per user on the AI Coach; declared in `wrangler.jsonc`, optional in `Env`, applied through `withinLimit` in `lib/ratelimit.ts`, which treats a missing binding or key as unlimited so a limit can never be why a legitimate request fails; `test/api/ratelimit.test.ts`). Registration is open by design, so `sweepOAuth` runs beside `reverifyExpiring` in the daily cron (`scheduled` in `index.ts`): expired codes and tokens, and clients older than a day that no grant references. A signed-out user is sent through `/auth/login` (or `/auth/apple/login`) with `next` set back to the authorization request; `isSafeNext` accepts only a path into `/oauth/authorize?`, and `next` rides the provider round trip in the `auth_next` cookie (`SameSite=None`, for Apple's cross-site POST).

- **The AI Coach** (epic #314, tickets 4–5, #318 / #319; wire format `docs/specs/native/NS-58-ai-coach.md`; always "AI Coach" — a bare "coach" is a person, NS-38): `routes/aiCoach.ts` is `POST /api/ai/coach` and `POST /api/ai/coach/verify`, behind `requireSession` + **`requireEntitlement`** — POSTs that write nothing (an analysis request and a key check), so "no write route checks entitlement" holds, and both are enumerated in `test/api/entitlement-gates.test.ts`. **It is mounted by `index.ts` at `/api/ai`, not through `api.ts`'s list**, for two reasons that are both requirements: the AI Coach runs over your own logbook only, and `api.ts`'s list is also the coach mount and the tool layer's private copy (a student did not agree to their data going to their coach's AI provider — `/api/students/:id/ai/coach` is a 404 and a test asserts it, for a coach with a live grant); and `ai/tools.ts` imports `api.ts`, so the route cannot be in its import graph (the `itemSharePublic.ts` rule). The request names its provider and carries the driver's key in two headers, `X-TE-AI-Provider` (`anthropic` | `openai`) and `X-TE-AI-Key`; the body is `{ context, messages, model? }` and the server is stateless — the conversation lives on the client.

**The key is never at rest and never in a log**: `resolveCredential(c)` is the one place the headers are read (answering `{ kind: "key", provider, key }`; #503 adds `linked` and `oauth` there and nothing downstream reads a header), the key goes into the one outbound request, nothing in the route or the adapters logs a header or a caught error object, and a provider's error body is **mapped, never relayed** (OpenAI's 401 quotes part of the key back). The loop is `ai/coach.ts`: `startCoach` makes the first provider call *before* the route commits to a 200, so a rejected key or an outage is a plain `{ error }` with a status, and everything after is in-stream; it runs `TOOLS` from `ai/tools.ts` — all of them, unchanged, through `answerTool`, the same function the MCP server answers with — as the signed-in driver, capped at `MAX_TOOL_ROUNDS` (8, then one last request with tools forbidden so the driver gets what was found, ending `stop: "tool_limit"`) and `MAX_TOOL_CALLS` (24). **The CPU cost of a worst-case run has not been measured against the Workers limit**; do that before raising either. The stream is server-sent events — `text`, `tool`, `done`, `error`, plus a `: keepalive` comment every 15 s — and a write that fails because the client left ends the run, so an abandoned debrief stops spending the driver's tokens.

`ai/providers.ts` holds the adapters, each a thin layer over an injected `fetch` (no SDK): **Anthropic's Messages API** (streamed; assistant turns are appended as the content blocks they arrived as, thinking blocks and signatures included, which a tool loop requires; `output_config.effort: "medium"`, top-level `cache_control` so rounds two to eight read the tools and system prompt from cache, and `fallbacks: "default"` under the `server-side-fallback-2026-07-01` beta — a classifier refusal is retried by the API on another Claude model — except on Haiku, which has none) and **OpenAI's Responses API** (not chat completions: it is what a Sign in with ChatGPT token calls, so #503 reuses the adapter; `store: false`, with every output item of a round, reasoning items included, resent in order). **Models are the provider's own list, not an allow-list**: `verify` calls `Provider.listModels` — the provider's models API, one call that both proves the key and lists what the account can use — and Settings' model field completes from the answer. Anthropic's `GET /v1/models?limit=1000` carries a capability tree, so only models reporting adaptive thinking and `effort.medium` are offered (the request sends both); OpenAI's `GET /v1/models` has no capability field and lists embedding, speech, image and realtime models too, so chat models are told apart by name (`isOpenAIChatModel`), and a 403 there is a restricted key that works but may not list — it gets the built-in models rather than "rejected". `mergeModels` puts each `Provider`'s built-in `models` first (`claude-sonnet-5-5` and `gpt-6.2-astra` the defaults, both checked against the providers' docs on 2026-11-25), caps the answer at 60, and the built-ins are also the fallback. A request's `model` passes `acceptsModel` — a built-in id or anything shaped like that provider's chat model — so a hand-typed id works; the provider judges the rest, and a 400 on a model outside the built-ins is mapped to `424 the model <id> doesn't work with the AI Coach`. Because the model is no longer one of a known few, **request parameters that only some models take are sent by family, never by default**: `fallbacks` only for the families Anthropic documents it on (`anthropicHasFallback`). **`X-TE-AI-Provider: fake`** is a scripted provider — one tool call, a fixed reply — for the web tests, the native UI suites, the stream fixture and the guide captures, gated on `isDevHost` like every dev shortcut and `400 unknown AI provider` anywhere else. Provider failures map to `424` (`provider rejected the key`, out of credit, no access to the model — never our 401, which signs a client out), `429` (theirs, with their `Retry-After`) and `502`; our own limit is the `AI_COACH` binding, 10 a minute per user, `429` with `Retry-After: 60`. The system prompt is `ai/coach-prompt.ts`, reviewed like code: the MCP `INSTRUCTIONS`, then the coach's own rules, then a paragraph naming the entry point from `context`'s integer ids — nothing a user typed is interpolated. `contracts/golden/ai-coach-verify.json` pins verify; the stream is recorded to `contracts/streams/ai-coach.sse` by `contracts/generate.mjs` (and covered by `contracts:check`).

The logbook export carries them (`comments` per session, `comments_written` for a coach's own, by name and never by the other account's id), and `ai-tools.test.ts` asserts no MCP tool result does. **All three clients have it** (`android.md` and `ios.md` carry the phones' halves).

- `youtube/` — NS-46's server half that isn't a route. `google.ts` is Google: the token endpoint (`exchangeCode`, `refreshAccessToken`, whose `invalid_grant` marks the connection `revoked`), `revokeToken` (`invalid_token` counts as done), YouTube's resumable `initUpload` and `videoState` (`videos.list`), and `accessTokenFor` — the stored access token while it has five minutes left, else a refreshed one stored encrypted.

**Every call takes its `fetch`**: the routes pass the global one (stubbed by `fetchMock` in `vitest.workers.config.mts`, 200-only, since undici's mock can't compute a status from the request body), the step and the cron take it from their caller, which is how `test/api/youtube.test.ts`'s `FakeYouTube` scripts a resumable server. `step.ts` is the queue: `stepUpload` takes the row's **lease** in one conditional UPDATE (zero rows: gone, done, or another message has it — ack), and **every write after that is conditional on still holding it**, so a disconnect or a retry from the lap page mid-step is never overwritten. One thing per message — mint the session (after claiming the project budget in `youtube_daily`), or send one `YT_CHUNK_BYTES` (32 MiB) chunk read from R2 by range through a `FixedLengthStream` — and the next step is a new message.

**The offset is YouTube's** (`parseResumeRange` on the 308), never our sum; a 404/410 session restarts at most `MAX_RESTARTS` (2); a 5xx or transport failure probes with an empty `bytes */total` PUT and then retries (`message.retry`, backoff 30 s → 1 h, counting toward `max_retries` and the dead-letter queue, whose consumer fails the row in words); a spent budget, `quotaExceeded` or `uploadLimitExceeded` is `later` — a **new** message for Pacific midnight, capped at Queues' 12 h, so a wait doesn't burn retries. `youtubeQueue` is the Worker's `queue` export, telling the DLQ apart by `batch.queue`. `sweepYouTube` runs in the daily cron beside `sweepClips`: revocations (up to 200), expired tickets, the 30-day re-check at 25 days (a forced refresh per grant; `videos.list` per `done` upload — gone, or no usable grant, deletes the row and the lap offers the upload again; an unreadable answer leaves the grant as the thing re-checked), revoked connections deleted after 25 days, `uploading` rows stuck two days failed, and rows untouched for `STALE_STEP_MS` (13 h — longer than the longest wait, so a waiting row never gets a second message) re-sent.
