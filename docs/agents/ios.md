# iOS app (`apps/ios/`)

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

The app target is SwiftUI; all pure logic is in the `TrackEvolutionKit` package. Rules shared with Android and the web are in `clients.md`.

## Project and package

`apps/ios/` is a SwiftUI-lifecycle app (`App/`) plus a local SPM package `Packages/TrackEvolutionKit/` holding all pure logic — models, API client, recorder core, lap geometry, offline store — which **must never import UIKit or SwiftUI**; it builds for macOS as well as iOS, which is what lets `swift test` run the suite in seconds with no simulator. `TrackEvolution.xcodeproj` is generated from `project.yml` by XcodeGen *and committed* (a clean checkout, and CI, needs only Xcode), so project settings are changed in `project.yml` followed by `apps/ios/generate.sh` — never in Xcode's inspector, where the edit would be lost on the next generate; shared schemes XcodeGen can't express (the package's test scheme) live in `apps/ios/Schemes/` and are copied in by that script.

**`apps/ios/Packages/TrackEvolutionKit/Package.resolved` is the app's resolved file, not just the Kit's**: it pins `firebase-ios-sdk` and its tree beside GRDB, and Xcode Cloud resolves with automatic resolution disabled, so it builds from exactly that file. `swift test` in the Kit rewrites it with the Kit's dependencies alone — revert that drift, never commit it (doing so broke every Xcode Cloud archive after NS-45); `ios.yml` runs the strict resolve in its `app` job, on a checkout `swift test` never touches (the Kit's tests are the separate `kit` job), so a stripped file fails the PR. Load-bearing: bundle id `app.trackevolution` (kept from the retired shell so the native build shipped as an in-place App Store update, preserving ratings and the Universal Links association — Xcode Cloud archives *this* project, and `MARKETING_VERSION` in `project.yml` is the shipping one), deployment target iOS 17, Swift 6 language mode with complete concurrency checking, and `com.apple.developer.carplay-driving-task` **is** checked in (Apple has granted it) — dropping the key fails no build and no test, it just makes the CarPlay scene stop attaching, so CI asserts its presence and lints every entitlements file. CarPlay itself is `App/CarPlay/`: a single-template `CPTemplateApplicationScene` driving the *same* recorder the phone UI does, reachable from UIKit via `AppServices`, with the event-attachment rule ported into the Kit's `RemoteRecording` and pinned against the web implementation by `contracts/logic/remote-attach.json`. 

## Screens and features

The iOS logbook lives in `App/Screens/` (one `@Observable` model per screen owning its data and writes; the views are layout, and nothing bypasses `APIClient`, which *is* the offline layer — so there is no separate offline path to forget to test) with the typed `NavigationStack` path in `App/Navigation/Router.swift` and deep-link parsing in the Kit's `DeepLink` (pure, so the routing table is unit-tested: `/share/<slug>` — the only pattern `src/routes/wellKnown.ts` advertises — opens the read-only shared logbook, and `trackevolution://auth?code=` is deliberately **not** a route, since `ASWebAuthenticationSession` consumes it and racing it would burn the one-time code).

**A lap opens** (#267): every lap row on the event page is a `Button` pushing `Route.lap(eventId:sessionId:lapId:)` — `App/Screens/LapDetailScreen.swift`, whose pure `Detail` (`build` / `subtitle` / `comparePreselect`, pinned by `Tests/LapDetailTests.swift`) carves the lap's own channel entry into a one-entry `SessionChannels` for `LapChannelPanel`, gives the racing line only to the lap the session's trace was drawn from (the best — `sessions.trace` is one polyline per session, so any other lap would be drawn on a line it never took), and opens the session's overlay as a sheet off its own *Compare laps* button with this lap lit beside the best; the event page's overlay control reads *Compare laps* now too. The route carries three ids that can each be temp, and `remapTempIds` follows each of them. Screens are exercised end to end by `UITests/CoreScreensUITests`, `UITests/ChannelGraphsUITests`, `UITests/GarageUITests`, `UITests/VideoImportUITests`, `UITests/ChecklistTemplateUITests` and `UITests/TwoPaneUITests` (the two-pane shell at both widths, NS-34 ticket 2) against `npm run dev` (skipped when absent, so CI stays green; a second checkout whose `wrangler dev` landed on 8788 points them at it with `TEST_RUNNER_TE_DEV_SERVER=…` in xcodebuild's *environment* — a `KEY=VALUE` argument is a build setting and is silently ignored); they attach screenshots on success because the charts, trackmap and wear bars are drawn rather than laid out and a bad render fails no assertion, and they delete the data they create because the dev logbook is shared between tests.

**They get their session from `-authToken`, not from the browser**: `devSessionToken()` in `DevServerSignIn` performs the app's own PKCE exchange over HTTP against the `DEV_MODE` bypass — `GET /auth/login?client=app&code_challenge=…` then `POST /auth/exchange` — and hands the app a real token through a DEBUG-only launch argument. The token is as real as any other and the PKCE check still runs; what is skipped is `ASWebAuthenticationSession`, a system service these suites never meant to exercise and which takes the app down with an XPC fault inside BoardServices on some machines, leaving every screen test unrunnable for reasons unrelated to the screens. `SignInUITests` still drives the real browser flow, so that coverage moved rather than vanished. The example seed's last event is dated **relative to today** for the same class of reason: written as a literal it stopped being upcoming the day it passed, quietly taking the dashboard's hero-slot assertion with it. The channel panel is tabs on every client since #188. It is Traces / Grip / Car since the feedback merge, Traces being what Time and Inputs were, with the distance-or-time axis switch and the cursor's per-lap map dots from `LapAxis` on all three clients. On the phones the cursor parks on a tap and is borrowed by a pointer (the `Mark` / `PanelPointer` rule). It is kept with the axis in `PanelMemory` on iOS and in `rememberSaveable` on Android, where a restored tab name that no longer exists (`TIME`, `INPUTS`) falls back to the first populated tab. Its dots go to the expanded-width `AnalysisColumn`'s map, or to the page's own map through `onCursor`. Only a panel with no map beside it draws its own small one at the top of Traces, from the `mapTrace` / `trace` argument, and unlike the web's it is not pinned while the charts scroll. Android's `LapAxis.gridAtElapsed` is `VideoSync`'s, as the JS imports it. On both phones every page with a lap stage (lap page, session compare, the compares, the leaderboard lap) leaves the cursor off, because a tap there seeks the stage and the stage's map is the place: Android's panel keys it on `onSeek` (`cursorEnabled`), turns a time-axis tap into side A's grid index through `LapPlayhead.aLap`, and draws the playhead in each plot's draw phase over the canvas the cursor is drawn in, while `TrackMap` takes the cursor as `dots` and the stage's cars as the draw-phase `liveDots`. iOS's `AxisMarkLayer` draws both the cursor and the stage playhead in `.chartOverlay`. The Car tab carries the per-lap scalars (#190). The three analyses that ride on it are `Gears`, `Limits` and `Grip` in the Kit and `:core`, ports of `public/js/gears.js`, `limits.js` and `grip.js` pinned by `contracts/logic/gears.json`, `limits.json` and `grip.json`: a **gear ribbon** under the RPM trace (`GearRibbon`, hand-rolled on a canvas on both phones — a run of one gear is a filled rectangle with a label in it, which is a bar chart of nothing), a per-gear **upshift table** (`ShiftTable`), **limit bands** shaded behind the brake / throttle / steering traces, **limit marks** on the best-lap track map with a legend under it (`LimitLegend`), the limit count on the session stats line, and — on the Grip tab — the **friction circle** (`FrictionCircle`), a square scatter of `latG` against `longG` with the 99th-percentile reference arc and the quadrant read-out under it. That one is hand-rolled on a canvas on both phones for the same reason the ribbon is, plus two of its own: the plot area is forced square (a circle drawn as an ellipse makes the reading wrong) and **braking plots up**, against the sign of the stored `longG`, which on a canvas whose y already grows downward means the JS mapping ports across unchanged — "fixing" the sign draws the chart upside down and fails no test. The **Car tab** is filled on both phones too by `HealthStrip` (#190): a card per stored per-lap scalar with the session's figure by that channel's own rule, the rule word under it, and a sparkline whose threshold bands shade in the garage's wear colours — plus the cross-corner tire spread and the fuel outlook. Two layout calls differ from the web and are stated in both ports: the per-lap table is **absent** (fifteen columns is a desk layout; the sparkline carries the shape) and the cards go two to a row. Under the friction circle on the Grip tab sits the **balance scatter** with its per-corner table (`BalanceScatter`, #189): rotation per metre against steering angle, a dashed line for this car's typical response (`Balance.balanceReference`, whose K the points are corrected by — never the bare `referenceGain`, which reads corner speed), and a row per corner reading each highlighted lap and the session. Its two drawing rules are the friction circle's read the other way and are stated in both ports: the plot is deliberately **not square**, because the axes carry different units, and its y is **subtracted**, so more rotation is up and oversteer sits above the line; on a phone the corner's place on track and its peak G ride under its label rather than in columns of their own, which is what keeps the table inside the width. The `yaw` trace joined both clients' channel enums with it. On iOS the bands go in `.chartBackground` rather than in the chart builder, because a `RectangleMark` beside the lines breaks the one-homogeneous-`ForEach` rule below.

**The setup notebook is native on iOS too** (NS-40, `App/Screens/SetupNotebook.swift`, `SetupFormScreen.swift`): `SetupNotebookCard` sits above the sessions on the event page, **collapsed by default** as the web's `<details>` is (one `.plain` toggle row saying `SetupNotebook.summary`, the web's summary line; the open flag is `EventScreen`'s `@State`) — a row per event day, its sheet in the driver's units, values changed since `Garage.previousSheet` set in the accent *and* said as "changed from …", the part names from `/garage` (read by `EventModel.loadGarage`, its failure swallowed) — locked in place with `ProUpsellCard` for a free account and absent for a coach, with the **pressure loop** under it from the latest session that recorded tire pressures (`SetupNotebook.loopSession` / `defaultLoopDay`, both named accessibility actions). The form is `Route.setupForm(eventId:day:startFrom:)`, a **pushed page, never a sheet** (the event page already carries two `.sheet`s), whose draft is the typed text per flat key on `AppRouter.heldFields` with a `_hydrated` key for the event form's rule; it starts from a held draft, else `startFrom` (the loop's next-day sheet), else the day's sheet, else `APIClient.setupPrefill`, else `Garage.previousSheet` over the cached event, and saves through the queueable `putSetup` / `deleteSetup`. `analyticsPath` is `/event/:id/setup/:day` and `remapTempIds` follows its event id. The event page re-reads on `.onAppear` when it already has a detail, which is how it shows what a pushed form wrote. `EventFormScreen` carries the four cost line items behind a *What it cost* disclosure (`EventFormModel.costs` by column, held in `EventFormDraft.costs`), the event page a *Cost* tile and breakdown, the track page a Pro *"$N spent"* line (`SetupNotebook.spentLine`) and the car page a *Track-day spend* tile; `SessionPatch` is a pair of `Patch<String>`s and the session edit sends only what changed (`EventModel.sessionPatch`). Pinned by `SetupsTests` / `CostsTests` in the Kit and `Tests/SetupNotebookTests.swift`.

**Season Wrapped is native** (NS-36, `App/Screens/WrappedScreen.swift`, `Route.wrapped(year:)`): the port of the web story over `APIClient.wrapped(year:)`, with the card rules and the poster's words from the Kit's `WrappedStory`. It is the third route that **owns the window** — a story is full-screen at every width — and the dashboard's November banner calls `presentFullWindow` directly rather than `openFromList`, so it is a cover on a phone too and the cover's Back is the way out. Navigation is the thirds, a horizontal swipe, the arrow buttons (← / → on a keyboard) and the progress segments, with VoiceOver's adjustable action and a screen-changed announcement; Reduce Motion makes the slide a cut. The share image is `WrappedPosterImage` through `ImageRenderer` at scale 1 (1080×1920 and 1200×630), rendered when the poster card appears and handed to `ShareLink`, so the story presents nothing of its own and the system sheet supplies Save Image. `-wrapped` (plus `-wrappedPro`) opens it on a sample season with no server.

**Share with a coach is native** (NS-38 ticket 3, `App/Screens/Coaching/`): `CoachingScreen` (Settings → *Open Coaching*, `Route.coaching`) carries *Your students* with *Stop coaching*, the Pro-gated invite (the link shown once with Copy, `ShareLink` and a `CIQRCodeGenerator` QR code; `ProUpsellCard` for free), open invites with Withdraw, the coaches with `lastViewedText` and Remove, and the profile card; `ProfileFormScreen` (`Route.profile`) is built from the Kit's `DriverProfile.PROFILE_GROUPS`, each yes/no a three-way picker, its typing held on the router; `CoachInviteScreen` (`Route.coachInvite(token:)`, from the Kit's `DeepLink.coachInvite` — parked across a sign-in like any link) previews the invite and words the used/expired/own/already-coach cases. A student is `Route.student(id:page:)`, always pushed on the **Events** stack (`AppRouter.openStudent`), and `StudentLogbook` re-reads their `/me/profile` under the mount on every page: that gives the **`LogbookOwner`** (in the Kit: `.me` / `.student(id, name, pro)`) it sets as the `\.logbookOwner` environment value, and a 404 there calls `APIClient.forgetStudent` (the Kit's `OfflineStore.removeCachedPrefix`) and says the logbook is no longer shared. The owner's `EventScreen`, `TrackScreen`, `LapDetailScreen`, `CompareLapsScreen`, `AnalysisColumn` and `VehicleScreen` are reused under it: their models read through `auth.api.scoped(to: owner)` — which prefixes `/students/<id>` and throws `APIError.readOnly` on any write before a request is built, so nothing under the prefix is sent or queued — every write control, the recorder/import doors and drop target, the checklist, course notes, goal, leaderboard, share link and the vehicle page's `/garage` half hide on `owner.isReadOnly`, links go through `owner.link(_:)` (`TENavCard` does it for every card), and the channel panel's `pro` is `owner.canViewChannels(viewer:)` — **the student's tier** — with the panel saying `studentFreeNote` rather than showing the upsell for a free student. `StudentHomeScreen` is the student's small dashboard. The pure halves are ported as `Coaching.studentLine` / `lastViewedText` / `inviteExpiryText` and `DriverProfile.PROFILE_GROUPS` / `profileSections` / `profileBody`, pinned by `contracts/logic/coaching.json` (`CoachingTests`); `UITests/CoachingUITests` covers both halves, the coach's with a second account's token (`TEST_RUNNER_TE_COACH_TOKEN`, minting it is in the file), and DEBUG `-openLink <url>` hands the app a link as the OS would.

**The leaderboard is its own screen**, `App/Screens/LeaderboardScreen.swift` (`Route.leaderboard(trackId:)`, pushed from the track page's *Leaderboard* button, shown for every catalog track), not a section of the track page — the port of `viewLeaderboard`, carrying the board, the "why isn't my best ranked" note and the opt-in controls.

**Opening a leaderboard lap** (NS-35) is `App/Screens/LeaderboardLapScreen.swift`, the port of `viewLeaderboardLap` — their ranked lap and the viewer's own best at the track, through `CompareLaps.alignLapPair` into the same `LapChannelPanel` the two-lap compare uses. It is a **sheet at every width**, presented from the leaderboard screen — that screen's one `.sheet`, as the compare is the track screen's, because two `.sheet` modifiers on one view is the watchdog crash listed among the SwiftUI hazards below. The lap overlay (NS-23) is `App/Charts/LapChannelChart.swift` — the port of `public/js/channel-graphs.js`: every lap of an imported session on one driven-distance axis, three highlight slots, best lap pre-selected, chips as the legend, with the matching and axis maths in the Kit's `ChannelGraphs` (pinned against the JS by `contracts/logic/channels.json`). It opens as a **sheet** from the event page rather than expanding in place, which is not only a layout preference: a Swift Charts chart of that many marks inside a `List` row never settles. Two more Swift Charts traps are documented where they bite — accessibility must be suppressed *per mark* (Charts publishes an element for every one, and a snapshot of that hierarchy never returns, which kills VoiceOver and every UI test), and the chart builder must stay one homogeneous `ForEach` (a `RuleMark` or an `if` beside it wedges layout, so the read-out's rule is a two-point line in the same data). Since `sessions.channels` is written only by the web importer, `-channelGraphs` launches the panel on synthetic data and `UITests/ChannelGraphsUITests` seeds a session over the dev API.

**Video telemetry import is native** (NS-30, `App/Import/` + the Kit's `Telemetry/`): `PDR.swift`, `PDR25.swift`, `GPMF.swift`, `Series.swift`, `LapChannels.swift` and `PDRLaps.swift` are line-for-line ports of `public/pdr.js`, `js/import/pdr25.js`, `js/import/gpmf.js`, `series()`, `channels.js` and `pdr-laps.js`, reading through a `TelemetryByteSource` (`ByteSource.swift`) so the Kit knows nothing about `URL`, Photos or security scopes and `swift test` runs them on macOS. `Telemetry.swift` is the dispatch (`parse.js`) plus the non-DOM half of `js/import/ui.js` — `applyGate`, `metricsSummary`, `estimatedNote` — so a phone import writes the same session, notes included, the browser would (the notes are the source and the estimate caveat; the top speed / max RPM / max G line is the review's preview only, since 2026-11; sessions imported before then keep it in their notes).

**Video and `.vbo` are ported** (`VBO.swift`, the port of `vbo.js`, since 2026-09): the rest of the long tail stays web-only, and `docs/specs/native/README.md` records why that line moved twice. Correctness is pinned, not eyeballed: `contracts/logic/video/*.mp4` are the *committed synthetic MP4s* from `test/fixtures/build.mjs` and `contracts/logic/video-parsers.json` is the JS parsers' output over them, which `VideoContractTests` asserts equality against — lap times to the millisecond, coordinates to 1e-9, channel arrays element for element. Two things about the app half are load-bearing: **the video is never copied** (the no-copy paths are `.fileImporter`'s security-scoped URL and `PHAsset` → `requestAVAsset` → `AVURLAsset.url`; `PhotosPicker`'s `loadTransferable` materialises the whole clip and is why `PHPickerConfiguration(photoLibrary:)` plus an `NSPhotoLibraryUsageDescription` is worth the permission prompt), and the parse runs off the main actor in one task with the `FileHandle` confined to it, checking `Task.isCancelled` between samples. `ReviewScreen` is now shared by the recorder and the importer — its input generalised from `ParsedRecording` to `ParsedTelemetry`, with the checkpoint/discard behaviour behind an optional recorder — which is also how a *recorded* session finally stores per-lap channels, since `buildLapChannels` now exists natively. `UITests/VideoImportUITests` runs a committed fixture clip end to end via the debug-only `-importFixture` launch argument, because the system Files and Photos pickers are other processes and automating them would make the suite flaky about the wrong thing. The prep **checklist template** is native too: `AuthController` owns it (`checklistTemplate`, `setChecklistTemplate`) so the Settings editor and the event page's "Use my list" button read one value rather than two copies, and `EventDates.DEFAULT_CHECKLIST` is pinned to `public/js/checklist.js` by `contracts/logic/checklist.json`. Editing the template never rewrites a checklist already on an event — those are snapshots, and rewriting one would untick what the driver had already done.

**Billing is native too** (NS-32 phase B, `App/Billing/`): `StoreController` is StoreKit 2 — `Product.products(for:)` over `Entitlement.APPLE_PRODUCT_IDS`, `purchase()`, `AppStore.sync()` behind the mandatory Restore Purchases control, `AppStore.showManageSubscriptions` for Manage — and a `Transaction.updates` listener started from `TrackEvolutionApp.init` (never a view's `.task`) so it outlives every view. Three rules there are load-bearing: **every verified transaction — purchase, renewal, restore, `Transaction.unfinished` at launch — is posted to `POST /api/billing/apple` (with `renewal_jws` from `Transaction.subscriptionStatus` when there is one) and `finish()`ed only after the server's 200**, because a finished transaction is never redelivered and a failed post would be the last anyone heard of it (a 400/409 *is* finished, since neither changes on retry, and the server's reason is shown); **a transaction with no signed-in user is held and posted after sign-in**, never dropped (`withObservationTracking` over `auth.state`, plus a retry on foreground); and **nothing in the app decides tier** — the entitlement each billing route returns is written into `AuthController.me` and read through the Kit's predicates. Grandfathering is `AppTransaction.shared` on launch: an install whose `originalAppVersion` is a paid one posts the JWS to `/api/billing/apple/legacy` **once per account per server** (`LegacyClaimRecord`, a `UserDefaults` flag; a 409 or 400 also counts as done, and Restore re-runs it past the flag) and is skipped outright in the Xcode StoreKit environment, whose signatures the Worker can't verify. **The cutoff is `Entitlement.APPLE_FIRST_SUBSCRIPTION_BUILD: String? = nil`, mirroring the Worker's unset `APPLE_FIRST_SUBSCRIPTION_BUILD`**: nil means "the app is still a paid download, so every install bought it" — true through phases B and C — and it cannot be filled in earlier because the build number is Xcode Cloud's, not `CURRENT_PROJECT_VERSION`'s; phase D sets both from the first free build's number (`compareVersions` is ported from `src/routes/billing.ts` so app and server draw the line identically). The Kit side is `Billing/EntitlementRules.swift` — the port of `public/js/entitlement.js` under the same names (`isPro`, `canRecord`, `canViewChannels`, `canUseGarage`, `canUseSetups`, `canViewYearInReview`, `manageUrl`, `entitlementSummary`), pinned to `contracts/logic/entitlement.json` by `EntitlementTests`, which also pins `apps/ios/Configuration.storekit` (one group "Track Evolution Pro", the two products, P1M/P1Y, a P2W free trial) to the Kit's product ids — plus `ProGate.decide(_:entitlement:gatesEnabled:)`, the recorder-start decision behind **`Entitlement.gatesEnabled`, `true` since phase D** (import is free, so `.record` is the only `Feature`): the record screen's Start and CarPlay's `RemoteRecorder` (a `.pro` refusal, since a head unit can't show a sheet) consult it against the *cached* entitlement — `ImportScreen` no longer does, since importing is free, so a driver who was Pro at the last sync records with no signal, and the tests cover both states with the constant injected. `APIError.proRequired` is the 402 case, distinct the way 401 is, so a gated read can show the paywall rather than the sync banner. `PaywallSheet` (guideline 3.1.2: title, term, `displayPrice`, renewal wording, Restore, privacy + terms links) always hangs off a *button* — the record screen and Settings each already present a modal, and two presentations on one view is the hazard above. The `.storekit` file is referenced from the scheme's run action in `project.yml` (`storeKitConfiguration`) and listed under `fileGroups`; Xcode-signed transactions are rejected by the Worker with 400 on purpose, so the server round trip is tested in sandbox, not locally. The **garage is native** (`App/Screens/VehicleScreen.swift` + the Kit's `Garage.swift`, spec NS-29): the wear math is *not* ported — `GET /api/garage` arrives with each part's estimate already computed by `src/lib/wear.ts`, and the client only decides how to say it, with the due/low thresholds and the "≈2 track days" phrasing pinned against the web implementation by `contracts/logic/garage-status.json`. Its writes stay off the offline queue on purpose (retiring a part rewrites its neighbours' wear; a new part's expected life is defaulted server-side; a refresh is a retire-plus-create whose successor id the client can't invent), so the garage is readable offline and not writable, and the dashboard fetches `/garage` independently of everything else and swallows its failure.

**The garage is its own tab since NS-37**: the signed-in shell is a `TabView` of *Events* and *Garage* (`RootView.signedIn`), each tab holding the NS-34 shell — its own `NavigationStack`, or its own `NavigationSplitView` at expanded width with `GarageDetailPlaceholder` ("Pick a car") as the garage's empty detail — and the recording and sync banners are insets on **each tab's content** rather than on the `TabView`, where they would sit under the tab bar. `AppRouter` keeps one path per tab (`eventsPath`, `garagePath`; `path` is the visible tab's) and `Route.tab` says where a route lives when it is *opened* — `show`, a deep link, the list pane switch tab, `.vehicle` to the Garage, `.settings` to neither — while a *push* never changes tab, so an event page's car link keeps Back on the event; `remapTempIds` walks both stacks. `GarageScreen` is the free list: `/vehicles` + the cached `/events` (the Kit's `Garage.vehicleLogbook` / `vehicleTileLine`, pinned by `contracts/logic/garage-logbook.json`) for every account, `/garage` beside them with a 402 locking the Pro half in place (`ProUpsellCard`), and a *+ Add car* tile presenting `AddCarSheet` with `CatalogCarPicker` — Settings' vehicle section is gone. `VehicleScreen` is free the same way — `VehicleModel` loads the car from `/vehicles` and only its Pro half from `/garage`, so a 402 no longer makes the whole page `.paywall` — and carries *Delete car*, on its own button's dialog. The dashboard lost its garage cards and strip for one `heroGarage` line under the next-event hero, and the tab's `.badge` is `router.garageAlertCount`, written by whichever screen last read `/garage`. Three more SwiftUI hazards it shook out, each of which kills the app with a watchdog "lost connection" rather than a stack trace, so none of them is cheap to rediscover: **one modal presentation per view** (two `.sheet` modifiers on one view), **no `.fixedSize()` on a button whose style already sets `frame(maxWidth: .infinity)`**, and **name `.datePickerStyle(.compact)` explicitly** on any `DatePicker` inside a scrolling sheet. UI tests also want the simulator's hardware keyboard connected and the destination pinned by id — see `apps/ios/README.md`. 

**Sharing one lap, or two laps compared, on iOS** (NS-56, `docs/specs/native/NS-56-share-lap-compare.md`): the Kit's `ItemShareKind` gains `lap` (`l`) and `compare` (`c`), and what the owner shares is an `ItemShareTarget` — `.event` / `.session` / `.lap(id)` / `.compare(a:b:)`, ordered, whose `ownerPath` is the route (`/laps/:id/share`, `/laps/:id/compare/:otherId/share`) and whose `hasTempId` is why a lap not yet synced offers nothing — taken by `APIClient.createItemShare` / `itemShare` / `deleteItemShare` (live, never queued, refused unsent on a student's client; `ItemShareAPITests`). `SharedItem` gains `lapId`, and a comparison decodes as `SharedCompare` (`a`, `b`: `SharedLapSide`, each a lap link's payload) through `sharedCompare(token:)`, public and past the cache like `sharedItem`; `DeepLink.sharedItem` parses both letters with no new case, and `Route.sharedItem(kind: .compare, …)` is sent to `SharedCompareScreen` by `RootView` (analytics `/share/l/:token`, `/share/c/:token`). *Share…* is in the lap page's toolbar (the lap), the session compare's toolbar (the first two lit laps, first lit = A, disabled under two) and under the track compare's pickers (the picked pair, whose ids `CompareLapsModel.shareTarget` finds the way it finds a pick's clip) — each that view's **one** `.sheet`, `ItemShareSheet(target:)`, the stage's full-bleed cover staying `LapStageView`'s own; hidden for a coach and for a temp id, and each pauses the stage first. A lap link is `SharedItemScreen` with one *Lap time* tile; a comparison is `SharedCompareScreen` (in `SharedItemScreen.swift`): the two sides and their times, then — for a Pro owner whose laps stored telemetry — the lap stage with both videos over the link's signed URLs, `CompareHeadToHead` (the track compare's table, extracted so both draw one) and the channel panel over `CompareLaps.alignLapPair`; a free owner's link shows the two times and `ItemShareText.compareFreeNote`, never an upsell, and laps with no telemetry their times, a sentence and each lap's video. The words are `ItemShareText`, NS-56's own; `Tests/ItemShareTests.swift` pins them and the three share-target rules. No UI test covers the new *Share…* controls or `SharedCompareScreen`.

**Coach-comment notifications on iOS** (NS-54 ticket 2, `docs/specs/native/NS-54-comment-push.md`): `App/Push/PushController.swift`, on `AppServices.push` and in the environment, is the phone's half of the server's FCM sender. Four rules there are load-bearing.

**Firebase is configured only where `AppAnalytics` configures it** (`AppAnalytics.firebaseStarted`: a release build, or a debug run with `-FIRDebugEnabled`), so the simulator, an ordinary debug run and every UI suite register nothing, ask nothing and draw no toggle — the push half is checked on a real device, never in CI.

**Swizzling is off** (`FirebaseAppDelegateProxyEnabled` and `FirebaseMessagingAutoInitEnabled` false in Info.plist): `AppDelegate.didRegisterForRemoteNotificationsWithDeviceToken` hands Messaging the APNs token, and auto-init is switched on only once the user has said yes, so no token exists before then.

**A registration belongs to the session server-side**, so the controller only re-sends `PUT /push/device` (`APIClient.registerPushDevice`, live, off the queue) on arrival into the signed-in state and on a new token; signing out needs no call.

**The ask is in context, never on launch**: `PushAskCard` under an open comment thread (`CommentsModel.asksForPush` — an owner's once their coach has spoken, a coach's once they have), *Not now* remembered per install (`push.comments.asked`); Settings → Coaching carries *Comment notifications* (`push.comments.enabled`, off = `DELETE /push/device`), which opens iOS's notification settings when iOS has said no. A tap goes `UNUserNotificationCenterDelegate` → the Kit's `DeepLink.commentPush` (the table Android's `:core` shares, pinned by `PushTests`) → `PushController.tappedLink` → `RootView` → `AppRouter.open(_:signedIn:)`, which parks it across a sign-in like a Universal Link; `AppRouter.commentRoute` is the lap, else the event, in a student's logbook through `LogbookOwner.link` when the data names one (`Tests/CommentPushTests.swift`). The badge mirrors `AuthController.commentsUnread`, refreshed from `/me` on every foreground. `aps-environment` is `$(APS_ENVIRONMENT)`, development / production per configuration in `project.yml`.

**The lap stage on iOS** (NS-51 ticket 2, `docs/specs/native/NS-51-video-synced-laps.md`): the Kit's `Analysis/VideoSync.swift` is the port of `public/js/video-sync.js` under the same names (the spec's extra exports included), pinned by `contracts/logic/video-sync.json` in `VideoSyncTests`, which also carries the JS cases. ## iPhone Duo and the Mac

**The iPhone Duo** (epic #277 — the epic is the spec): Apple's foldable lands in classes the app already ships — closed is compact (466pt, the widest compact window it has met), open portrait medium, open landscape expanded — so nothing about layout asks "is this a Duo". Two things are new.

**Typed state lives above the shell swap**: rotating the open Duo (like an iPad mini, 744 → 1133pt) crosses 840pt, and `RootView` swapping the stack shell for the split shell drops every screen's `@State`, so the event form's whole draft is `AppRouter.eventFormDraft` (`EventFormDraft`, with Android's `hydrated` rule — a load finishing after a restore never writes a field, and a restored edit form does not refetch) and the short typed fields on other pages — the event page's hand-entered session, lap append and checklist item, a part's measurement, Settings' checklist item — are `AppRouter.heldFields`, keyed by route. Both are dropped the moment their route leaves both stacks, which is what "discard" means for a form without a Cancel; the router rather than `@SceneStorage` because a draft carries `Encodable`-only staged sessions and the bug is a resize, not a kill. What still resets re-fetches or re-derives, and an open sheet is dismissed with its presenter. Pinned by `apps/ios/Tests/EventFormDraftTests.swift` and `TwoPaneUITests.testAHalfTypedEventSurvivesARotationAcrossTheBreakpoint`, which needs an iPad mini (or Duo) because its orientations must straddle 840.

**The tabletop recorder is ported**: `apps/ios/App/DesignSystem/FoldPosture.swift` is `FoldPosture.kt` under the same names (`Folds.geometry`, `HINGE_LIMIT`, plus `geometry(division:in:)`, the reduction from iOS 27.1's `reservedRegions(kind: .division)` — the layout signal; the hinge angle is for effects), published as `\.foldGeometry` by `publishingFoldGeometry()` on the record route only, and read by `RecordingScreen`'s `fold` parameter (defaulted from the environment — the test seam). Tabletop, while live, is timing above the crease and attachment / fix card / warnings / Start–Stop below, split at `Folds.tabletopTopShare`; stopped and recovered recordings keep the phone layout. The division read is `proxy.reservedRegions(kind: .division)`, behind `#available(iOS 27.1, *)` for the device **and** `#if canImport(SwiftUI, _version: 8.0.85)` for the SDK — Xcode 27.0 and 27.1 ship the same Swift compiler, so the module version is what tells them apart — which means a build on Xcode 27.0 (CI, until ticket 2) still compiles and answers flat everywhere, and **a release archived on 27.0 ships without the posture** and no test notices: Xcode Cloud has to archive on 27.1; `-tabletop <fraction>` (DEBUG) forces the posture for a look on any simulator. Pinned by `apps/ios/Tests/FoldsTests.swift`, which carries `FoldsTest.kt`'s cases.

**The listing's screenshots** are `UITests/AppStoreScreenshotsUITests`: the screens behind a tap (leaderboard, two-lap compare, lap detail, friction circle), filmed against the promo's demo logbook and skipped unless `TEST_RUNNER_TE_SHOT_TOKEN` is in xcodebuild's environment; it captures whichever display the app's window fills, because on the Duo `XCUIScreen.main` is the cover display, dark while the phone is open. The deep-linkable screens need no test (`-openLink` plus `simctl io <device> screenshot --display=<id>`). `simctl` has no fold control — the pose is set by hand in Xcode 27.1's Device Hub — and `simctl location start` advances **one waypoint per update** whatever `--speed` says, so a simulated drive's pace is set by the waypoint spacing.

**The Mac** (epic #230): the iPad build is offered on Apple silicon Macs as a *Designed for iPad* app — no new target, no Catalyst (`SUPPORTS_MACCATALYST: NO` stays in `project.yml`), the same bundle id, App Store record and Pro subscription, and no second archive; it is an App Store Connect availability toggle, not a build. A Mac window is expanded width, so the NS-34 split shell is what a Mac user sees, and sign-in, StoreKit, the `.fileImporter` no-copy path (Finder there), Photos, the offline store and Universal Links all run unchanged. The one code rule is that **the recorder is hidden on the Mac**: a Mac has Wi-Fi location and no GPS, so a recording made there is noise, and the record screen is a phone-in-a-mount layout that makes no sense in a window. The value is `Platform.runsOnMac` in `apps/ios/App/DesignSystem/Platform.swift`, read once from `ProcessInfo.isiOSAppOnMac` — **never `userInterfaceIdiom`**, which reports iPad there, and **never window width**, which is NS-34's job and would also hide the recorder on a 13-inch iPad, where NS-34 keeps the route reachable. It lives in the app target beside `LayoutClass` because it is a fact about the process and the Kit forbids app-framework reads; like the breakpoints, the decisions on it are pure and pinned by `apps/ios/Tests/PlatformTests.swift` for both values, since no CI job runs the app as *My Mac (Designed for iPad)*. Three doors close through it: the dashboard's + menu has no *Record laps* item (`dashboardOffersRecorder`, which also carries the idle-recorder rule the button always had, so neither can be forgotten by the other), the event page's *Add a session* card puts a record-on-your-iPhone sentence in the recorder's slot (`eventPageOffersRecorder`; import stays, since Finder is a better import door than a phone), and `AppRouter` resolves every `.record` route through `Route.resolved(runsOnMac:)` on push, show and present — to the event it was for, or the dashboard when it had none — so a stale path, the banner's sheet or a door this list missed cannot reach `RecordingScreen` either. `RecordingBanner` is deliberately unguarded: a recording only exists from a Start on this device, and every Start is gone. CarPlay is untouched (the scene never attaches on a Mac). Web-only stays web-only there, on NS-34's rule — a desk-sized native client is the standing *argument* for revisiting that list in `docs/specs/native/README.md`, not the change — and a native macOS target is the follow-on if the Mac earns one.
