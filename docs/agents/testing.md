# Tests

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

**Tests** (`test/`, Vitest with two projects — see `vitest.config.mts`):
- `test/unit/` — pure-function tests running in Node: `src/lib/*` plus the frontend modules (`public/js/format.js`, `chart.js`) and `pdr.js` internals.
- `test/api/` — the whole Worker under `@cloudflare/vitest-pool-workers`: real D1 with migrations applied per test (`setup.ts`), requests via `SELF.fetch`. `helpers.ts` creates users/sessions directly in D1 so multi-user ownership isolation is testable; DEV_MODE bindings live in `vitest.workers.config.mts`.
- New API behavior needs a test here; new pure logic belongs in `src/lib`/`public/js` where it's unit-testable.
- YouTube (NS-46) is `test/api/youtube.test.ts`: the connect routes over `fetchMock` (the token endpoint echoes an authorization code that is base64url JSON of the id_token payload, like the Apple mock), and the queue step, the handler (`createMessageBatch` / `getQueueResult`) and the cron over `FakeYouTube`, a scripted resumable server injected as `fetch`. The test pool points `YOUTUBE_QUEUE` at a queue nothing consumes (`queueProducers` in `vitest.workers.config.mts`), so a POST never races a consumer; the tests step uploads themselves, in 256 KiB chunks. One test walks every D1 table for a plaintext token.
- The MCP work is tested in three layers: `ai-tools.test.ts` calls the tools directly (shape, reach, ownership, size bounds) over sessions built by `telemetry-fixture.ts` — a synthetic lap with corners, braking zones, shifts, an ABS pulse and wheelspin, so every analysis finds something; `mcp.test.ts` is the transport and the token/session boundary, with tokens minted in D1 by `mcpTokenFor` in `helpers.ts`; `oauth.test.ts` walks the whole authorization flow by hand, consent form included (the client-ID metadata documents it fetches are `fetchMock` interceptors on `assistant.example`).
- Billing (`test/api/billing.test.ts`, `test/unit/billing-jws.test.ts`, `test/unit/entitlement.test.ts`) signs Apple-shaped payloads with the synthetic chain in `test/fixtures/billing/` (root → WWDR-marked intermediate → receipt-signing leaf, plus a wrong-root chain and an OID-less leaf; regenerate with `build.sh`, keys are PKCS#8). The Worker trusts that root only under `DEV_MODE` via `APPLE_IAP_TEST_ROOT_PEM`. The App Store Server API, Play Developer API, Google token endpoint and Google JWKS are `fetchMock` interceptors in `vitest.workers.config.mts`, driven by the id/token in the request path (contracts in `test/billing-helpers.ts`); workerd has no filesystem, so the PEMs reach the API tests as bindings. Stripe (`test/api/billing-stripe.test.ts`, `test/unit/stripe.test.ts`) is mocked the same way: an `api.stripe.com` id of the form `<prefix>_<base64url JSON>` is answered with that JSON, the creates echo their form body back in the URL they return (`stripeEchoedForm`), and a request without the test key or a pinned `Stripe-Version` is a 401; the ships-dark test calls the Worker's `fetch` directly with `STRIPE_SECRET_KEY` unset.
