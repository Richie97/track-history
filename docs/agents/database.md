# Database and seed data

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

## Migrations

**Database** (`migrations/`, applied in order by wrangler): schema changes are new numbered migration files, never edits to existing ones.

`0017_subscriptions.sql` adds `subscriptions` (unique on `(provider, external_id)`) and `users.entitled_until`, the latter **trigger-maintained** like every other derived column here — recomputed on every insert, update and delete of a subscription row, so a support script or a backfill that writes the table directly cannot leave a user's tier stale. `subscriptions.signed_date` is the ordering guard on Apple's writes: Apple retries a failed notification for days carrying its *original* payload, and a client can re-post any JWS it still holds, so a write whose payload was signed before the row's current one is refused (`applyStoreState` returns false and the webhook acks it as stale). `tracks`/`events`/`sessions`/`vehicles` (and the garage tables from `0012_garage_logbook.sql`: `parts`, `part_measurements`, `setups`) carry an `updated_at` (ms) maintained entirely by triggers (`0011_updated_at.sql`, `0012_garage_logbook.sql`) — inserts and updates bump the row, and nested writes bump ancestors (laps → session → event; measurements → part → vehicle; setups → event) — so route code never touches it; it drives the frontend's offline-cache staleness checks.

`0018_laps_device_timed.sql` adds `laps.device_timed`, the per-track leaderboards' eligibility flag (NS-33): trigger-maintained on lap insert and on any rewrite of `sessions.channels`, set when the session's channel blob carries a lap entry with the lap's exact `time_ms` — the same match the channel graphs use — and backfilled by the migration, so it is never route-set and a support script cannot leave it stale. `laps.time_ms` is never updated by any route; a route that starts to owes the column an `AFTER UPDATE OF time_ms` trigger.

`0020_session_conditions.sql` adds `sessions.ambient_c` and `sessions.elevation_m` (#191), trigger-maintained from `sessions.channels`' `meta` on insert and on any rewrite of the blob, and backfilled — the same arrangement as `laps.device_timed`, and for the same reason: reading one number out of a megabyte of per-lap arrays once per session is the wrong shape for a query that spans a logbook. `eventSelect` aggregates them as `ambient_lo_c` / `ambient_hi_c` (MIN/MAX, not an average: the laps LEFT JOIN repeats a session's row once per lap, so an average would silently weight by lap count, and a day that warmed from 15 °C to 32 °C is the confounder the band exists to show) and `elevation_m` (a MAX: it is a per-recording range, not a sum). Both are outside the Pro strip on purpose — a temperature is context for a lap time, not analysis of it.

`0019_vehicle_target_hot_psi.sql` adds `vehicles.target_hot_psi` (REAL, nullable psi) — a plain column, route-set, no trigger; it reached the golden captures and so both native `Vehicle` / `GarageVehicle` models, which decode it and read nothing from it.

`0023_vehicle_geometry.sql` adds `vehicles.wheelbase_mm` (INTEGER) and `vehicles.steering_ratio` (REAL) — #208's two spec-sheet constants, plain route-set columns with no trigger, both nullable so a car with neither behaves exactly as before.

`0024_car_catalog.sql` is **generated** (`seed/cars/generate.mjs`, see Seed) and adds `car_catalog` — one row per car *generation* with `make`, `model`, `generation`, `year_from`/`year_to`, `wheelbase_mm`, a nullable `steering_ratio` and a `source` line saying where both numbers came from, unique on `(make, model, generation)` — plus `vehicles.catalog_id REFERENCES car_catalog(id)`, the same identity-not-ownership role `tracks.catalog_id` plays. Two rules there: once `0024` has been applied remotely, additions go in a *new* generated migration (`--append`), because wrangler never re-runs an applied file; and rows are never deleted, since a vehicle may reference any id ever issued — a wrong number is fixed with an `UPDATE` in a new migration and the inputs corrected to match.

`0025_event_costs.sql` adds the four `events.cost_*_cents` line items (#147) — plain, route-set, nullable INTEGER cents with no trigger; `cost_cents` is computed in `withComputed`, not stored, and the goldens carry three of the four filled on the rich event so both native `Event` models decode a number and a null on the same row.

`0026_track_catalog_length.sql` adds `track_catalog.length_m` (NS-36) — integer metres, seeded from each venue's published figure for the layout the catalog row names, with the layout-sensitive rows commented; the three names that pin no single layout (MotorSport Ranch, Pocono, Utah Motorsports Campus) stay NULL on purpose. `GET /api/catalog` still selects only `id, name`. A wrong length is corrected by a new migration.

Catalog rows are matched **by name** in every later migration (`0026`, `0040`, `0041`), so a row added or renamed by hand in the hosted database silently misses them — or, for an `INSERT`, fails the deploy on the name's `UNIQUE` constraint. Both happened: `0041` therefore inserts with `OR IGNORE`, and `0042_vir_full_catalog_name.sql` repairs a hand-edited "Virginia International Raceway  (Full)" (two spaces) that had no length or coordinate. Add catalog rows with a migration, never by hand, and write a catalog `INSERT` as `INSERT OR IGNORE` (`test/unit/locate.test.js` reads both spellings).

`0027_session_odometer.sql` adds `sessions.odometer_km` (#192) from `channels.meta.odometerKm` — the car's lifetime odometer at the end of the session — trigger-maintained and backfilled exactly as 0020's conditions columns, and deliberately selected by no session response: it reaches a client only through `GET /garage`, so on every client's vehicle page it sits in the Pro half beside the hours.

`0028_oauth.sql` is the MCP authorization server's storage (#316): `oauth_clients` (a registered or metadata-document client), `oauth_grants` (one per user and client — the connected-app row Settings lists and *Disconnect* deletes, its codes and tokens cascading), `oauth_codes` and `oauth_tokens` (`access` / `refresh`), every secret SHA-256-hashed like `auth_sessions`. It is **deliberately separate from `auth_sessions`**: an MCP token is audience-bound to `/mcp` and read-only, and as an `auth_sessions` row it would open every `/api` route, writes included.

`0029_part_mounts.sql` adds `parts.size` and `part_mounts` (`part_id`, `mounted_on`, `removed_on`, both inclusive) — the stretches a part was on the car, backfilled one per existing part.

**Trigger-maintained against the part's own dates**: an insert into `parts` mounts it from `installed_on` (so the seed, a support script or an older client creates an equipped part), setting `retired_on` closes the open mount, clearing it reopens the mount that closed on that date (a part retired from the shelf stays on the shelf), moving either date moves the mount that sat on it, and mount writes bump the part's and vehicle's `updated_at`. Only the equip/unequip routes, and a create with `equipped: false`, write mounts directly. The seed's parts take an optional `mounts: [[on, off], …]` and `size`.

`0030_part_mount_sessions.sql` adds a swap point to each end of a mount: `mounted_event_id` / `mounted_after_session_id` and `removed_event_id` / `removed_after_session_id` — the event a swap happened during and the last of its sessions before it (NULL: the event's start), "after" so sessions logged later run on the part that went on. The routes set them: `swapPoint` in `routes/vehicles.ts` puts a swap on a date one of the car's events covers after that event's last logged session unless the body names `after_session_id`, and `PUT /parts/:id/mount` edits a part's latest mount start and moves whatever came off at the old point with it. A `BEFORE DELETE ON sessions` trigger moves a point off a deleted session to the one before it, and two triggers drop a point whenever 0029's triggers move its end's date — either way the mount keeps meaning where the swap was, or falls back to the date rule.

`0031_coaching.sql` (NS-38) adds `coach_grants` (one per student + coach, `UNIQUE` and `CHECK (student_id <> coach_id)`, `last_viewed_at`), `coach_invites` (token SHA-256-hashed, `expires_at`) and `users.profile` (JSON, plain and route-set); both tables cascade from `users`, so deleting either account ends the grant.

`0032_lap_clips.sql` (NS-45) adds `lap_clips` (one per lap, `UNIQUE(lap_id)`, `uploading` → `ready`, the R2 key `clips/<userId>/<clipId>.mp4`, `AUTOINCREMENT` so a key is never reused while its tombstone waits), `lap_clip_parts` (the etags until `complete`) and `lap_clip_tombstones` (no foreign keys).

**Deleting a row never deletes the object**: an `AFTER DELETE` trigger tombstones every clip row that goes — the clip, its lap, session, event or track, and the account, since `users` cascades (SQLite fires child triggers on a cascade, and `test/api/clips.test.ts` asserts it) — and the daily cron's `sweepClips` deletes the object or aborts the upload behind it, then drops uploads abandoned for a week. A clip arriving, turning ready or going bumps its lap's session and event `updated_at`.

`0033_item_shares.sql` (NS-48) adds `item_shares` (`user_id`, `token` UNIQUE, `event_id`, nullable `session_id`, `created_at`) — one shared link per event (`session_id` NULL) or session, enforced by two **partial** unique indexes because a plain UNIQUE treats every NULL as distinct; the token is stored in the clear, like `share_slug`, so the owner can copy it again, and the row cascades from its event, session and user. No trigger touches `updated_at`: sharing is not an edit.

`0039_lap_shares.sql` (NS-56) adds `item_shares.lap_id` and `lap_b_id` (both cascading from `laps`) for the lap and two-lap-comparison kinds, and **drops and re-creates the session index** with `AND lap_id IS NULL` — a lap's row fills `session_id` too — beside new partial unique indexes on `(lap_id)` and `(lap_id, lap_b_id)`; the pair is ordered, so A against B and B against A are two links.

`0043_wrapped_images.sql` (NS-36, #155) adds `wrapped_images` — `(user_id, year)` primary key, `image` (a 1200×630 JPEG `BLOB`, capped at 400 KB by the route) and `updated_at` in ms, written by the upsert in `PUT /api/wrapped/:year/image` rather than a trigger, since it doubles as the `og:image` URL's cache-buster. The season's link-preview poster, uploaded by the owner's browser. In D1 and not R2 so that `ON DELETE CASCADE` from `users` is the whole of its cleanup — no tombstone, no sweep. D1 hands the blob back as an array of byte values, which the share route turns into bytes.

`0034_stripe.sql` (NS-49)

**rebuilds `subscriptions`** to widen its `provider` CHECK to `stripe` — SQLite cannot alter a constraint — by copy, drop and rename, and so **re-creates both indexes and all three `subscriptions_entitled_*` triggers verbatim**, since triggers die with their table and a table without them still accepts every write while `users.entitled_until` silently stops following; `test/api/billing-stripe.test.ts` asserts they exist and recompute and `test/unit/migration-stripe.test.js` runs the migration over Apple, Google and legacy rows on Node's SQLite. A future change to those triggers owes the same rebuild-or-replace care. It also adds `users.stripe_customer_id` (unique, nullable), never exported (`FORBIDDEN_EXPORT_KEYS`).

`0035_youtube.sql` (NS-46) adds `youtube_connections` (one per user; `refresh_token_enc` / `access_token_enc` AES-GCM-encrypted, `status` `ok` / `revoked`, `verified_at` for the 30-day re-check), `youtube_connect_tickets` (hashed), `youtube_uploads` (one per clip, `UNIQUE(clip_id)`, cascading from it; `session_url_enc` encrypted, `bytes_sent` as YouTube last acknowledged it, `lease_until`, `error` the words the lap page shows — while `queued`, a wait), `youtube_daily` (the project budget by Pacific day) and `youtube_revocations` (no foreign keys), filled by an `AFTER DELETE` trigger on `youtube_connections` — so disconnecting and the account's own deletion (through the `users` cascade) both leave a grant for the cron to revoke, NS-45's tombstone arrangement again. An upload row arriving, changing status / video / privacy or going bumps its clip's session and event `updated_at`; `bytes_sent` deliberately doesn't (the lap page polls the status route for progress).

`0037_session_trace_geo.sql` (NS-53) adds `sessions.trace_geo` — JSON `{ "lat", "lon" }`, the origin the session's trace was projected from; plain and route-set with no trigger, NULL for every session saved before it (the origin was never kept, so there is no backfill — those borrow an anchor at read time). Both native `Session` / `LeaderboardLap` models decode it as `TraceGeo`, which the phones' map viewers read.

`0021_leaderboard_share_laps.sql` adds `users.leaderboard_share_laps` (NS-35) — likewise a plain, route-set preference with no trigger, since it is not derived from another column. It is a **second flag rather than a widening of `leaderboard_opt_in`** on purpose: that opt-in's copy, on every client, promises "exactly two things — your name and your best device-timed lap", and a driver who agreed to that has not agreed to publish their telemetry, so default 0 leaves every existing opt-in meaning exactly what it did.

## Seed

**Seed** (`seed/generate.mjs`): reads `seed/data.personal.mjs` if present (gitignored — real personal data), else `seed/data.example.mjs`, and writes `seed/seed.sql`. Beyond tracks/events/sessions, the data file can export `VEHICLES` (garage vehicles with consumable parts + wear measurements — a vehicle may name a `catalog` generation as `"make|model|generation"`, which links it and pre-fills its geometry inline the way a pick in the app does, and/or give `wheelbase_mm` / `steering_ratio` directly), `SETUPS` (per-event-day setup sheets, referencing parts by key) and `DEFAULT_CAR` (applied to events without their own car) — all optional, so older personal data files still generate.

**Car catalog seed** (`seed/cars/`, #221 — `seed/cars/README.md` is the full write-up): `generate.mjs` writes `migrations/0024_car_catalog.sql` from three inputs — `list.json` (the generations, each with a Wikidata item for its wheelbase or a cited manufacturer figure in mm or inches), `steering.json` (the hand-curated ratios, each with a citation; a variable-ratio rack the maker only quotes as a range is `null` with a note, since a single number for it would be a guess) and `wikidata.json` (the committed snapshot of Wikidata's P3039 answers, rebuilt by `--refresh`, so the migration regenerates byte-identically offline). The generator refuses a ratio without a citation, a row without a wheelbase, and a steering entry for a car the list lacks; `test/unit/car-catalog.test.js` pins every generated row inside the server's validation ranges and the committed migrations to exactly the rows the inputs describe, so an input edit without a regenerate fails CI. The list is deliberately short — a car it lacks is typed by hand in the vehicle form. `contracts/generate.mjs` picks the fixture Corvette from it, so the four vehicle goldens carry the link and the pre-filled geometry and both native `Vehicle` / `GarageVehicle` models plus `CatalogCar` decode it (`car-catalog` golden); the pickers themselves are #222.
