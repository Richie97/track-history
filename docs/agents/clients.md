# Rules the three clients share

Reference notes for agents, split out of `AGENTS.md`. Read this before working in the area it covers, and update it in the same change as the code it describes.

**Native clients** (`apps/`, the shipped iOS and Android apps — one spec per `NS-*` id in `docs/specs/native/`, which also records the fixed decisions and the deliberate web/native feature split). Conventions: ported logic keeps the **same function and constant names** as its JS original so the two diff by eye, and ports its JS test cases with it; `src/` and `public/` must not change for this work. See `apps/ios/README.md`.

## Which client gets which feature

**Three clients, and "add it everywhere" is not the default.** The web app (`public/`), iOS (`apps/ios/`) and Android (`apps/android/`) are maintained in parallel against one backend, and the feature split between them is a decision already taken per feature — recorded in `docs/specs/native/README.md`, which is the file to consult (and to update) before adding something to "the app". The shape of it: **web-only** are the desk-bound long tail — year in review, the *two-event* compare overlay, the setup-vs-lap-times diff — plus the PWA install path; **native-only** are the live GPS lap recorder and CarPlay; **video telemetry import** (PDR/GoPro parsed on-device) landed on iOS first (NS-30) and is now on Android too (NS-32), so it is native-only alongside the recorder — the browser keeps the same parsers; **`.vbo` import** is on all three clients since 2026-09 (Porsche Track Precision exports on the phone), ported as `VBO` to the Kit and `:core` and pinned by `contracts/logic/vbo-parsers.json` over the committed files in `contracts/logic/vbo/` — and so is Track Precision's **`.csv`** export, as `TrackPrecisionCsv`, pinned by `contracts/logic/csv-parsers.json`. Everything else — the logbook, the garage and its car-catalog picker (#222), offline reads and writes, charts, the two-lap telemetry compare (#165), sector splits and the theoretical best lap (#146), session conditions (#191), the per-track leaderboards and opening a lap on one (NS-35), Season Wrapped's story (NS-36 — its public share page stays web), sharing, settings — is on all three and should stay that way.

**The setup notebook, its tire-pressure loop, session notes and track-day costs (#147) are on all three since NS-40** (`docs/specs/native/NS-40-paddock-loop.md`): the notebook and form helpers are ported as `Garage` (`SETUP_FIELDS` … `diffSetups`, `previousSheet`), `Health` (`pressureLoop`, `nextTimeNote`, `recordHotSheet`, `nextDaySheet`) and `Costs` to the Kit and `:core`, pinned by `contracts/logic/setups.json` and `costs.json`; on both phones the loop sits **under the notebook on the event page**, not on the Car tab, because there the channel panel is a sheet or a destination of its own. Year in review — so the cost-per-second headline — stays web-only.

**Best-lap video clips (NS-45) landed native-first**: saving one is a passthrough cut of the source video at import, which the phones get from AVFoundation / MediaExtractor + MediaMuxer and the dependency-free web had to write by hand — which NS-47 did (`mp4cut.js`, `clip-upload.js`, above), so the web now saves clips as well as playing, downloading and deleting them.

**iOS saves them since ticket 2** (Android since ticket 3: the *Best-lap video clips on Android* paragraph above): the review's *Save best-lap video* row reads `LapClips.clipOffer` (the port of `public/js/import/clip.js` under the same names, pinned by `contracts/logic/lap-clips.json`; `ImportedClip` / `ReviewItem` keep a `ClipSource` — the security scope — and the file size until save or discard) — titled *Save lap videos* with a Best lap / Every lap segmented picker when `offersEveryLap` holds (NS-50; `ReviewModel.clipScope`, Best lap in every review) — and saving posts each session first and then hands each lap of `clipCandidates(parsed, scope)`, with its `lapNum`, to `AppServices.clips`, a `ClipUploader`, never awaited; it cuts one lap and runs one job at a time, in order, and the lap page finds its job by `ClipUploader.LapKey` (`ClipUploadQueue.isFor` on the lap number, the time alone for a job from before it). `App/Import/ClipCutter.swift` is an `AVMutableComposition` of the first *moving-picture* video track (a JPEG track — PDR 2.5's cover image — is skipped) and the first audio track, exported passthrough with no file-level metadata to `Application Support/clips/` (excluded from backup); the offset is **read back from the file** — the source keyframe, found through the track's *segments* because an encoder with B-frames offsets its media time behind an edit list, plus how far the output's edit list skips — and a Corvette PDR, whose AAC AVFoundation doesn't expose at all, is cut by `ClipRemux` (`AVAssetWriter`, video from an `AVAssetReader`, audio as raw AudioToolbox packets) so it keeps its sound. `ClipUploader` (`App/Import/ClipUploader.swift`) drives the Kit's pure `ClipUploadQueue` — a job waits while its session id is a temp id in the offline queue (`APIClient.tempIdState`), then create → parts → complete, with the transition table on the type — keeps the manifest beside the cuts, sends each 50 MiB part from its own file on a **background `URLSession`** (`AppDelegate` hands back its relaunch events), Wi-Fi only unless Settings' *Upload lap videos over cellular*, and is cleared on sign-out.

**No part may sit in the background session forever**: a part handed over while the app is backgrounded is discretionary to iOS whatever the configuration says (its description carries ` bg`) and is re-sent the moment the app is active; a part that sends no bytes for `stallSeconds` (60) with the app in front and a usable network is cancelled as a transport failure; and becoming active or arriving on a new usable network clears every backoff. The lap page reads `ClipUploader.Status` — preparing, waiting for its session / a connection / Wi-Fi, uploading with a percentage, or *interrupted* with *Retry now* — and an upload the queue drops is told once (`takeFailure`, the manifest's `failedCuts` now carrying the `DropReason`) rather than vanishing. A review that stages its drafts for the New Event form stages their cuts with them (`ClipUploader.stage` / `sessionPosted`). The lap page's `LapVideoSection` (`App/Screens/LapVideo.swift`) plays the signed URL through `auth.api.scoped(to: owner)` in an embedded `AVPlayerViewController` (`LapPlayerView`) — never SwiftUI's `VideoPlayer`, which draws no fullscreen button — — the menu (*Download*, *Delete*) for the owner only, `ProUpsellCard` plus *Delete* for a lapsed owner, the student-tier sentence for a coach of a free student — and the event page's lap row carries ▶, spoken "has video". `LapClipUITests` runs it end to end; the fixtures have no picture, so DEBUG `-syntheticClipVideo YES` gives the cutter a generated H.264 file. Both native `Lap` models already decode `clip` (`LapClip`, `sizeBytes` absent under the coach mount) and both `User`s `clips` (`ClipStorage`). A change to shared behavior therefore owes the ports their update: pure logic that exists in more than one language keeps the **same function and constant names** as its JS original so the copies diff by eye, carries its JS test cases with it, and is pinned by a fixture in `contracts/logic/` generated from the web implementation — assert against the reference, never against the other port. Response shapes are pinned the same way one level up by `contracts/golden/`.

The iOS and Android **shells that used to live in `mobile/`** — the web app wrapped in a WebView, with a `www/` sync step, a CarPlay bridge plugin and a CORS allowance in `src/` for its local origins — are gone (NS-27). Nothing in the tree should reference them; if you find something that does, it is stale rather than load-bearing. The platform seam they filled in (`public/js/platform.js`) and the recorder UI behind it were unwound in **#139**: the web app is same-origin/cookie-auth only, and `public/js/record/core.js` + `remote.js` remain solely as the reference implementations the Swift and Kotlin recorder ports are asserted against (`contracts/logic/recorder.json` and `remote-attach.json` are generated from them — see the `js/record/` bullet above). The NS-15…NS-17 specs still cite `js/record/ui.js` as the lifecycle reference; that file is deleted, so read it from git history if a port question ever needs it.

## Units

**The unit preference is on the account, and all three clients render it.** `User.units` exists in both native models (`UnitSystem`, optional so a `/me` cached before the field still decodes, `effectiveUnits` reading nil as imperial) and the golden tests map `units-set`/`me-units-metric`.

**Android**: `Units.kt` in `:core` is the port of `public/js/units.js` under the *same* names (`KPH_TO_MPH`/`MPS_TO_MPH`, `speedUnit`/`convSpeedKph`/`convSpeedMps`/`fmtSpeedKph`, `fmtDist`/`distAxisTicks`/`fmtAccuracy`, `tempUnit`/`tempToDisplay`/`tempToStored`/`fmtTemp`/`tempInputSpec`, `usUnits` — plus `healthUnits`, the same mapping for `Health.Units`), with `wearLimitHint`/`defaultMeasurementUnit` beside their JS originals in `Garage.kt`, `channelDefs(units)` as `Channel.unit(units)`/`convert(raw, units)` in `ChannelGraphs`, and `Telemetry.metricsSummary` (the import review's preview line; `importNotes` no longer writes it into the notes, since 2026-11) taking the system the review is shown in. It carries the JS test cases (`UnitsTest`) and is pinned to the web by `contracts/logic/units.json` — whose rows are chosen for the two ways a port goes wrong, JavaScript's `Math.round` on a negative tie and `toFixed` rounding the exact binary value (`Units.toFixed` is `BigDecimal`, not `%.1f`, because `(0.15).toFixed(1)` is "0.1"). The five scattered m/s→mph and km/h→mph constants collapsed onto it. The preference reaches the screens as `LocalUnitSystem` (`ui/UnitSystemLocal.kt`), published once by `MainActivity` off `AuthState.units` — the counterpart of the web's `currentUnits()` minus the cache, since every screen composes under the signed-in user — and every display site reads it: the event form's temperature label and entry (`EventFormModel.temp` is the *typed* number, converted to whole °F by `tempToStored` on save and back by `tempToDisplay` on load, so the server never sees a °C), the session conditions tag and stats line, the record screen's speed and accuracy, the channel charts' speed axis and distance ticks, the balance table's corner places, the trackmap's spoken speed range, the health strip, the progress chart's conditions wash, the two head-to-head tables, the import review's top speed and the garage's tread-depth defaults and hints. Settings' *Units* card sits beside the theme card, backed by `UnitsStore` — the seam `AuthController` implements next to `ChecklistTemplateStore`, so a save writes back to the auth state and the whole logbook redraws — and `ApiClient.setUnits` is a live write off the offline whitelist, asserted by `OfflineStoreTest` and `UnitsTest`. **iOS**: the Kit's `Units.swift` is the same port under the same names, carrying the JS test cases (`UnitsTests`); it reaches the display sites as the `\.unitSystem` **environment value** installed at the app root rather than as a read of `AuthController`, because the charts are also opened without one (the `-channelGraphs` launch argument) and a missing value falls back to imperial where a missing controller would trap. Settings offers the toggle beside the theme and `APIClient.setUnits` writes it live, off the offline queue, as on Android; the `2.236936`/`1/1.609344` constants scattered through the app collapsed onto the module with it.

## Large screens (NS-34)

**Large screens** (iPad, foldables, tablets — NS-34, `docs/specs/native/NS-34-large-screens.md`): both native apps share a **layout class** derived from *window width*, never from device or idiom — `LayoutClass` in `apps/ios/App/DesignSystem/` and in `:app`'s `ui/`, compact (< 600) / medium (600–839, the phone layout capped at `PAGE_MAX` and centred) / expanded (≥ 840, two-pane list-detail with the analysis panel beside the track map). `PAGE_MAX` mirrors `--page-max` in `public/style.css` and is emitted by both token generators; the breakpoint constants `MEDIUM_MIN_DP` / `EXPANDED_MIN_DP` are pinned by a unit test on each platform so they cannot drift. Four rules there are load-bearing: **compact is the phone layout unchanged**; the class is **observed while the app runs** (Split View, Stage Manager and folding cross a breakpoint without a relaunch); **the recording and sync banners and the review overlay span the whole window**, never one pane; and **width does not reopen the deferred list** — web-only features stay web-only on a 13-inch iPad. The class lives in the app targets, not the Kit or `:core`, because it is derived from window APIs and both pure modules forbid UI-framework imports.

**Ticket 1 has landed** (`LayoutClass.swift` + `LayoutClass.kt`, `LayoutTokens.generated.*` from `--page-max` and `--page-gutter`, the content column capped and centred, the tracks and garage grids filling by width, and iOS's `TEButtonStyle` no longer stretching past `TESpacing.controlMax`), so the shape of it is now real code: on iOS an environment `LayoutMetrics` is measured by `RootView.measuringLayoutClass()` and narrowed again by `TEPage`; on Android a `LocalLayoutMetrics` is published by `ProvideLayoutMetrics` in `MainActivity` and narrowed by `PageColumn`, which `AppNavHost` wraps every logbook destination in via `pageComposable` — **`Route.Record` and `Route.Import` keep the plain `composable`**, since the record screen is a phone-in-a-mount layout at every width and the importer hands straight over to the modal review. `LayoutMetrics.columns(minimum:)` is the native reading of the web's `repeat(auto-fill, minmax(280px, 1fr))` and is pinned against it on both platforms. Two consequences worth knowing: the iOS app gained its **first unit-test target** (`apps/ios/Tests`, run in `ios.yml`) purely to hold the breakpoints, since the Kit cannot; and iOS and Android **classify a phone in landscape differently** — UIKit's `.compact` horizontal size class keeps an iPhone one-column whatever its width, while Android has no such signal, so a 915dp Pixel window lands in expanded. That costs nothing while medium and expanded are the same layout, and it is a decision the two-pane ticket (#216) has to make with a height or `smallestScreenWidthDp` guard.

**Ticket 2 has landed too**: at expanded width the shell is list-detail — a `NavigationSplitView` on iOS (`RootView.splitShell`) and a `ListDetailPaneScaffold` on Android (`ui/TwoPaneShell.kt`) — with the dashboard as the list pane.

**On Android the scaffold is there at every width**, its list pane `Hidden` below expanded and the detail's `PaneWidth` passing the window's metrics through (`measure = false`), so the `NavHost` sits at the same place in the tree in both shapes: a phone turned sideways is an expanded window here, and when the detail was a bare `Box` below the breakpoint every destination's `rememberSaveable` was lost on rotation — saved state is keyed by position (`TwoPaneShellTest`). Five rules there are load-bearing.

**One path, two roots**: iOS keeps the single `AppRouter.path` and only the *root* differs (the dashboard in the stack shell, `DetailPlaceholder` in the split), and Android keeps `Route.Dashboard` as the Events graph's start destination (and `Route.Garage` the Garage graph's, NS-37) and changes only what it *draws* (`dashboardAsDetailPlaceholder` / `garageAsDetailPlaceholder`) — which is what makes a deep link land the same place at every width with no width-dependent branch to fall down.

**The list pane replaces the detail rather than deepening it** (`AppRouter.open`, Android's `popUpTo(Route.Dashboard)`), and at compact width that is provably the same operation as a push, because the dashboard is the stack's root there — so neither dashboard carries a width check for navigation. Which is exactly why **a destination is keyed by its route** on iOS (`.id(route)` in `RootView.destination`): a replacement lands at the *same* stack depth in the same screen type, so SwiftUI keeps that view's identity and every `@State` with it — and each screen builds its model in a `.task { if model == nil … }`, so the detail went on showing the first row you picked while the list pane's selection border moved on without it. The `.id` does nothing at compact width, where a push lands at a new depth, which is what made it easy to leave out and impossible to notice in a stack. The **window-owning routes are excluded** from the keying on purpose: they are never replaced in place, while `remapTempIds` does rewrite their ids when an offline-created event's insert flushes — and keying them would let that rewrite restart a video parse or pop an unsaved recording's review.

**The recorder and the importer own the window** at every width (`Route.ownsTheWindow` on iOS presents them over the split — every door goes through `AppRouter.push(_:at:)` / `open(_:at:)`, the dashboard's and the event page's alike (#270), and finishing one inside the cover closes the cover (`finishWindowOwningTask`) rather than emptying the path under it; Android drops the scaffold to one pane for those destinations), because a phone-in-a-mount layout on half a tablet is worse than on a phone — but **owning the window is about reach, not about stretching a form across it**, which is a distinction Android had to learn twice. Those two destinations skip `pageComposable`, so on a 1200dp tablet the review drew its start/finish picker 1200dp wide and 280dp tall (`TraceMap.fit` scales uniformly, so the circuit came out small against the short side with most of the row empty — the worst shape there is for the one thing on that screen whose job is to be tapped) and gave Save and Discard the full width. `FormColumn` / `FORM_MAX` in `ui/LayoutClass.kt` is the answer: the covering `Box` keeps the window and paints the background, its content keeps a 640dp column, and the picker's height grows with that column — bounded by the window's *height* as well, because a phone in landscape is an expanded window on this platform and 915dp of map does not go in a 412dp-high one. 640 rather than `PAGE_MAX` because a page is a grid of cards that improves as more fit a row and a form is one column of fields that does not — and on iOS **that cover carries its own way back** (`fullWindowBack`, a `cancellationAction` on the cover's stack). A `fullScreenCover` is the *root* of its own stack, so the system draws no back button and there is no stack behind it to swipe: without it the recorder was a room with no door on an iPad, reachable from the dashboard's own button and leaveable only by force-quitting. On the root only, which the toolbar's scoping gives for free — the review is *pushed* onto that stack, so it keeps its own back and stays undismissable from outside, and leaving never stops a recording, which is what the window-spanning banner is for.

**The banners span the window and the review overlay covers both panes**, which is NS-18's rule and the easiest thing to break once there are two panes. And **the detail pane never shows the dashboard twice** — it names the next upcoming event or says "Pick an event". Android's `compileSdk` moved to **37** for `material3.adaptive` 1.3.0 while `targetSdk` stays 36; both CI workflows install the platform explicitly. A pane **publishes its own content width** (`measuringPaneWidth()` on iOS, `PaneWidth` on Android) while keeping the window's class — without that a sidebar inherits the window's column and lays its cards out three across at 110pt, which is what a narrow-looking pane actually is.

**Ticket 3 has started**: the event page splits again at expanded width into the page and an `AnalysisColumn` — the selected session's track map above its channel panel, in one eyeline — with the session cards' channel control becoming a *selection* (the iOS sheet and the Android inline panel both stand down) and the best lap's channel-carrying session pre-selected. The column is a **sibling of the list, never a row in it**, which is the constraint `LapChannelChart` documents rather than a preference.

**Tap-to-mark cross-linking** landed next, which is what the column was for: tapping a sample on the friction circle marks that driven distance across every chart sharing the axis and **rings the place on the track map**, the behaviour the web had on hover and the README recorded as web-only *because* the phones' panels were sheets. The hit is a `ChannelHit` (`chIdx` / `k` / `frac`, the web's `onHover` payload under the same names) and the fraction reaches the map through `TrackMap.traceIndexAtFraction` — a new port of `public/js/trackmap.js`'s pure half in the Kit and `:core`, pinned by `contracts/logic/trackmap.json`. It walks **cumulative chord length, not sample index**: a trace is denser where the car was slower, so indexing is wrong by whole corners, and the fixture pins exactly that difference. A hit from a lap that is not the traced one rings nothing — the stored trace is the best lap only, the same constraint `Limits.limitMarkers` works under. The **health per-lap table** and the **balance table's wide columns** followed, both at expanded width only and both the reversal of a stated phone-width sacrifice: fifteen columns is a desk layout, and a corner's place and peak G ride under its label on a phone because that is what keeps the table inside the width. The health table is **its own card** on both platforms rather than the last thing inside the strip's — that card declares itself one accessibility element, so a table placed inside it would be invisible to VoiceOver and TalkBack as well as to a test. The balance table's **corner rows are a hit source** too, carrying `chIdx: nil` because a corner is a place every lap shares. Both tables' width decisions read `layout.contentWidth`, never the class: the panel is itself a narrow right-hand column at expanded width, and reading the class there would put five columns into 380pt.

**So does the decision to split at all**, and getting that wrong is what shipped: `LayoutMetrics.sideColumnWidth(fraction:minimum:maximum:)` — the same rule and the same numbers on both platforms, pinned by each `LayoutClassTest` — answers nil where the page's own column has no room for two, and every splitting page (the event's analysis, the track's compare, the vehicle's part) asks it rather than the class. An iPad in portrait is an *expanded window* with a 683pt detail pane once the sidebar is showing, and two columns do not go into that: it split anyway, and the right-hand column ran off the side of the screen. It is now one column there — the trace back in the list, the panel back to being a sheet — which is the layout that pane has room for. Two SwiftUI mechanics under it, both stated where they bite.

**`measuringPaneWidth()` goes inside a fixed frame, never outside one**: it measures with a `GeometryReader`, which is greedy, so `column.frame(width: w).measuringPaneWidth()` hands an `HStack` two flexible children and it halves the row — the fixed width then decides nothing, and whatever it was is either short of the half (a strip of dead background) or over it (content off the window). And **a pushed screen does not inherit its pane's measurement**: applied to a `NavigationStack` the modifier reaches that stack's root and not what `navigationDestination` builds, so every detail screen was reading the *window's* width while being laid out in a pane a third narrower — `RootView.destination` therefore measures each destination, where the reader is inside the container it is measuring. Android has neither mechanic (a `Modifier.width` is a real constraint and `LocalLayoutMetrics` crosses the nav graph) and took only the `sideColumnWidth` half. It took it on two of its three splitting pages: **Android's track compare lives in `AppNavHost`'s `Route.Track` destination rather than in `TrackScreen`**, so it was missed with the other two and went on reading the window's class — splitting a 627dp detail pane into the compare's 380dp floor and a 230dp track page. `TrackCompareLayoutTest` now pins the wiring rather than the arithmetic: after tapping *Compare laps*, is the page still on screen beside it? A column and a destination differ in exactly that, at whatever widths the two containers choose. `UITests/TwoPaneUITests` pins the invariant the two mechanics broke — the column ends where the window ends, at both orientations, or is not there at all — because both were arithmetic that compiled and passed every unit test, and were wrong only once something laid them out.

**Sector headings are a hit source too** — tapping one says where that sector *begins*, which is behaviour NS-34 adds rather than a port (the web wires only the friction circle and the balance scatter to `onHover`); a sector is a range and the mark is a point, so the boundary is what gets marked, and the boundaries are computed thirds with nothing on the track to show them. And the **track page's two-lap compare opens as its page's right column** at expanded width — the same `CompareLapsScreen`, given a close control, because a sheet has a swipe-down and a column has nothing. One rule came out of wiring those taps and is worth carrying: every one of these chart cards is a **single accessibility element** (their cells are dozens of unlabelled numbers), so a tap added inside one is unreachable with VoiceOver and TalkBack unless it is also offered as a **named accessibility action** on the card — `accessibilityActions` on iOS, `customActions` on Android, both calling the same function the tap does. The **vehicle page** takes the same shape last: consumables on the left, the *selected* part's measurements on the right — logging a measurement on a phone happens inside whichever card you scrolled to, and the column gives it a fixed place. (The track-hours ledger that used to sit under the measurements is gone; see the garage note above.)

**Ticket 3 is complete.** The sector and shift tables needed no wide-column work — neither carries a place or a peak G under a label; that sentence in the spec is about the balance table, which is done.

**Ticket 5 has landed too**: pointer hover, the panel's keyboard shortcuts and drag-and-drop import. Four things there are load-bearing.

**A tap parks a mark and a pointer only borrows one** — the `Mark` pair in `LapChannelChart.swift` and `PanelPointer` in `:app`'s `ui/charts/`, both tested — so a mouse crossing a plot hands back whatever a tap had committed when it leaves; `hovered ?: parked`, and the other order reads just as well and is wrong.

**Hover is offered exactly where a tap already points** (the friction circle's samples, the balance corner rows, the sector headings, and on iOS the traces' read-out), and Android's `pointerHover` **ignores anything that is not `PointerType.Mouse`**, because a finger produces move events too and treating those as hover would mark and unmark on every scroll.

**The iPad shortcuts are titled `Button`s with `.keyboardShortcut`** — `1`–`4` for the tabs by their place in the bar, `[` / `]` to step the newest lit lap (`LapChannelPanel.stepped`, which skips laps already lit and wraps), ⌘F to hide the friction circle's envelope — rather than `onKeyPress`, because that is what registers them as `UIKeyCommand`s and lists them by name in the ⌘-key overlay; the two with no visible control to hang off are zero-sized invisible buttons, which does register, and `UITests/ChannelPanelKeyboardUITests` proves it — the one UI suite here that needs **neither a dev server nor sign-in**, since `-channelGraphs` opens the panel before the shell exists. And **the drop target on the event page** (`EventScreen.droppedClip`, `DroppedClip`) reads the clip in place through `loadInPlaceFileRepresentation`, inheriting NS-30's no-copy rule, with the trap stated at the call site: the URL it yields is valid **only inside the callback** — an in-place one survives because opening its security scope there extends it, and a provider that will only hand back a *copy* has that copy deleted the instant the callback returns, so the handler moves it out first and deletes it when the import is done. Android gets no drop target (the SAF picker and `ACTION_SEND` already cover it) and no shortcuts; its half of this ticket is the hover.

**Ticket 4 completes the epic** — foldable postures, Android only when it landed, since iOS then had neither a foldable nor a posture API (both arrived with the iPhone Duo; see the Duo paragraph below). Posture is deliberately **not** part of `LayoutMetrics`: a half-open Fold is the same number of dp as a flat one, and width says how much room there is while posture says where the room *is not*. It is `ui/FoldPosture.kt` — `Folds.geometry(halfOpened, horizontal, hingeFraction)` reducing the two facts `FoldingFeature` carries into `Flat` / `Tabletop` / `Book` plus where the crease falls, published as `LocalFoldGeometry` by `ProvideFoldGeometry` beside `ProvideLayoutMetrics`.

**`androidx.window` stays at the edge**: four lines read the window and everything decidable is a pure function over three plain values, so the postures nobody can produce on a desk are unit-tested rather than left to a Fold emulator profile — the same split `AutoRecording` uses. A hinge more than 35% from the middle is treated as flat, because a 15/85 split is a worse layout than an even one.

**Tabletop is the recorder's shape and the epic's one new feature**: the live timing above the crease and Start/Stop, fix quality and the attached event below it, weighted by the actual hinge rather than halving the window, because the half you glance at from the driver's seat and the half you reach for are different halves. Every other posture is the phone layout unchanged, and `RecordScreen` takes the posture as a **parameter** defaulted from the local, which is the seam its tests drive. Book posture is `bookDirective` in `TwoPaneShell`: the list pane's preferred width is the hinge fraction of the window, so the two-pane gutter lands on the seam — `defaultPanePreferredWidth` rather than `excludedBounds`, since the hinge on these devices is a seam and not a cutout to route around. The **fold/unfold audit** found one real bug and it was the one the spec had assumed was safe: `RecordingFlow` was built in `MainActivity.onCreate` against `lifecycleScope`, so every configuration change — a fold, a rotation, a font-scale change — threw away the picked start/finish line, the edited labels, the notes and the include flags, while `SignedInScaffold`'s `reviewing` flag is `rememberSaveable` and came *back*, reopening an empty review. It is now a `rememberScreenModel` in the composition, which is the right lifetime: longer than the activity, shorter than the process. Three confirmation dialogs on the vehicle page moved from bare `remember` to a saveable part **id** (a `Part` is not `Parcelable`, and an id re-reads rather than describing a stale copy), and the channel panel's tab and lit-lap state — `rememberSaveable`, but never once exercised through a restore — is now pinned by `PanelRestorationTest` through `StateRestorationTester`, because `rememberSaveable` fails at *runtime* on a value a `Bundle` cannot carry and an inspection is not a fact.

## Analytics

**Native analytics** (Google Analytics for Firebase, project `track-evolution-app`, the same GA4 property as the web): screen views by route **shape** and nothing else — no user id, no user property, no custom event. The shapes are the **web's own paths** (`/event/:id`, `/track/:id/leaderboard`, `/student/:id/event/:id`, `/wrapped/2026`), so one GA report counts a screen on all three clients; the screens the web lacks get paths in the same idiom (`/record`, `/import`, `/event/:id/lap/:id`, `/event/:id/session/:id/compare`), and sign-in is `/signin`. The mapping is `Route.analyticsPath` on both platforms under that name — an exhaustive switch / `when`, so **a new route fails to compile until it is named there** — pinned by `AnalyticsPathTest` (`:app`) and `AnalyticsPathTests` (the iOS app target) over the same table, which also asserts no path carries a digit (Wrapped's year aside), a slug or a token. Reported from `SignedInScaffold` on each new back-stack entry (`NavBackStackEntry.analyticsRoute()`) on Android and from `RootView` on each change of `AppRouter.analyticsPath` (the window-owning route, else the visible tab's top, else its root) on iOS, through `AppAnalytics` on each, which drops a repeat of the screen just reported.

**Collection is off by default and switched on only in release builds**: Android's manifest says `firebase_analytics_collection_enabled=false` and `AppAnalytics.start` enables it when `BuildConfig.ANALYTICS` (true for release, and for debug only with `-Pte.analytics=true`); iOS's Info.plist says `FIREBASE_ANALYTICS_COLLECTION_ENABLED=NO` and `AppAnalytics.start` configures Firebase only in a release build or a debug run launched with `-FIRDebugEnabled` — so the emulator, the simulator, Robolectric and every UI suite send nothing. Both switch off the automatic screen report (it can only name `MainActivity` / a hosting controller), the IDFV / SSAID, and the ad-storage / ad-user-data / ad-personalization signals; Android removes the merged `AD_ID` permission (`tools:node="remove"`) and iOS never links AdSupport, so there is no advertising id and no ATT prompt. The config files are committed — `apps/android/app/google-services.json` and `apps/ios/App/GoogleService-Info.plist` identify the Firebase apps and grant nothing — and iOS's `AppAnalytics` checks the plist is in the bundle before `FirebaseApp.configure()`, which traps without it. iOS links the `FirebaseAnalytics` SPM product (`firebase-ios-sdk`, declared in `project.yml`) with `OTHER_LDFLAGS = -ObjC`, which Analytics needs at run time and no build notices the absence of. A change to what is sent owes the privacy policy's *Analytics* section, the App Store privacy label and Play's Data safety form.

## Features described for both phones

**Sharing one event or one session** (NS-48) is on all three clients. **iOS**: the event's ⋯ menu and each session's menu carry *Share…*, hidden for a coach, opening `ItemShareSheet` (`App/Screens/ItemShareSheet.swift`) through the event page's single `FormSheet` `.sheet` — shared with *Edit label & notes*, because a second `.sheet` beside the channel panel's is the watchdog hazard — which POSTs `APIClient.createItemShare` and offers Copy, a `ShareLink` and *Stop sharing*; the Kit's `ItemShareKind` / `ItemShareLink` / `SharedItem` (whose `event` is the ordinary `EventDetail`) and `DeepLink.sharedItem(kind:token:)`, matched ahead of the slug rule, open `Route.sharedItem` and `SharedItemScreen`.

**Android**: *Share…* is a button beside *Edit event* and each session's *Edit* (the event page has no overflow menu there), hidden when `readOnly`, opening `ItemShareDialog` (`screens/ItemShare.kt`) whose requests run in `EventModel.sharing` (`ItemShareState`) rather than the dialog's composition; `:core` carries the same models and `DeepLink.SharedItem`, and a link lands on `Route.SharedItem(kind, token)` and `SharedItemScreen`. On both phones the owner routes are live writes off the offline whitelist (pinned by `ItemShareAPITests` / `ItemShareApiTest` and `OfflineStoreTest`), the public reads send no token and read past the cache, and the shared page is a **lean read-only screen built from the event page's pieces** rather than `EventScreen` under an owner — its ids are the owner's, so laps are rows, not doors, which would open the viewer's own rows with the same id. The channel panel opens to the response's `pro` (the owner's tier) with a neutral free-plan note in place of the upsell (`freeNote` on iOS's `LapChannelChart`, `LocalChannelFreeNote` on Android), clips play over the link's own signed URL (`LapVideoPlayer(signedURL:)`, `SharedLapVideoCard`), analytics reports `/share/e/:token` or `/share/s/:token`, and the words are `ItemShareText` on both, the same as the web's. Like `/share/<slug>`, a link opened in a **signed-out app waits for sign-in** — the browser is the no-account path.

## Empty states and first run

**An empty state is one component on every client, and it offers the next step when the page doesn't already** (#342): the web's `emptyHtml`, iOS's `TEEmpty(title:_:action:)` and Android's `TEEmpty(text, title, action)`. A failed load retries through one control — `TERetryButton` on both phones, *Try again* in the quiet / outlined style, and on the web the route's catch-all (*Couldn't load this* + the message + *Try again*, a 404 going to the *Not found* page instead) — never a *Retry* `TextButton`, and the two expanded-width detail placeholders (*Pick an event*, *Pick a car*) share `PanePlaceholder` / `TEPanePlaceholder`. A coach's read-only view gets the sentence without the action. The copy keeps one glossary on every client (#343): **event** for the thing you add, **track day** only when counting days, then **session** and **lap**; the web says *the Track Evolution app* where it points at the phone recorder, and the same message is worded the same on all three.

**An empty logbook is a first run, not a dashboard of zeros** (#344): with no event at all, every client's dashboard is one welcome card — *Add your first event*, plus *Record laps* on the phones while the recorder is idle, and under them the *New to track days? Start here* link to `site/docs/track-days.html` (the web's `.panel.welcome`, iOS's `welcomeCard`, Android's `WelcomeCard`) — and the web hides *Year in review* and the share panel until an event has started, since both count past events only. The two detail placeholders say so too (*Add your first event and it opens here.* / *Add a car and its page opens here.*), but only on an answer — offline with nothing cached is not an empty logbook. A review with no event to save onto offers **Save to a new event** in the save button's place: the drafts go to the New Event form through the same hand-off a new-event import uses (`AppRouter.stagedSessions`, `RecordingFlow.staged`) while the review waits underneath, intact — on iOS the form is pushed over the review (`EventFormScreen(onCreated:)`, which then holds no `eventFormDraft`), on Android the overlay closes and `RecordingFlow.awaitingNewEvent` brings it back if the form leaves the Events stack without creating — and a recording is forgotten only once its own draft is among those the form posted. The form it opens is **dated from the sessions** — the earliest session date, with `days` spanning to the latest — rather than today, since a clip or recording already knows its day. A few more of these are shared rules rather than per-client choices: a track's progress chart **waits for two timed events** (one point is a dot, not a trend) and says *The chart starts once two events here have a lap time.* in its place on every client, the share page included; **Wrapped's empty year** is *No track days in {Y}* for a finished year and *… — yet* only for the running one, and a shared link to such a year is that page, not *isn't shared*; a coach opening a logbook with **no events** gets one sentence (*{who} hasn't logged an event yet.*) in place of the tiles; and the public share page hides *Year in review* until an event has started, and its empty review offers no action — the reader isn't the driver.
